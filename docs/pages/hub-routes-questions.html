JS Express : Router({ mergeParams: true })

Quand un routeur est monté sous un chemin qui contient un paramètre — ici le :eventId de app.use('/api/events/:eventId/questions', …) — ce paramètre appartient au routeur parent. Par défaut, le routeur enfant ne le voit pas dans req.params. L'option mergeParams: true demande à Express de fusionner les paramètres du parent dans ceux de l'enfant, rendant req.params.eventId accessible ici.

Sans cette option, req.params.eventId serait undefined dans ce fichier, et openEventDb(undefined, …) échouerait. C'est un piège classique des routeurs imbriqués.

→ notion : openEventDb (cache LRU des bases d'événement) — vue dans eventStore.js

Invariant §11.1 : routes fixes avant /:id

// PUT /reorder/batch — déclarée AVANT /:id (sinon Express interprète "reorder" comme un id)
router.put('/reorder/batch', requireUser, requireOwner, (req, res, next) => { … });

// PUT /:id — déclarée APRÈS
router.put('/:id', requireUser, requireOwner, (req, res, next) => { … });
⛔ L'ordre de déclaration des routes (§11.1)

Express évalue les routes dans l'ordre et s'arrête à la première qui « matche ». Le motif /:id matche n'importe quel segment, y compris "reorder". Si /:id était déclaré avant /reorder/batch, une requête PUT /reorder/batch serait captée par /:id avec id = "reorder" (puis échouerait, ou pire ferait une action sur une « question reorder »). D'où la règle : toujours déclarer les routes à segment littéral avant les routes paramétrées. Même principe pour /export/csv dans gallery.js.

Le gel d'édition

const FROZEN_STATUSES = new Set(['live', 'closed', 'pushed', 'processed', 'purged']);

function checkFrozen(req, res) {
  const event = req.event ?? getEvent(getDb(), req.params.eventId);
  if (event && FROZEN_STATUSES.has(event.status)) {
    res.status(409).json({ error: `Édition impossible : événement en statut ${event.status}` });
    return true;
  }
  return false;
}

Comme dans events.js, on bloque la modification des questions dès que l'événement est live ou au-delà. req.event ?? getEvent(...) : on réutilise l'événement déjà chargé par requireOwner s'il existe, sinon on le relit. La fonction renvoie true si elle a déjà répondu (gelé) — l'appelant fait alors if (checkFrozen(req, res)) return;.

UPDATE dynamique sur champs partiels

PUT /:id permet de ne mettre à jour que certains champs. On construit le SQL en fonction de ce qui est fourni : 

const fields = [];
const values = [];
if (text !== undefined)         { fields.push('text=?');         values.push(text.trim()); }
if (max_duration !== undefined) { fields.push('max_duration=?'); values.push(max_duration); }
if (countdown !== undefined)    { fields.push('countdown=?');    values.push(countdown); }
if (enabled !== undefined)      { fields.push('enabled=?');      values.push(enabled ? 1 : 0); }
if (order_index !== undefined)  { fields.push('order_index=?');  values.push(order_index); }
if (fields.length === 0) return res.status(400).json({ error: 'Aucun champ à mettre à jour' });

fields.push('updated_at=CURRENT_TIMESTAMP');
values.push(req.params.id);
db.prepare(`UPDATE questions SET ${fields.join(', ')} WHERE id=?`).run(...values);

Même technique que updateEvent dans registry.js : on accumule les fragments colonne=? et les valeurs en parallèle, puis on assemble. Ici les noms de colonnes sont des littéraux dans le code (pas des clés d'objet externes), donc pas de risque d'injection sur les noms ; les valeurs sont paramétrées. Noter enabled ? 1 : 0 : SQLite n'a pas de booléen, on stocke 0/1, et l'opérateur ternaire convertit le booléen JS.

JS Valeurs par défaut dans le destructuring

Dans POST / : const { text, max_duration = 60, countdown = 3 } = req.body;. Si le corps ne contient pas max_duration, la variable prend 60. C'est l'équivalent d'un argument par défaut Python (def f(max_duration=60)), mais appliqué à l'extraction d'un objet. Pratique pour fournir des valeurs sensées sans if supplémentaires.
