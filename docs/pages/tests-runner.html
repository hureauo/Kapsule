6 — Tests

node:test & supertest

Le projet teste chaque route avec un cas nominal et au moins un cas d'erreur. Deux choix structurants : le test runner natif de Node (pas de Jest/Mocha) et supertest pour attaquer les serveurs en mémoire sans les démarrer. On prend ici apps/hub/server/test/auth.test.js comme exemple représentatif.

L'ossature d'un fichier de test

import { describe, it, before, after } from 'node:test';
import assert from 'node:assert/strict';
import { mkdtempSync, rmSync } from 'node:fs';
import { tmpdir } from 'node:os';
import { join } from 'node:path';
import supertest from 'supertest';
import { createApp } from '../src/index.js';
import { getDb, closeRegistry, insertUser } from '../src/registry.js';

let dir, app, request;

before(async () => {
  dir = mkdtempSync(join(tmpdir(), 'kapsule-hub-auth-'));   // dossier temporaire unique
  app = createApp(dir);                                     // app construite, PAS démarrée
  request = supertest(app);
  // … seed de données de test (insertUser…) …
});

after(() => {
  closeRegistry();
  rmSync(dir, { recursive: true, force: true });            // nettoyage total
});
JS node:test — le runner intégré

Depuis Node 18+, un framework de test est intégré au runtime (node:test) — plus besoin d'installer Jest ou Mocha. Il fournit les primitives classiques :

  • describe(nom, fn) — groupe de tests.
  • it(nom, fn) — un test individuel (« il fait ceci »).
  • before / after — exécutés avant/après le groupe (setup/teardown).

Les assertions viennent de node:assert/strict (lui aussi intégré) : assert.equal(a, b) (égalité stricte), assert.ok(x) (truthy). La variante /strict utilise === par défaut.

JS supertest — tester un serveur sans l'écouter

supertest(app) prend une app Express et permet de lui envoyer des requêtes sans ouvrir de port : il branche directement sur l'app en mémoire. On écrit await request.post('/api/auth/login').send({...}) et on inspecte res.status / res.body. C'est ici que prend tout son sens le « main module guard » de index.js : comme createApp est exporté sans .listen(), le test obtient l'app pure et supertest l'attaque en mémoire — rapide, sans conflit de port, parallélisable. 

it('retourne un token JWT pour des identifiants valides', async () => {
  const res = await request.post('/api/auth/login')
    .send({ email: 'alice@test.com', password: 'password-alice' });
  assert.equal(res.status, 200);
  assert.ok(res.body.token);
});

⛔ Règle du projet : les tests ne dépendent JAMAIS de Docker

Chaque suite crée un DATA_DIR temporaire avec mkdtempSync(join(tmpdir(), 'kapsule-…')), y instancie le serveur via createApp(dir), et le supprime en after avec rmSync(dir, { recursive: true, force: true }). Les serveurs s'instancient donc en mémoire de test, avec une base SQLite jetable — aucun conteneur, aucun port, aucun état partagé entre suites. C'est ce qui rend les tests rapides et reproductibles. (Le runner lui-même tourne dans le conteneur dev, parce que Node n'est pas en local — mais le code testé ne dépend pas de Docker.)

JS mkdtempSync + tmpdir — isolation par dossier jetable

mkdtempSync(prefix) crée un dossier temporaire au nom unique (suffixe aléatoire), tmpdir() renvoie le dossier temp du système (/tmp). Chaque suite a ainsi son propre DATA_DIR isolé — deux suites ne se marchent pas dessus, même lancées en parallèle. Le rmSync(..., { force: true }) nettoie tout à la fin. C'est le pattern d'isolation par filesystem, simple et fiable pour des tests qui touchent à des fichiers (ce qui est le cas ici : SQLite, vidéos).

Tester un invariant de sécurité : le jeton alg:none

it('retourne 401 pour un token alg:none (§S5.1/L1)', async () => {
  const header = Buffer.from(JSON.stringify({ alg: 'none', typ: 'JWT' })).toString('base64url');
  const payload = Buffer.from(JSON.stringify({ sub: 1, role: 'client', iat: ... })).toString('base64url');
  const noneToken = `${header}.${payload}.`;            // signature vide
  const res = await request.get('/api/events').set('Authorization', `Bearer ${noneToken}`);
  assert.equal(res.status, 401);
});

Ce test forge à la main un JWT malveillant alg:none (sans signature) et vérifie que le serveur le rejette (401) — c'est la preuve que l'épinglage algorithms: ['HS256'] de requireUser fonctionne. Tester explicitement les attaques connues est une bonne pratique : l'invariant de sécurité est vérifié, pas seulement supposé. On construit le jeton en encodant header et payload en base64url via Buffer (les briques d'un JWT).

JS Muter la config ESM partagée dans un test

Certains tests font config.allowRegister = true avant une assertion, puis le remettent à false. C'est possible parce que config est un objet partagé exporté par le module (un « live binding » ESM — voir ESM et config.js). Ça permet de tester un comportement dépendant de la config sans relancer le serveur. À manier avec soin (effet de bord global), d'où la remise à l'état initial juste après.

ℹ Couverture : un cas nominal + un cas d'erreur par route

La règle de CLAUDE.md : « un endpoint n'est terminé que testé ». Chaque route a au minimum un test du chemin heureux (200/201) et un test d'échec (400/401/403/ 404/409). Les tests d'auth couvrent en plus le cloisonnement (Alice ne voit pas les événements de Bob → 403) et les attaques (alg:none). Le worker, lui, est testé avec des handlers factices injectés via _setHandlers (voir worker) pour ne pas dépendre de ffmpeg.
