JS better-sqlite3 — SQLite synchrone

better-sqlite3 est un binding Node vers SQLite. Sa particularité : son API est synchrone. db.prepare('…').get() renvoie la ligne immédiatement, sans await, sans callback. C'est inhabituel en Node (où presque tout est asynchrone) et c'est voulu.

L'API en 5 méthodes

  • new Database(path) — ouvre (ou crée) le fichier .sqlite.
  • db.pragma('…') — exécute un PRAGMA SQLite (réglage de la base).
  • db.exec('…') — exécute du SQL brut (plusieurs instructions, sans paramètres ni résultat). Idéal pour les CREATE TABLE.
  • db.prepare('… ?') — prépare une requête paramétrée et renvoie un statement réutilisable. On l'exécute ensuite avec :
    • .run(args) — pour INSERT/UPDATE/DELETE → renvoie { changes, lastInsertRowid }.
    • .get(args) — pour un SELECT d'une ligne → renvoie l'objet ligne (ou undefined).
    • .all(args) — pour un SELECT de plusieurs lignes → renvoie un tableau d'objets.
  • db.transaction(fn) — emballe une fonction dans une transaction atomique (voir plus bas).

Le piège : les paramètres se passent avec ?

On n'interpole jamais une valeur dans la chaîne SQL (risque d'injection). On met des ? et on passe les valeurs à .run()/.get() : 

// BIEN — paramètre lié
db.prepare('SELECT * FROM users WHERE email = ?').get(email);
// MAL  — injection SQL possible
db.prepare(`SELECT * FROM users WHERE email = '${email}'`).get();

Pourquoi une API synchrone est-elle acceptable en Node ? Node est mono-thread avec une boucle d'événements : tout appel bloquant gèle le serveur le temps de l'opération. C'est pour ça que les I/O réseau/fichiers sont normalement async. Mais SQLite via better-sqlite3 lit un fichier local, en mémoire ou sur disque rapide : une requête typique prend quelques microsecondes. Le « blocage » est si court qu'il est inférieur à l'overhead d'une bascule asynchrone. L'auteur de la lib a mesuré que le synchrone est en pratique plus rapide que les wrappers async, tout en simplifiant énormément le code (pas de await sur chaque requête, transactions réellement atomiques). On revient sur ce choix dans Décisions.

Statement préparé = compilé une fois. db.prepare() compile le SQL en bytecode SQLite. Si tu exécutes la même requête en boucle, prépare-la une fois hors de la boucle et réutilise le statement — c'est ce que fait le code partout (ex. upsertState dans le push). Réutiliser un statement est l'optimisation SQLite la plus courante.

Lecture de createEventDb

Ouverture + PRAGMA

import Database from 'better-sqlite3';

export function createEventDb(filePath) {
  const db = new Database(filePath);

  // journal_mode=WAL est persistant (stocké dans le fichier) ;
  // foreign_keys est par-connexion → à re-poser à chaque new Database()
  db.pragma('journal_mode = WAL');
  db.pragma('foreign_keys = ON');
  // …
JS WAL et foreign_keys — deux PRAGMA, deux portées

WAL (Write-Ahead Logging) est un mode de journalisation SQLite. Au lieu d'écrire directement dans le fichier principal et de journaliser l'ancien état, SQLite écrit les modifications dans un fichier annexe db.sqlite-wal puis les « rejoue » dans le fichier principal lors d'un checkpoint. Avantage : un lecteur et un écrivain peuvent travailler en même temps (le lecteur voit l'état d'avant, l'écrivain ajoute au WAL). C'est précieux ici : le serveur HTTP lit/écrit pendant que le worker ou le push lisent la même base.

Le commentaire du code pointe une asymétrie cruciale :

  • journal_mode = WAL est persistant : une fois posé, il est stocké dans le fichier. Toute connexion ultérieure hérite du mode.
  • foreign_keys = ON est par connexion : SQLite désactive les clés étrangères par défaut, et ce réglage doit être reposé à chaque new Database(). C'est pourquoi tous les fichiers qui ouvrent une base (registry du Hub, de la Borne…) répètent ces deux lignes.

Le WAL crée deux fichiers compagnons : -wal (le journal) et -shm (mémoire partagée d'index). Ils doivent voyager avec le .sqlite ou être « checkpointés » avant transfert. C'est exactement l'objet de l'invariant §11.8 : avant de calculer le checksum d'une base ou de l'envoyer, on force wal_checkpoint(TRUNCATE) pour replier tout le WAL dans le fichier principal et vider le journal. Sinon le Hub recevrait un .sqlite incomplet (les dernières écritures restées dans le -wal). Voir sync/push.js et la suppression défensive des -wal/-shm dans hub/routes/sync.js.

Création des tables

Le schéma est créé en une seule chaîne SQL passée à db.exec(). On y trouve les cinq tables d'un événement : 

  db.exec(`
    CREATE TABLE IF NOT EXISTS event_meta ( key TEXT PRIMARY KEY, value TEXT );

    CREATE TABLE IF NOT EXISTS questions (
      id           INTEGER PRIMARY KEY AUTOINCREMENT,
      text         TEXT    NOT NULL,
      max_duration INTEGER NOT NULL DEFAULT ${DEFAULTS.MAX_DURATION_S},
      countdown    INTEGER NOT NULL DEFAULT ${DEFAULTS.COUNTDOWN_S},
      order_index  INTEGER NOT NULL DEFAULT 0,
      enabled      INTEGER NOT NULL DEFAULT 1,
      created_at   DATETIME DEFAULT CURRENT_TIMESTAMP,
      updated_at   DATETIME DEFAULT CURRENT_TIMESTAMP
    );

    CREATE TABLE IF NOT EXISTS sessions (
      id           TEXT PRIMARY KEY,
      guest_name   TEXT,
      consent_at   DATETIME NOT NULL,
      started_at   DATETIME DEFAULT CURRENT_TIMESTAMP,
      completed_at DATETIME
    );

    CREATE TABLE IF NOT EXISTS videos (
      id            TEXT PRIMARY KEY,
      session_id    TEXT    NOT NULL REFERENCES sessions(id) ON DELETE CASCADE,
      question_id   INTEGER REFERENCES questions(id) ON DELETE SET NULL,
      question_text TEXT    NOT NULL,
      filename      TEXT    NOT NULL UNIQUE,
      mime_type     TEXT    NOT NULL DEFAULT 'video/mp4',
      size          INTEGER, checksum TEXT,
      recorded_at   DATETIME DEFAULT CURRENT_TIMESTAMP,
      uploaded_at   DATETIME DEFAULT CURRENT_TIMESTAMP,
      UNIQUE(session_id, question_id)
    );

    CREATE TABLE IF NOT EXISTS derived (
      video_id   TEXT PRIMARY KEY REFERENCES videos(id) ON DELETE CASCADE,
      thumbnail  TEXT, duration_s REAL, width INTEGER, height INTEGER, probed_at DATETIME
    );
  `);

Quelques décisions de schéma à comprendre :

  • ${DEFAULTS.MAX_DURATION_S} dans le SQL : le schéma interpole une constante JS (constants.js) dans la chaîne SQL. Ici c'est sûr car ce sont nos propres constantes numériques, pas une saisie externe.
  • ON DELETE CASCADE (videos → sessions, derived → videos) : supprimer une session supprime ses vidéos, supprimer une vidéo supprime ses données dérivées. Nécessite foreign_keys = ON — d'où l'importance du PRAGMA.
  • ON DELETE SET NULL (videos → questions) : supprimer une question ne supprime pas les vidéos déjà enregistrées pour elle ; leur question_id passe à NULL (mais question_text garde une copie du libellé — d'où sa présence redondante).
  • UNIQUE(session_id, question_id) : un invité ne peut avoir qu'une vidéo par question. Ré-enregistrer remplace — c'est la base de la « transaction de remplacement » de videos.js (§11.9).

JS Les transactions better-sqlite3

db.transaction(fn) ne lance pas la transaction : il retourne une nouvelle fonction qui, quand on l'appelle, exécute fn entre un BEGIN et un COMMIT (et fait ROLLBACK si fn lève). D'où le motif en deux temps : const seedAll = db.transaction(() => {…}) puis seedAll().

Pourquoi une transaction pour le seed ? Pour l'atomicité et la vitesse : insérer 4 lignes hors transaction = 4 écritures disque ; en transaction = une seule. Et si une insertion échoue, aucune n'est conservée (pas de seed partiel).

.forEach((q, i) => …) itère sur un tableau ; le second argument i est l'index, réutilisé ici comme order_index. Équivalent de for i, q in enumerate(...) en Python.

Le pattern « transaction() retourne une fonction » paraît étrange mais il est puissant : la fonction transactionnelle est réutilisable et composable. better-sqlite3 fournit même des variantes (.deferred, .immediate, .exclusive) sur l'objet retourné. Surtout, comme tout est synchrone, la transaction est réellement atomique du point de vue du thread : aucune autre requête ne peut s'intercaler entre le BEGIN et le COMMIT, contrairement à un environnement async où un await au milieu d'une transaction peut laisser passer d'autres opérations. C'est un argument de plus pour le SQLite synchrone.

⛔ Qui ferme le handle ?

createEventDb ouvre mais ne ferme pas. La fermeture (db.close()) est gérée par les caches (eventStore / eventDb) ou explicitement avant un transfert/suppression de fichier. Oublier de fermer avant un rm -rf ou un écrasement du fichier corrompt la base (invariant §11.11). On y revient dans les pages des caches.
