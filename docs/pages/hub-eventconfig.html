3 — Le serveur Hub

hub/eventConfig.js — application de config partagée

Trois endroits du Hub écrivent la configuration d'un événement (questions + event_meta) dans sa db.sqlite : le PUT /:eventId (édition depuis l'UI client), l'import de config UI et la remontée de config poussée par la Borne (POST /events/:id/config de sync.js). Avant la phase 8R, la logique d'écriture — quelles clés meta accepter, comment se comportent les modes overwrite et merge, le clamp à 500 caractères — était dupliquée à l'identique dans chacun. Ce module la centralise : une seule fonction applyEventConfig et une seule liste META_KEYS font foi.

La source unique des clés meta

import { THEMES, TEXT_FIELDS } from '@kapsule/core';

// Clés event_meta gérées par applyEventConfig — source unique pour les routes config.
export const META_KEYS = ['theme', 'idle_timeout', ...Object.keys(TEXT_FIELDS)];

META_KEYS est la liste blanche des clés event_meta que le Hub accepte d'écrire : theme, idle_timeout, plus tous les textes éditables (TEXT_FIELDS). La dériver de TEXT_FIELDS (via Object.keys + spread) évite qu'une nouvelle clé de texte ajoutée dans le core soit oubliée ici. Elle est aussi réexportée vers admin.js, dont le configHash dérive son META_HASH_KEYS = META_KEYS : les clés hashées pour comparer deux configs sont donc exactement celles qu'on sait écrire — impossible de désynchroniser les deux listes.

La fonction applyEventConfig

export function applyEventConfig(edb, { mode, meta, questions }) {
  const upsert = edb.prepare(
    'INSERT INTO event_meta (key, value) VALUES (?, ?) ON CONFLICT(key) DO UPDATE SET value=excluded.value'
  );

  if (meta && typeof meta === 'object') {
    for (const key of META_KEYS) {                 // on n'itère QUE la liste blanche
      if (meta[key] === undefined) continue;
      if (mode === 'merge') {
        const existing = edb.prepare('SELECT value FROM event_meta WHERE key=?').get(key)?.value;
        if (existing && existing.trim() !== '') continue;   // merge : ne pas écraser une valeur déjà posée
      }
      if (key === 'theme' && !THEMES.includes(meta[key])) continue;  // thème inconnu → ignoré
      upsert.run(key, String(meta[key]));
    }
  }

  if (Array.isArray(questions)) {
    if (mode === 'overwrite') edb.prepare('DELETE FROM questions').run();   // overwrite : table vidée d'abord
    const existingTexts = new Set(edb.prepare('SELECT text FROM questions').all().map(q => q.text));
    const insert = edb.prepare(
      'INSERT INTO questions (text, max_duration, countdown, order_index, enabled) VALUES (?, ?, ?, ?, ?)'
    );
    const maxRow = edb.prepare('SELECT MAX(order_index) as m FROM questions').get();
    let nextOrder = (maxRow?.m ?? -1) + 1;
    for (const q of questions) {
      if (!q.text || typeof q.text !== 'string') continue;
      if (mode === 'merge' && existingTexts.has(q.text)) continue;   // merge : pas de doublon de texte
      insert.run(q.text.slice(0, 500), q.max_duration ?? 60, q.countdown ?? 3, nextOrder++, q.enabled !== undefined ? (q.enabled ? 1 : 0) : 1);
    }
  }
}

Les deux modes

  • overwrite : la source fait foi. Les questions sont vidées (DELETE FROM questions) puis réinsérées ; les event_meta connues présentes dans meta sont écrasées.
  • merge : on ne fait qu'ajouter. Une valeur de meta déjà non vide n'est pas touchée, et une question dont le texte existe déjà est ignorée (dédoublonnage par texte via un Set). Rien n'est effacé.
JS Une fonction qui reçoit le handle DB en paramètre

applyEventConfig ne sait pas quelle base elle écrit : l'edb (le handle better-sqlite3 déjà ouvert) lui est passé par l'appelant. C'est le même pattern que registry.js, où chaque fonction prend db en argument plutôt que d'ouvrir elle-même la base. Avantage : la fonction reste pure de tout effet d'ouverture/fermeture (c'est l'appelant qui gère le cache eventStore), donc testable en isolation avec une base temporaire — ce que font les tests unitaires eventConfig.test.js.

C'est de l'injection de dépendance minimaliste : au lieu d'un import global vers une base, on passe la ressource. En Python on parlerait d'une fonction prenant une connection en argument plutôt que d'utiliser un singleton de module. Cela découple la logique métier (overwrite/merge) de la gestion du cycle de vie du handle.

→ notion JS : better-sqlite3 prepare/run/get/all, ON CONFLICT, transaction (vue dans core/eventDbSchema.js)

API

ExportRôle
META_KEYSListe blanche des clés event_meta écrivables (theme, idle_timeout, TEXT_FIELDS). Source unique réutilisée par admin.js (META_HASH_KEYS) et le PUT /:eventId de events.js.
applyEventConfig(edb, { mode, meta, questions })Écrit meta + questions sur une event DB ouverte selon le mode overwrite ou merge. Thème invalide ignoré, texte de question tronqué à 500 caractères.

Ce qu'il ne fait pas

  • Il n'ouvre ni ne ferme la base : c'est l'appelant qui fournit l'edb (via openEventDb).
  • Il ne valide pas le mode ni le statut de l'événement (gel ≥ live) : ces gardes restent dans les routes appelantes (400 mode invalide, 409 statut figé), car elles dépendent du contexte HTTP.
  • Il ne trace rien dans sync_log : l'insertSyncLog('config_import') reste côté route.
ℹ Trois appelants, une seule logique

applyEventConfig est appelé par le PUT /:eventId et l'import UI de events.js (mode overwrite), et par la remontée POST /events/:id/config de sync.js (overwrite ou merge, selon ce que pousse la Borne). Toute évolution du comportement de config se fait désormais ici, en un seul endroit.
