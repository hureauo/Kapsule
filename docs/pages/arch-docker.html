1 — Architecture

Docker & variables d'environnement

Tout Kapsule s'exécute dans Docker — il n'y a aucune dépendance Node installée sur la machine de dev. Il y a trois fichiers compose, chacun pour un usage précis. Le code ne « connaît » pas Docker : il lit sa configuration depuis des variables d'environnement que Docker lui injecte.

Les trois fichiers compose

FichierUsage
docker-compose.ymlDéveloppement : un service dev (node:20-alpine) qui lance les tests. C'est lui qu'on utilise pour npm test.
docker-compose.hub.ymlDéploiement du Hub : backend + worker + frontend.
docker-compose.borne.ymlDéploiement de la Borne : backend + frontend.

Le service de dev

services:
  dev:
    image: node:20-alpine
    working_dir: /app
    volumes:
      - .:/app                          // le code du repo monté dans le conteneur
    environment:
      - NODE_ENV=development
    // better-sqlite3 est natif → besoin de python3/make/g++ pour compiler à l'install
    entrypoint: sh -c "apk add --no-cache python3 make g++ && \"$$@\"" --
    command: ["npm", "test"]

Le point notable : better-sqlite3 est un module natif (du C++ compilé). Son installation exige une chaîne de compilation, d'où le apk add python3 make g++ avant toute commande. C'est aussi pour ça que les commandes Docker du projet prennent un moment au premier lancement.

ℹ Les commandes de dev passent toujours par Docker

Exemples tirés de CLAUDE.md : 

docker compose run --rm dev npm test                 # tous les tests
docker compose run --rm dev npm test -w @kapsule/core # un seul workspace
docker compose up dev:borne                           # serveur Borne en dev

Le -w @kapsule/core est le raccourci de --workspace (voir Monorepo).

Le Hub : trois conteneurs, une image

Dans docker-compose.hub.yml, backend et worker utilisent la même image (même Dockerfile) mais des commandes différentes : 

backend:
  build: { context: ., dockerfile: apps/hub/server/Dockerfile }
  // (commande par défaut du Dockerfile : node src/index.js)

worker:
  build: { context: ., dockerfile: apps/hub/server/Dockerfile }
  command: ["node", "src/worker/index.js"]   // même image, autre point d'entrée
  depends_on: [backend]

C'est élégant : le serveur HTTP et le worker partagent tout le code et les dépendances (dont ffmpeg installé dans le Dockerfile), seul leur process d'entrée change. Les deux montent le même volume hub_data sur /app/data — ils voient donc les mêmes bases et les mêmes fichiers vidéo, ce qui permet au worker de traiter ce que le backend a reçu.

Les variables d'environnement

Docker passe la config au code via le bloc environment. Côté Hub : 

environment:
  - JWT_SECRET=${JWT_SECRET:-change-me}    // ${VAR:-defaut} = valeur de l'hôte ou défaut
  - DATA_DIR=/app/data
  - PORT=3001
  - ALLOW_REGISTER=${ALLOW_REGISTER:-false}

Côté Borne, il y a en plus les paramètres de synchronisation :

- ADMIN_PASSWORD=${ADMIN_PASSWORD:-admin123}
- HUB_URL=${HUB_URL:-}            // vide = mode autonome, sans Hub
- BOX_TOKEN=${BOX_TOKEN:-}        // jeton d'identification auprès du Hub
- PULL_INTERVAL_MS=${PULL_INTERVAL_MS:-300000}   // 5 min
JS process.env — lire l'environnement en Node

Node expose les variables d'environnement dans l'objet global process.env. Chaque valeur est une chaîne (ou undefined si absente) — il faut convertir soi-même les nombres et booléens. C'est l'équivalent de os.environ en Python ou os.Getenv en Go.

LangageLire une variable
Pythonos.environ.get("PORT", "3001")
Goos.Getenv("PORT")
JSprocess.env.PORT ?? "3001"

C'est exactement ce que fait hub/config.js :

const env = process.env;
export const config = {
  port: parseInt(env.PORT ?? '3001', 10),   // chaîne → entier (base 10)
  jwtSecret: env.JWT_SECRET ?? 'change-me',
  dataDir: env.DATA_DIR ?? '/app/data',
  allowRegister: env.ALLOW_REGISTER === 'true',  // chaîne → booléen explicite
};

L'opérateur ?? (nullish coalescing)

a ?? b renvoie a sauf si a est null ou undefined, auquel cas b. C'est plus sûr que le || classique pour des valeurs par défaut.

Pourquoi ?? et pas || ? Le || se déclenche sur toute valeur « falsy » : 0, "", false, NaN… Donc parseInt(env.PORT) || 3001 donnerait 3001 si PORT valait "0" — rarement voulu. Avec ??, seuls null/undefined déclenchent le défaut : 0 et "" sont conservés. Ici, sur env.PORT ?? '3001', ça garantit qu'une variable explicitement vide n'est pas silencieusement écrasée.

Le second argument de parseInt(x, 10) est la base. On le met toujours à 10 : sans lui, une chaîne comme "0x10" serait interprétée en hexadécimal. Habitude défensive standard en JS.

Le Dockerfile (exemple Borne)

FROM node:20-alpine
RUN apk add --no-cache python3 make g++       // pour compiler better-sqlite3

WORKDIR /app
// On copie d'abord les manifestes seuls → la couche "npm ci" est cachée
// tant que les dépendances ne changent pas (optimisation du cache Docker)
COPY package.json package-lock.json ./
COPY packages/core/package.json ./packages/core/
COPY apps/borne/server/package.json ./apps/borne/server/
RUN npm ci --omit=dev                          // install reproductible, sans devDependencies

COPY packages/core/src ./packages/core/src     // ensuite seulement, le code
COPY apps/borne/server/src ./apps/borne/server/src

WORKDIR /app/apps/borne/server
CMD ["node", "src/index.js"]

Le pattern « copier les package.json avant le code source » est une optimisation classique : Docker met en cache chaque couche, et tant que les manifestes ne changent pas, l'étape npm ci (longue) n'est pas rejouée même si tu modifies du code. npm ci installe exactement ce qui est figé dans le lockfile (« clean install »), et --omit=dev ignore les devDependencies (pas de supertest en prod).
