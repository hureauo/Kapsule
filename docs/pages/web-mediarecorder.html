borne/web useMediaRecorder

Le hook React qui pilote l'enregistrement vidéo dans le kiosque : accès caméra, capture, chrono, auto-stop, génération du blob à uploader. C'est la page la plus dense en notions React et la meilleure pour comprendre les closures et la différence useRef vs useState — un point qui piège tous ceux qui arrivent à React.

JS React et les « hooks » en deux minutes

React construit l'interface à partir de composants : des fonctions qui décrivent ce qu'il faut afficher. Quand une donnée change, React ré-exécute la fonction du composant pour recalculer l'affichage (« re-render »). Les hooks (fonctions useXxx) permettent à ces fonctions d'avoir de la mémoire et des effets :

  • useState(v) → un état qui, quand on le change, déclenche un re-render. Renvoie [valeur, setValeur].
  • useRef(v) → une « boîte » mutable qui persiste entre les renders mais ne déclenche pas de re-render. On lit/écrit ref.current.
  • useCallback(fn, deps) → mémorise une fonction (stabilité de référence entre renders).
  • useEffect(fn, deps) → exécute un effet de bord après le render ; peut retourner une fonction de nettoyage.

Un hook custom (comme useMediaRecorder) est juste une fonction qui combine ces hooks de base pour offrir une fonctionnalité réutilisable. Il retourne ici un objet { status, blob, startRecording, … } que le composant utilise.

État affiché vs références internes

const [status, setStatus] = useState(REC_STATUS.IDLE);   // affiché → re-render à chaque changement
const [duration, setDuration] = useState(0);             // affiché (le chrono à l'écran)
const [blob, setBlob] = useState(null);

const streamRef   = useRef(null);   // MediaStream (caméra) — pas affiché
const recorderRef = useRef(null);   // MediaRecorder — pas affiché
const chunksRef   = useRef([]);     // morceaux vidéo collectés — pas affiché
const timerRef    = useRef(null);   // id du setInterval — pas affiché
const durationRef = useRef(0);      // COPIE de duration pour le callback du timer (closure)
JS useRef vs useState : le critère de choix

La règle : est-ce que l'affichage dépend de cette valeur ?

  • Oui → useState (changer la valeur doit redessiner l'UI). Ici : status (afficher « enregistrement… »), duration (le chrono), blob (afficher l'aperçu).
  • Non (donnée technique interne) → useRef. Ici : le MediaStream, le MediaRecorder, l'id du timer, les chunks. Les mettre dans un state provoquerait des re-renders inutiles (voire des bugs).

Différence cruciale de comportement : une variable useState est figée à la valeur du render courant (chaque render « voit » sa propre version). Une ref.current est toujours la valeur la plus récente, partagée entre tous les renders. Cette distinction est au cœur du piège ci-dessous.

Le piège des closures : pourquoi durationRef existe

recorder.start(1000);                         // chunks de 1 s (robustesse si crash)
timerRef.current = setInterval(() => {
  durationRef.current += 1;                    // on incrémente la REF (toujours à jour)
  setDuration(durationRef.current);            // on met aussi à jour le STATE (pour l'affichage)
  if (durationRef.current >= maxDuration) {     // auto-stop quand la durée max est atteinte
    clearInterval(timerRef.current); timerRef.current = null;
    if (recorderRef.current?.state !== 'inactive') recorderRef.current.stop();
  }
}, 1000);
⛔ Le piège classique : une closure capture une valeur figée

Le callback de setInterval est créé une fois, au lancement de l'enregistrement. Par le mécanisme de closure, il capture les variables visibles à ce moment-là. S'il lisait la variable d'état duration, il verrait éternellement 0 — la valeur du render où il a été créé — car chaque re-render produit une nouvelle variable duration que l'ancien callback ne voit pas. Le chrono ne s'arrêterait jamais (la condition duration >= maxDuration resterait fausse).

La solution : durationRef. Une ref n'est pas « recréée » à chaque render ; durationRef.current est une boîte unique, toujours à jour. Le callback lit durationRef.current et voit donc la vraie valeur courante. On met aussi à jour le state setDuration en parallèle, uniquement pour rafraîchir l'affichage. C'est le pattern « ref pour la logique, state pour l'affichage » — indispensable dans tout callback à longue durée de vie (timer, abonnement) qui doit lire une valeur évolutive.

JS Les closures, en général

Une closure est une fonction qui « capture » les variables de son environnement de définition et continue d'y accéder même après. C'est un mécanisme JS fondamental (on l'a déjà croisé avec les factories à closure de config dans borne/middleware/auth.js, et validateUuidParams). En React, les closures sont partout — chaque callback dans un composant capture les variables du render où il est créé. Bien le comprendre évite la majorité des bugs « ma valeur ne se met pas à jour ».

La détection du codec : Safari n'accepte que mp4

const MIME_CANDIDATES = [
  'video/mp4;codecs=avc1,mp4a.40.2',  // Safari iOS — codec explicite
  'video/mp4',                         // Safari fallback
  'video/webm;codecs=vp9,opus',        // Chrome/Firefox préféré
  // …
];
function detectMimeType() {
  if (typeof MediaRecorder === 'undefined') return 'video/mp4';
  for (const mime of MIME_CANDIDATES) {
    if (MediaRecorder.isTypeSupported(mime)) return mime;   // premier supporté gagne
  }
  return 'video/mp4';
}
⛔ Invariant Safari : choisir un codec que MediaRecorder supporte

MediaRecorder (l'API navigateur d'enregistrement) ne supporte pas les mêmes formats partout : Safari/iOS n'enregistre qu'en mp4 (codec AVC/AAC), pas en webm ; Chrome/Firefox préfèrent webm. MediaRecorder.isTypeSupported(mime) teste à la volée ce que le navigateur sait faire ; on prend le premier candidat supporté, en mettant mp4 d'abord pour l'iPad (la cible). Choisir un format non supporté ferait échouer l'enregistrement silencieusement. C'est pourquoi l'ordre de la liste compte.

Gestion mémoire : les object URLs

recorder.onstop = () => {
  const recorded = new Blob(chunksRef.current, { type: mimeType });
  const url = URL.createObjectURL(recorded);   // crée une URL blob:… pour l'aperçu <video>
  setBlob(recorded);
  setBlobUrl(url);
  setStatus(REC_STATUS.STOPPED);               // STOPPED ici → garantit blob disponible
};

const revokeBlobUrl = useCallback(() => {
  setBlobUrl((prev) => { if (prev) URL.revokeObjectURL(prev); return null; });  // libère la mémoire
}, []);
JS URL.createObjectURL / revokeObjectURL

Pour afficher la vidéo enregistrée dans un <video>, on a besoin d'une URL. URL.createObjectURL(blob) crée une URL locale blob:… qui pointe vers le blob en mémoire. Piège : ces URLs gardent le blob en mémoire tant qu'on ne les révoque pas explicitement avec URL.revokeObjectURL(url). Oublier de révoquer = fuite mémoire (les vidéos s'accumulent en RAM). Le hook révoque systématiquement l'ancienne URL avant d'en créer une nouvelle, et au nettoyage.

⚠ onstop est asynchrone par rapport à .stop()

Subtilité : recorder.stop() ne produit pas le blob immédiatement — l'événement onstop arrive un peu après, une fois les derniers chunks rassemblés. C'est pourquoi le passage au statut STOPPED est fait dans onstop (pas juste après .stop()) : on garantit ainsi que blob et blobUrl sont disponibles au moment où le statut change, donc l'aperçu s'affiche correctement. Le code neutralise aussi onstop avant un .stop() de nettoyage, pour éviter qu'un handler tardif ne « ressuscite » un blob après le démontage (autre source de fuite).

Nettoyage au démontage

// Démontage du composant parent → libère TOUJOURS la caméra
useEffect(() => () => { cleanup(); }, [cleanup]);

useEffect avec une fonction de retour : cette fonction est appelée quand le composant est démonté (retiré de l'écran). Ici elle appelle cleanup() qui arrête le MediaRecorder, coupe la caméra (track.stop()), efface le timer et révoque l'URL. Sans ce nettoyage, la caméra resterait allumée (LED active) après avoir quitté l'écran d'enregistrement — fuite de ressource visible et gênante. C'est le rôle « destructeur » de useEffect.

ℹ Le attachPreview et les invariants Safari

attachPreview(videoEl) branche le flux caméra sur un <video> pour l'aperçu en direct, en posant muted, autoplay et surtout playsInline — indispensable sur iOS, sinon Safari force la vidéo en plein écran. C'est un des invariants Safari de PROJET.md §11 : tous les <video> doivent avoir playsInline. Safari peut aussi exiger un play() explicite, d'où le videoEl.play().catch(() => {}).
