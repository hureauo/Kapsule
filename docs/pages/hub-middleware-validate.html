3 — Le serveur Hub

hub/middleware/validateParams.js

Plusieurs routes du Hub prennent un identifiant d'événement ou de vidéo dans l'URL, puis l'utilisent pour construire un chemin de fichier (events/<id>/…). Si on ne valide pas cet identifiant, un attaquant peut y glisser .. et sortir du répertoire de données. Ce middleware impose que chaque paramètre soit un UUID v4 strict avant tout accès disque.

Le fichier (commentaires d'origine inclus, ils sont excellents) :

// Validation des paramètres d'URL qui finissent dans un chemin de fichier.
//
// Pourquoi : Express n'autorise pas '/' dans un segment :param, mais laisse passer
// '..' (ou son encodage %2e%2e). Sans contrôle, un :id/:videoId valant '..' permet à
// path.join(dataDir, 'events', id, …) de SORTIR du répertoire de données → écriture/lecture
// de fichier arbitraire (audit SECURITY.md H1).

const UUID_V4 = /^[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$/i;

export function validateUuidParams(...names) {
  return function (req, res, next) {
    for (const name of names) {
      const value = req.params[name];
      if (!value || !UUID_V4.test(value)) {
        return res.status(400).json({ error: `Paramètre ${name} invalide` });
      }
    }
    next();
  };
}
⛔ Path traversal (audit SECURITY.md H1)

Le danger concret : une requête vers /api/sync/events/..%2f..%2fetc/files/x pourrait, sans garde, faire écrire multer dans /etc ou lire un fichier hors du dossier de données. La parade est de n'autoriser que des UUID v4 : un UUID ne contient ni / ni ., donc aucun chemin malveillant ne peut passer. Et surtout, la validation a lieu avant que multer ne calcule sa destination — aucun octet n'est écrit sur disque tant que l'UUID n'est pas validé.

JS RegExp littérale et .test()

/^[0-9a-f]{8}-…$/i est une expression régulière littérale : en JS, on l'écrit entre slashes (pas entre guillemets), avec des drapeaux après le slash final — ici i pour « insensible à la casse ». regex.test(chaine) renvoie true/false selon que la chaîne correspond.

Décodage du motif UUID v4 : 8 hex, tiret, 4 hex, tiret, 4 + 3 hex (le 4 impose la version 4), tiret, un caractère parmi 8/9/a/b + 3 hex (le « variant »), tiret, 12 hex. Les ancres ^ et $ forcent la correspondance sur toute la chaîne (sinon un préfixe valide suivi de ../ passerait).

La regex littérale est compilée une fois au chargement du module (elle est au niveau fichier, pas dans la fonction). C'est l'équivalent d'un regexp.MustCompile hissé hors de la boucle en Go. La recréer à chaque appel serait du gaspillage. Petit piège à connaître : si on ajoutait le drapeau g (global), .test() deviendrait stateful (il mémorise lastIndex entre appels) et donnerait des résultats alternés — à éviter pour de la validation. Ici pas de g, donc .test() est sans état.

JS Une factory de middleware + les rest params ...names

validateUuidParams n'est pas un middleware : c'est une fonction qui retourne un middleware. On l'appelle avec les noms de paramètres à valider, elle renvoie la fonction (req, res, next) adaptée : 

// dans routes/sync.js
router.put('/events/:id/files/:videoId',
  validateUuidParams('id', 'videoId'),    // ← valide DEUX params
  uploadVideo.single('file'),
  handler);

...names est un rest parameter : il collecte tous les arguments dans un tableau names = ['id', 'videoId']. C'est l'inverse du spread ... (qui étale) ; ici il rassemble. Équivalent de *args en Python ou names ...string en Go.

Ce pattern « factory » est partout dans Express : il permet de configurer un middleware avant de le brancher. On l'a déjà vu avec les makeXxxRouter(dataDir) et on le reverra avec la config injectée côté Borne.

Pourquoi une factory plutôt qu'un middleware qui lirait une liste fixe ? Parce que les paramètres à valider varient selon la route : certaines n'ont que :id, d'autres :id + :videoId. La factory capture ces noms dans une closure (le middleware retourné « se souvient » de names). La closure est le mécanisme JS qui rend ce pattern possible — on l'explore en détail dans useMediaRecorder.
