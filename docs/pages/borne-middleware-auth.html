4 — Le serveur Borne

borne/middleware/auth.js

L'authentification de la Borne diffère de celle du Hub : pas de table d'utilisateurs, juste deux mots de passe statiques qui distinguent deux rôles — client et technicien (§11.19). Ce fichier contient le handler de login et deux middlewares de garde : requireAdmin (client OU tech) et requireTech (tech seul). Deux notions à connaître ici : la comparaison à temps constant (timingSafeEqual) et le pattern factory à closure de config.

Login : comparer un mot de passe sans fuite temporelle

import jwt from 'jsonwebtoken';
import { timingSafeEqual } from 'node:crypto';

function safeCompare(a, b) {
  const ba = Buffer.from(String(a));
  const bb = Buffer.from(String(b));
  if (ba.length !== bb.length) return false;       // longueurs différentes → pas égal
  return timingSafeEqual(ba, bb);
}

// Compare les DEUX mots de passe (toujours évalués, sans court-circuit) puis signe
// 'client' ou 'tech' selon celui qui correspond.
export function makeAuthRouter(config) {
  return async function loginHandler(req, res, next) {
    try {
      const { password } = req.body;
      if (!password) return res.status(401).json({ error: 'Mot de passe incorrect' });
      const isClient = safeCompare(password, config.adminPassword);
      const isTech   = safeCompare(password, config.techPassword);
      if (!isClient && !isTech) {
        return res.status(401).json({ error: 'Mot de passe incorrect' });
      }
      const role = isClient ? 'client' : 'tech';
      const token = jwt.sign({ role }, config.jwtSecret, { expiresIn: '24h' });
      res.json({ token });
    } catch (err) { next(err); }
  };
}
ℹ Un seul endpoint de login, le mot de passe décide du rôle

POST /api/admin/login est partagé par les deux espaces (/admin et /admin/tech). Le formulaire n'envoie que le mot de passe ; le serveur le compare aux deux secrets et signe le rôle correspondant dans le JWT. Les deux comparaisons sont faites à chaque login (pas de || qui court-circuiterait après la première réussie) : le temps de réponse ne dépend donc pas du rôle saisi — même logique anti-timing que safeCompare lui-même. C'est ensuite le composant front qui range le jeton dans la bonne clé localStorage (admin_token ou tech_token) ; voir borne/web client.js.

JS timingSafeEqual — comparaison à temps constant

Comparer deux chaînes avec === s'arrête au premier caractère différent. Le temps de comparaison dépend donc du nombre de caractères corrects au début — une fuite minuscule, mais qu'un attaquant peut exploiter pour deviner un secret caractère par caractère (attaque par timing). timingSafeEqual (de node:crypto) compare tous les octets quel que soit le résultat : le temps ne révèle rien sur le contenu.

Il opère sur des Buffer (octets bruts), d'où la conversion Buffer.from(String(...)). Subtilité : timingSafeEqual exige des Buffers de même longueur (il lève sinon) — on teste donc d'abord ba.length !== bb.length. Ce test-là fuit la longueur, mais la longueur d'un mot de passe est une information négligeable comparée à son contenu.

Pourquoi le String(...) et pas Buffer.from(a) tout court ? Parce que a vient de req.body.password, et le corps est du JSON arbitraire : un client peut très bien envoyer {"password": 1234}, true ou même un objet. Or Buffer.from attend une chaîne (ou des octets) — appelé sur un nombre ou un booléen, il lève un TypeError. Le String() est une conversion défensive : il garantit une entrée toujours valide pour Buffer.from et, au passage, une longueur cohérente pour la comparaison (un nombre devient sa représentation textuelle plutôt que de faire planter le handler).

⛔ §S5.2 : pourquoi c'est important ici

Le Hub compare les mots de passe via argon2.verify, qui est déjà résistant au timing. Mais la Borne compare ses mots de passe en clair (config.adminPassword et config.techPassword) directement — sans hachage. Sans timingSafeEqual, elle serait vulnérable à une attaque par timing sur ces secrets statiques. C'est l'ajout de la phase S5.2 visible dans l'historique git ; les deux comparaisons étant faites à chaque login (§11.19), le temps de réponse ne révèle pas non plus quel rôle correspond.

requireAdmin et requireTech : deux gardes, un extracteur de jeton

L'extraction du jeton (header Bearer ou ?token=, §11.2) est factorisée dans un helper extractToken, partagé par les deux middlewares : 

function extractToken(req) {
  const authHeader = req.headers['authorization'];
  return (
    (authHeader && authHeader.startsWith('Bearer ') ? authHeader.slice(7) : null) ??
    req.query.token ??
    null
  );
}

// requireAdmin : accepte 'client' OU 'tech' (le tech est un sur-ensemble du client, §11.19)
export function requireAdmin(config) {
  return function (req, res, next) {
    const token = extractToken(req);
    if (!token) return res.status(401).json({ error: 'Token manquant' });
    try {
      const payload = jwt.verify(token, config.jwtSecret, { algorithms: ['HS256'] });
      if (payload.role !== 'client' && payload.role !== 'tech') {
        return res.status(403).json({ error: 'Accès refusé' });
      }
      req.admin = payload;
      next();
    } catch {
      res.status(401).json({ error: 'Token invalide ou expiré' });
    }
  };
}

// requireTech : réservé au technicien (préflight, clôture, synchro) — §11.19
// Un token 'client' reçoit 403, pas 401.
export function requireTech(config) {
  return function (req, res, next) {
    const token = extractToken(req);
    if (!token) return res.status(401).json({ error: 'Token manquant' });
    try {
      const payload = jwt.verify(token, config.jwtSecret, { algorithms: ['HS256'] });
      if (payload.role !== 'tech') {
        return res.status(403).json({ error: 'Accès refusé' });
      }
      req.admin = payload;
      next();
    } catch {
      res.status(401).json({ error: 'Token invalide ou expiré' });
    }
  };
}

La logique JWT est identique au Hub : extraction header-ou-query (§11.2), vérification avec algorithms: ['HS256'] épinglé (§S5.1). La nuance des codes d'erreur est importante : un jeton valide mais du mauvais rôle reçoit 403 (« connu mais interdit »), alors qu'un jeton absent ou invalide reçoit 401. Un client qui tape une route tech voit donc 403, pas 401 — il est bien authentifié, mais pas autorisé.

→ notion JS : jsonwebtoken, algorithms pin, ?token= (vue dans hub/middleware/auth.js)
⛔ §11.19 : le contrôle d'accès est dans le middleware, pas dans l'UI

requireTech traduit l'invariant §11.19 : le technicien est un sur-ensemble du client (il peut tout faire), mais un jeton client doit recevoir 403 sur le préflight, la clôture et toute la synchro. Le contrôle se fait route par route côté serveur (voir events.js et sync.js) — jamais en se contentant de cacher l'onglet côté front. Cacher un bouton n'empêche pas un appel fetch direct avec un jeton client.

JS Factory à closure : requireAdmin(config) retourne le middleware

Différence d'architecture avec le Hub : là-bas, requireUser est directement un middleware qui import { config }. Ici, requireAdmin(config) est une factory : on lui passe la config, elle retourne le middleware. Le middleware retenu « se souvient » de config grâce à une closure (la fonction interne capture la variable de la fonction externe).

Pourquoi cette différence ? Pour la testabilité et l'injection de dépendances : on peut créer un requireAdmin avec une config de test (autre secret, autre mot de passe) sans toucher au module global. Le serveur assemble tout dans index.js : requireAdmin(cfg). C'est le même pattern de factory que validateUuidParams, appliqué à la config.

Une closure est une fonction qui capture des variables de son environnement de définition et les garde accessibles même après que la fonction externe a fini de s'exécuter. Ici, quand makeAuthRouter(config) a retourné, config « devrait » disparaître — mais le loginHandler retourné y fait référence, donc JS garde config en vie aussi longtemps que le handler existe. C'est le mécanisme central de beaucoup de patterns JS ; on l'explore en profondeur, avec un piège classique, dans useMediaRecorder.
