hub/worker/ffmpeg.js & les jobs

Les trois handlers de jobs (probe, thumbnail, archive) et le wrapper ffmpeg qu'ils partagent. C'est la page de référence pour lancer un sous-processus (child_process) et manipuler des Buffer, ainsi que pour la génération de ZIP avec archiver.

ffmpeg.js : exécuter une commande externe

import { spawn } from 'node:child_process';

function run(cmd, args) {
  return new Promise((resolve, reject) => {
    const proc = spawn(cmd, args);
    const out = [];
    const err = [];
    proc.stdout.on('data', (d) => out.push(d));        // collecte stdout par morceaux
    proc.stderr.on('data', (d) => err.push(d));
    proc.on('close', (code) => {
      if (code === 0) resolve(Buffer.concat(out).toString());
      else reject(new Error(`${cmd} exit ${code}: ${Buffer.concat(err).toString().slice(0, 300)}`));
    });
    proc.on('error', reject);                          // ex. binaire introuvable
  });
}
JS child_process.spawn — lancer un programme externe

spawn(cmd, args) lance un sous-processus (ici ffprobe ou ffmpeg, installés dans l'image Docker). Il retourne un objet processus dont stdout/stderr sont des streams : on s'abonne à leurs événements 'data' pour collecter la sortie, et à 'close' pour récupérer le code de retour. Code 0 = succès.

LangageÉquivalent
Pythonsubprocess.run([...], capture_output=True)
Goexec.Command(cmd, args...).Output()

On promisifie l'API événementielle (comme dans checksum.js) : la Promise résout avec la sortie sur 'close' code 0, et rejette sinon. Pourquoi spawn et pas exec ? spawn streame la sortie (pas de limite de buffer) et ne passe pas par un shell — donc pas de risque d'injection de commande via les arguments.

JS Les Buffer — données binaires brutes

Un Buffer est la représentation Node des octets bruts (Node n'utilise pas bytes comme Python). Les chunks émis par un stream sont des Buffers. Buffer.concat(out) recolle tous les morceaux en un seul Buffer, et .toString() le décode en texte (UTF-8 par défaut). On accumule dans un tableau out puis on concatène à la fin, plutôt que de concaténer à chaque chunk (plus efficace).

Les deux fonctions ffmpeg

export async function runFfprobe(filePath) {
  const json = await run('ffprobe', ['-v', 'quiet', '-print_format', 'json', '-show_streams', filePath]);
  const data = JSON.parse(json);
  const video = (data.streams ?? []).find((s) => s.codec_type === 'video') ?? {};
  const duration_s = parseFloat(video.duration ?? data.format?.duration ?? '0');
  return { duration_s, width: video.coded_width ?? video.width ?? 0, height: video.coded_height ?? video.height ?? 0 };
}

export async function makeThumbnail(inputPath, outputPath) {
  await run('ffmpeg', ['-y', '-ss', '1', '-i', inputPath, '-frames:v', '1', '-q:v', '2', outputPath]);
}

runFfprobe demande à ffprobe les métadonnées en JSON, puis extrait durée et dimensions. Le data.format?.duration utilise l'optional chaining ?. : si format est absent, l'expression vaut undefined au lieu de planter (≈ accès sécurisé). makeThumbnail extrait une image à t=1s (-ss 1, -frames:v 1) en JPEG qualité 2.

⚠ Ces fonctions nécessitent ffmpeg/ffprobe installés

Le wrapper suppose que ffmpeg et ffprobe sont dans le PATH — ils sont installés dans l'image Docker du Hub. C'est aussi pourquoi backend et worker partagent la même image (voir Docker). En test, les jobs sont remplacés par des handlers factices via _setHandlers pour ne pas dépendre de ffmpeg.

jobs/probe.js et jobs/thumbnail.js

export async function runProbe(job, dataDir) {
  const { event_id, video_id } = job;
  const edb = openEventDb(event_id, dataDir);
  const video = edb.prepare('SELECT filename FROM videos WHERE id = ?').get(video_id);
  if (!video) throw new Error(`Vidéo ${video_id} introuvable…`);

  const filePath = join(dataDir, 'events', event_id, 'videos', video.filename);
  const { duration_s, width, height } = await runFfprobe(filePath);

  edb.prepare(`INSERT INTO derived (video_id, duration_s, width, height, probed_at)
               VALUES (?, ?, ?, ?, CURRENT_TIMESTAMP)
               ON CONFLICT(video_id) DO UPDATE SET
                 duration_s = excluded.duration_s, width = excluded.width,
                 height = excluded.height, probed_at = excluded.probed_at`).run(video_id, duration_s, width, height);
}

Pattern commun aux deux : ouvrir la base de l'événement (openEventDb), lire le nom de fichier de la vidéo, lancer ffmpeg, écrire le résultat dans derived. Le UPSERT (INSERT … ON CONFLICT(video_id) DO UPDATE SET … = excluded.…) gère le re-traitement : si une ligne derived existe déjà pour cette vidéo, on la met à jour au lieu d'échouer. excluded est le mot-clé SQLite qui désigne « la valeur qu'on tentait d'insérer ». thumbnail.js est identique mais écrit le champ thumbnail et crée le dossier derived/ au passage.

jobs/archive.js : générer le ZIP en streaming

import archiver from 'archiver';

export async function runArchive(job, dataDir) {
  const { event_id } = job;
  const edb = openEventDb(event_id, dataDir);
  const videos = edb.prepare('SELECT id, filename FROM videos').all();
  const zipPath = join(dataDir, 'events', event_id, 'derived', 'archive.zip');

  await new Promise((resolve, reject) => {
    const output = createWriteStream(zipPath);
    const archive = archiver('zip', { store: true });    // store = pas de compression
    output.on('close', resolve);
    output.on('error', reject);
    archive.on('error', reject);
    archive.pipe(output);                                // archiver → fichier
    for (const video of videos) {
      const filePath = join(dataDir, 'events', event_id, 'videos', video.filename);
      archive.append(createReadStream(filePath), { name: video.filename });   // ajoute chaque vidéo
    }
    archive.finalize();                                  // clôt l'archive
  });
  // … met à jour events.updated_at …
}
JS archiver + pipeline de streams

archiver (paquet npm) construit un ZIP en streaming : il ne charge jamais toutes les vidéos en mémoire. On crée un flux d'écriture vers le fichier ZIP (createWriteStream), on pipe l'archiver dedans, on append chaque vidéo (elle-même lue en stream), puis finalize(). Le tout est enveloppé dans une Promise qui résout sur l'événement 'close' du fichier de sortie (= ZIP entièrement écrit).

Pourquoi { store: true } (§11.17) ? Le mode « store » désactive la compression. Les vidéos (mp4/webm) sont déjà compressées : tenter de les re-compresser dans le ZIP coûterait beaucoup de CPU pour un gain quasi nul (voire une taille légèrement supérieure). Le ZIP ne sert ici qu'à regrouper les fichiers en un seul téléchargement, pas à les réduire. C'est un réglage important pour les performances du worker.
