7 — Transversal

Flux complet : pull & push

Cette page relie tout le code de synchronisation vu séparément. Elle suit le cycle de vie complet d'un événement, de sa préparation sur le Hub jusqu'à la mise à disposition des vidéos après l'événement — en pointant à chaque étape le fichier qui l'implémente.

Vue d'ensemble du cycle de vie

Un événement traverse une suite de statuts. Qui déclenche quoi :

StatutOùDéclenché par
draftHubCréation de l'événement (POST /events).
readyHubLe client marque l'événement prêt (transition manuelle draft↔ready).
loadedHub + BorneLa Borne a tiré le bundle (GET /bundle passe ready→loaded).
liveBornePremier invité (POST /sessions) — local à la Borne.
closedBorne → HubClôture (PUT /close) ; remonté au Hub au début du push (POST /status, best-effort).
pushedHubPush finalisé (POST /finalize).
processedHubTous les jobs terminés (worker).
purgedHub et/ou BorneSuppression RGPD.

Phase A — Préparation (sur le Hub)

  1. L'admin crée un événement (draft) — la création est réservée à l'admin (events, requireAdmin) — puis l'assigne à un client (PUT /events/:id/owner, qui crée le compte client et son lien d'enregistrement si besoin). Le client édite ensuite « son » événement : questions, consentement (questions). Variante : il peut aussi peaufiner la config sur une borne d'essai et la remonter au Hub (POST /sync/push-config → POST /sync/events/:id/config).
  2. L'admin génère un token de borne pour cet événement (POST /admin/events/:id/tokens) → jeton en clair (aussi re-consultable, §11.13b), à configurer dans BOX_TOKEN sur la Borne. Le token désigne l'événement (modèle token = événement, §11.20) : il n'y a plus d'étape d'« assignation de borne » séparée.
  3. L'admin passe l'événement ready.

Phase B — Pull (Borne ← Hub, avant l'événement)

La Borne, quand elle a du réseau, tire l'événement :

  1. Le pull one-shot au démarrage (index.js) ou un pull manuel depuis l'espace technicien appelle pullMyEvent (il n'y a plus de pull périodique).
  2. pull.js demande l'unique événement de son token (GET /sync/event, 404 si rien à tirer), puis son bundle (GET /bundle) — ce qui passe l'événement ready→loaded côté Hub.
  3. La Borne écrit les questions + réglages dans son db.sqlite local — seulement si le statut local est encore loaded (invariant §11.10, vérifié au moment d'appliquer).

À ce stade, la Borne a tout pour fonctionner hors-ligne : le réseau peut disparaître, l'événement se déroulera quand même.

Phase C — L'événement (Borne, hors-ligne)

  1. L'opérateur active l'événement (PUT /activate) — il devient l'unique événement actif servi au kiosque.
  2. Premier invité : POST /sessions (consentement strict) fait passer l'événement loaded→live.
  3. Les invités enregistrent (capture) et uploadent (XHR avec progression → POST /videos, transaction de remplacement §11.9).
  4. Fin : l'opérateur clôture (PUT /close) → live→closed.
  5. Pendant l'événement, la Borne est typiquement hors-ligne : les statuts live/ closed restent locaux. Le Hub n'apprend la clôture qu'au moment du push, qui commence par signaler closed (POST /status, best-effort) avant d'envoyer le manifest.

Phase D — Push (Borne → Hub, après l'événement)

Quand la Borne retrouve le réseau, l'opérateur lance le push (POST /sync/push/:eventId, exige closed). push.js exécute la séquence ; côté Hub, sync.js reçoit :

  1. Checkpoint WAL + checksums (§11.8) : la Borne replie le WAL et calcule le SHA-256 de chaque vidéo + du db.sqlite.
  2. Manifest : la Borne annonce ses fichiers (POST /manifest) ; le Hub répond la liste missing (ce qu'il n'a pas encore reçu).
  3. Upload des vidéos manquantes (PUT /files/:videoId) : le Hub recalcule le checksum à la réception, 422 si corruption (la Borne réessaie avec backoff).
  4. Upload du db.sqlite (PUT /db) : remplacement atomique côté Hub, après fermeture du handle et nettoyage WAL/SHM (§11.11).
  5. Finalize (POST /finalize) : le Hub revérifie que tout est présent (§11.12), passe closed→pushed, et enfile les jobs de traitement.
💡 La reprise sur erreur, étape par étape

Supposons que le réseau coupe pendant l'upload de la 3ᵉ vidéo sur 10. Au relancement du push :

  • Étape 1-2 rejouées : le manifest est renvoyé.
  • Le Hub, qui a gardé les 2 premières vidéos (avec bon checksum), répond missing = les 8 restantes.
  • La Borne n'ré-uploade que ces 8 — les 2 déjà transférées sont sautées.
  • Finalize revérifie l'intégralité avant de basculer en pushed.

C'est la combinaison de l'invariant §11.12 (le Hub recalcule missing, ne fait pas confiance au push_state local) et du backoff §11.7. Le push est donc idempotent et reprenable — essentiel sur le Wi-Fi d'une salle d'événement.

Phase E — Traitement (Hub, worker)

  1. Le worker dépile les jobs : probe (durée/dimensions), thumbnail (miniature), archive (ZIP).
  2. Quand tous les jobs d'un événement sont done, il passe pushed→processed.
  3. Le client consulte/télécharge ses vidéos via la galerie (lecture Range, CSV, ZIP).

Phase F — Purge (RGPD)

  • Côté Borne : après push, l'opérateur purge les fichiers locaux (POST /sync/purge, exige pushed) pour libérer le disque.
  • Côté Hub : le client supprime définitivement l'événement (DELETE /events/:id, confirmation par nom) → rm -rf du dossier, statut purged.
  • Dans les deux cas : closeEventDb avant la suppression (§11.11), et le registry ne garde aucune donnée invité (§11.13).
ℹ Le fil rouge : la base d'événement voyage telle quelle

Le point qui fait tenir tout l'édifice : le db.sqlite a le même schéma sur la Borne et le Hub (core/eventDbSchema.js). Le push ne fait pas un « export/import » de données — il transfère le fichier de base lui-même. C'est pourquoi le checkpoint WAL (§11.8) est si important : il faut que le fichier soit complet et autonome avant le voyage. Une fois reçu, le Hub ouvre ce fichier comme s'il l'avait créé.
