3 — Le serveur Hub

hub/eventStore.js — cache LRU

Le Hub manipule potentiellement beaucoup d'événements, chacun avec sa propre base db.sqlite. Ouvrir un fichier SQLite a un coût, et garder des centaines de handles ouverts épuiserait les descripteurs de fichiers du système. Ce module résout le problème avec un cache LRU (Least Recently Used) limité à 10 bases ouvertes simultanément.

Le cœur : une Map ordonnée

const LRU_MAX = 10;

// Map ordonnée par ordre d'accès : la première entrée est la moins récemment utilisée
const _cache = new Map();    // eventId → Database

export function openEventDb(eventId, dataDir) {
  if (_cache.has(eventId)) {
    // Rafraîchir la position LRU : supprimer + réinsérer en fin
    const db = _cache.get(eventId);
    _cache.delete(eventId);
    _cache.set(eventId, db);
    return db;
  }

  if (_cache.size >= LRU_MAX) evictOldest();

  const dbPath = join(dataDir, 'events', eventId, 'db.sqlite');
  const db = createEventDb(dbPath);     // crée le schéma si besoin (voir core)
  _cache.set(eventId, db);
  return db;
}
JS La Map et son ordre d'insertion garanti

Une Map est une structure clé→valeur (comme un dict Python ou une map Go), mais avec deux propriétés que l'objet {} classique n'offre pas aussi bien : les clés peuvent être de n'importe quel type, et surtout l'ordre d'insertion est garanti par la spécification du langage.

C'est exactement ce qui rend le LRU trivial : la Map mémorise dans quel ordre les clés ont été ajoutées. En supprimant puis réinsérant une clé à chaque accès (delete + set), on la repousse en fin de Map. Donc la première entrée est toujours la moins récemment utilisée — celle à évincer.

OpérationMap JSPython
Existence_cache.has(k)k in d
Lire_cache.get(k)d[k]
Écrire_cache.set(k, v)d[k] = v
Supprimer_cache.delete(k)del d[k]
Taille_cache.sizelen(d)

L'équivalent Python direct serait collections.OrderedDict avec move_to_end() — la Map JS a la même garantie d'ordre, mais on « déplace en fin » manuellement (delete+set) car il n'y a pas de move_to_end natif. La complexité reste O(1) pour toutes les opérations.

Pourquoi une Map et pas un objet {} ? Avec un objet, l'ordre des clés est presque garanti mais avec des exceptions tordues (les clés numériques sont réordonnées en premier !). Pour un LRU où l'ordre est la donnée centrale, la Map est le bon outil — c'est précisément son cas d'usage canonique.

L'éviction

function evictOldest() {
  const [oldestId, oldestDb] = _cache.entries().next().value;
  oldestDb.close();              // ferme proprement le handle SQLite
  _cache.delete(oldestId);
}

_cache.entries() renvoie un itérateur sur les paires [clé, valeur], dans l'ordre d'insertion. .next().value prend la première paire (la plus ancienne). Le const [oldestId, oldestDb] = … est un destructuring de tableau : il extrait les deux éléments de la paire en deux variables d'un coup (≈ oldest_id, oldest_db = ... en Python). Avant de l'oublier du cache, on ferme le handle — sinon fuite de descripteur de fichier.

Fermeture ciblée — l'invariant §11.11

export function closeEventDb(eventId) {
  const db = _cache.get(eventId);
  if (!db) return;
  db.close();
  _cache.delete(eventId);
}
⛔ Fermer le handle AVANT tout rm -rf ou écrasement (§11.11)

closeEventDb n'est pas qu'un utilitaire de cache : c'est une pièce d'un invariant critique. Avant de supprimer le dossier d'un événement (purge RGPD) ou d'écraser son db.sqlite (réception au push), il faut fermer le handle SQLite ouvert. Raisons :

  • Un rm -rf d'un fichier encore ouvert laisse SQLite dans un état incohérent (et sous certains systèmes le fichier « disparaît » mais reste verrouillé).
  • Écraser le fichier (via renameSync) pendant qu'un handle pointe dessus corrompt la base : le handle voit l'ancien inode, les fichiers WAL/SHM ne correspondent plus.

On retrouve closeEventDb(id) appelé explicitement dans routes/events.js (DELETE/purge) et routes/sync.js (PUT /db, avant le renameSync).

ℹ Contraste avec la Borne

La Borne n'a qu'un événement actif à la fois — pas besoin d'un LRU. Son équivalent eventDb.js est un cache à une seule entrée. C'est une bonne illustration de « la structure de données suit le besoin réel » : même problème (éviter de rouvrir une base), solution dimensionnée différemment.
