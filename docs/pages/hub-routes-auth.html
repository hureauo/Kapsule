3 — Le serveur Hub

hub/routes/auth.js

Les deux endpoints d'authentification du Hub : POST /api/auth/login et POST /api/auth/register. C'est la page de référence pour async/await, le pattern Router, le hachage de mot de passe avec argon2, et la limitation de débit avec express-rate-limit.

JS express.Router() — regrouper des routes

Un Router est un mini-app Express : un groupe de routes qu'on monte ensuite sous un préfixe (app.use('/api/auth', makeAuthRouter())). C'est l'équivalent d'un Blueprint Flask. Le projet enveloppe chaque routeur dans une factory makeXxxRouter(...) pour pouvoir lui injecter dataDir ou de la config. 

export function makeAuthRouter() {
  const router = Router();
  router.post('/login', loginLimiter, async (req, res, next) => { /* … */ });
  router.post('/register', async (req, res, next) => { /* … */ });
  return router;
}
JS async / await et le modèle de concurrence de JS

JavaScript est mono-thread avec une boucle d'événements : un seul fil exécute le code, et les opérations longues (I/O réseau, fichiers, crypto) sont déléguées en arrière-plan. Une fonction async peut await une Promise : elle « met en pause » à ce point et rend la main à la boucle, qui traite d'autres requêtes ; quand la Promise se résout, l'exécution reprend après le await.

ModèleMécanisme
JS1 thread + event loop, await sur Promise
Pythonasyncio : async def / await (très proche)
Gogoroutines + channels (plusieurs threads, modèle différent)

Exemple dans le login :

const valid = await argon2.verify(user.password_hash, password);
//            ↑ pendant que argon2 calcule (coûteux), la boucle traite d'autres requêtes

Différence clé avec Go : en JS il n'y a pas de parallélisme par défaut — un seul cœur exécute ton code. await ne crée pas de thread ; il libère le thread unique pendant l'attente. C'est de la concurrence (entrelacement), pas du parallélisme (simultanéité). Pour un serveur I/O-bound (ce qu'est un serveur web), c'est suffisant et efficace : pendant qu'une requête attend argon2 ou le disque, les autres avancent. Pour du CPU-bound lourd (transcodage vidéo), on sort du processus principal — c'est pourquoi le worker est séparé et appelle ffmpeg en sous-processus.

Le modèle est quasi identique à l'asyncio de Python : si tu as déjà écrit async def / await en Python, tu sais déjà lire le code async de Kapsule. La Promise JS ≈ le coroutine/Future Python.

Le handler de login

router.post('/login', loginLimiter, async (req, res, next) => {
  try {
    const { email, password } = req.body;
    if (!email || !password) return res.status(400).json({ error: 'email et password requis' });

    const db = getDb();
    const user = getUserByEmail(db, email);
    if (!user) return res.status(401).json({ error: 'Identifiants invalides' });

    const valid = await argon2.verify(user.password_hash, password);
    if (!valid) return res.status(401).json({ error: 'Identifiants invalides' });

    const token = jwt.sign({ sub: user.id, role: user.role }, config.jwtSecret, { expiresIn: '24h' });
    res.json({ token });
  } catch (err) {
    next(err);
  }
});

Le squelette try { … } catch (err) { next(err); } est le pattern obligatoire des handlers async (voir index.js) : toute exception est routée vers le gestionnaire d'erreurs.

JS argon2 — hacher les mots de passe

On ne stocke jamais un mot de passe en clair. argon2 est une fonction de hachage lente et salée, conçue pour résister au brute-force (lauréate de la Password Hashing Competition). Deux opérations :

  • await argon2.hash(password, { type: argon2.argon2id }) → produit un hash à stocker (le sel est inclus dans la chaîne de sortie).
  • await argon2.verify(hash, password) → compare un mot de passe au hash stocké, renvoie un booléen.

Les deux sont async car le calcul est volontairement coûteux (~100 ms) — d'où le await. C'est l'équivalent de bcrypt/argon2-cffi en Python. Noter qu'on renvoie le même message « Identifiants invalides » que l'email soit inconnu ou le mot de passe faux : on ne révèle pas quel champ est en cause.

JS express-rate-limit — limiter les tentatives

loginLimiter est un middleware de limitation de débit, placé avant le handler de login : 

const loginLimiter = rateLimit({
  windowMs: 15 * 60 * 1000,   // fenêtre de 15 min
  max: 10,                     // 10 tentatives max par IP sur la fenêtre
  message: { error: 'Trop de tentatives, réessayez dans 15 minutes.' },
});
router.post('/login', loginLimiter, async (req, res, next) => { … });

Au-delà de 10 tentatives en 15 minutes depuis une même IP, le middleware répond 429 Too Many Requests sans même atteindre le handler. C'est une défense contre le brute-force des mots de passe. Comme c'est un middleware, il s'insère naturellement dans la chaîne — l'ordre (limiter d'abord, handler ensuite) est ce qui le rend efficace.

Le handler de register

Même structure, avec deux gardes supplémentaires :

if (!config.allowRegister) {
  return res.status(403).json({ error: 'Inscription désactivée. Utilisez npm run create-admin.' });
}
// … validations …
const password_hash = await argon2.hash(password, { type: argon2.argon2id });
const result = insertUser(db, { email, password_hash, name: name ?? null, role: 'client' });
const token = jwt.sign({ sub: result.lastInsertRowid, role: 'client' }, config.jwtSecret, { expiresIn: '24h' });
res.status(201).json({ token });
  • L'inscription publique n'est ouverte que si config.allowRegister est vrai (sinon 403). Par défaut elle est fermée : on crée le premier admin via le script create-admin, pas via l'API.
  • Un nouvel inscrit a toujours le rôle 'client' (jamais admin). On récupère son id via result.lastInsertRowid pour le mettre dans le jeton.
