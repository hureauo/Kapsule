4 — Le serveur Borne

borne/routes/sync.js

Les routes technicien qui pilotent la synchronisation depuis la Borne : consulter l'état, déclencher un pull manuel, lancer un push, purger un événement poussé. Ce sont des déclencheurs — la logique réelle vit dans sync/ (pull.js, push.js). La notion clé ici : lancer une tâche de fond sans bloquer la réponse HTTP.

⛔ §11.19 : toute la synchro est réservée au technicien

Le routeur lie sa garde au middleware tech, pas au middleware client : const auth = cfg.requireTech;. Toutes les routes ci-dessous utilisent ce auth — un jeton client (espace /admin) reçoit donc 403 sur /sync/status, /sync/pull, /sync/push et /sync/purge. La synchro fait partie des outils de déploiement réservés à l'installateur (espace /admin/tech). Voir requireTech.

Lancer un push en tâche de fond

function isPreviewMode(cfg) {
  return !!(cfg.previewMode ?? config.previewMode) || !!(getActiveEvent()?.is_preview);
}

router.post('/sync/push/:eventId', auth, (req, res, next) => {
  const { eventId } = req.params;
  const db = getRegistry();
  const event = db.prepare('SELECT * FROM local_events WHERE id = ?').get(eventId);

  if (!event) return res.status(404).json({ error: 'Événement introuvable' });

  if (isPreviewMode(cfg)) {
    return res.status(409).json({ error: 'Push interdit en mode démo (borne d\'essai)' });
  }

  if (event.status !== 'closed') return res.status(409).json({ error: 'Clôturez l\'événement avant le push' });

  const state = getPushState();
  if (state.running) return res.status(409).json({ error: 'Un push est déjà en cours' });

  // Lancement en tâche de fond — la progression se lit via GET /sync/status
  pushEvent(eventId, dataDir).catch(() => {});

  res.json({ ok: true });
});
⛔ Invariant §11.21 : push interdit en mode démo (borne d'essai)

Le garde isPreviewMode(cfg) est testé en premier (juste après le 404) : une borne d'essai ne doit jamais envoyer ses données au Hub — c'est tout l'intérêt du mode démo (le client teste sans polluer l'événement réel). Le mode démo se déduit de deux sources : la config (previewMode, fixée par PREVIEW_MODE=true) ou le flag is_preview de l'événement actif (persisté au pull depuis le token Hub, §11.20). On répond 409 sans rien transférer. La même fonction isPreviewMode garde aussi POST /sync/reset-preview ci-dessous (à l'inverse : reset autorisé seulement en mode démo).

JS Tâche de fond : appeler une async sans await

pushEvent(...) est une fonction async longue (transfert de plusieurs vidéos). On l'appelle sans await : le handler n'attend pas la fin du push, il répond { ok: true } immédiatement. Le push continue « en arrière-plan » (la Promise vit sa vie). Le client suit l'avancement via GET /sync/status.

Le .catch(() => {}) est obligatoire : une Promise non-attendue qui rejette sans .catch provoque un « unhandled rejection » (warning, voire crash selon la config Node). Ici, comme on ne fait pas await, on doit attacher un .catch pour absorber une éventuelle erreur — l'erreur réelle est de toute façon stockée dans l'état de push (_state.lastError) et lisible via /sync/status.

FormeEffet
await f()attend la fin, propage l'erreur
f().catch(()=>{})lance en fond, n'attend pas, absorbe l'erreur

C'est le pattern « fire and forget » : adapté quand l'opération est longue et que le client n'a pas besoin d'attendre sa complétion pour continuer (il pollera l'état). Le risque à connaître : si le processus s'arrête, la tâche de fond meurt avec lui. Pour le push, ce n'est pas grave — il est reprenable via le manifest, donc un push interrompu se relance proprement. Pour une opération non reprenable, ce pattern serait dangereux.

Les gardes avant push

Quatre conditions avant de lancer :

  • L'événement existe (404 sinon).
  • La borne n'est pas en mode démo (409 sinon, §11.21) — une borne d'essai ne pousse jamais.
  • Il est closed (409 sinon) — on ne pousse qu'un événement clôturé.
  • Aucun push déjà en cours (getPushState().running → 409 sinon) — un seul push à la fois, l'état partagé sert de verrou. Voir push.js.

Le reset de la borne d'essai (§11.21)

router.post('/sync/reset-preview', auth, (req, res, next) => {
  try {
    if (!isPreviewMode(cfg)) {
      return res.status(403).json({ error: 'Disponible uniquement en mode démo (borne d\'essai)' });
    }

    const active = getActiveEvent();
    if (!active) return res.status(404).json({ error: 'Aucun événement actif' });

    const db = getActiveEventDb(dataDir, active);
    const videos = db.prepare('SELECT filename FROM videos').all();

    db.transaction(() => {
      db.prepare('DELETE FROM videos').run();
      db.prepare('DELETE FROM sessions').run();
    })();

    for (const v of videos) {
      unlink(join(dataDir, 'events', active.id, 'videos', v.filename), () => {});
    }

    res.json({ ok: true, deleted: videos.length });
  } catch (err) { next(err); }
});
ℹ Reset = repartir d'une borne d'essai propre, sans perdre les questions

Pendant une démo, le client enregistre des vidéos de test. reset-preview lui permet de tout effacer (sessions + vidéos) pour repartir d'une borne vierge, sans toucher aux questions ni à la configuration de l'événement — il n'a donc pas à re-pull depuis le Hub. Logique :

  1. On lit d'abord la liste des filename à supprimer (avant de vider la table — sinon on perdrait les chemins des fichiers à unlink).
  2. DELETE FROM videos + DELETE FROM sessions dans une transaction : les deux tables sont vidées atomiquement. Les questions, elles, restent intactes.
  3. unlink best-effort de chaque fichier physique (callback vide, on ignore les erreurs). Même esprit que videos.js : base d'abord, fichiers ensuite.

Réponse : { ok: true, deleted: <n> }.

⛔ Invariant §11.21 : reset réservé au mode démo (403 sinon)

Symétrique du push : reset-preview est refusé hors mode démo (403). Effacer toutes les sessions/vidéos d'un événement réel serait catastrophique (souvenirs perdus). Le garde isPreviewMode(cfg) n'autorise l'opération que sur une borne d'essai. Un événement réel renvoie donc 403 même avec un jeton technicien valide.

La purge locale (§11.11)

router.post('/sync/purge/:eventId', auth, (req, res, next) => {
  // … vérifie status === 'pushed' et confirm === event.name …

  closeEventDb();                               // §11.11 : fermer le handle AVANT rm -rf

  const eventDir = join(dataDir, 'events', eventId);
  if (existsSync(eventDir)) rmSync(eventDir, { recursive: true, force: true });

  db.prepare('DELETE FROM push_state WHERE event_id = ?').run(eventId);
  db.prepare('UPDATE local_events SET active = 0, updated_at = CURRENT_TIMESTAMP WHERE id = ?').run(eventId);
  updateEventStatus(eventId, 'purged');
  res.json({ ok: true });
});
⛔ Purge : seulement après push, avec confirmation, et closeEventDb d'abord

La purge locale supprime les fichiers de la Borne pour libérer de l'espace, une fois que les données sont en sécurité sur le Hub. D'où l'exigence status === 'pushed' : on ne purge pas un événement non sauvegardé. Comme côté Hub, on exige la confirmation par le nom exact, et on appelle closeEventDb() avant le rmSync (§11.11) — l'événement purgé peut encore être l'actif, donc son handle est peut-être ouvert. On nettoie aussi push_state et on désactive l'événement (il ne doit plus être servi au kiosque).

Pull manuel

router.post('/sync/pull', auth, (req, res) => {
  pullMyEvent(dataDir).catch(() => {});   // best-effort, sans attendre
  res.json({ ok: true });
});

Même pattern « fire and forget » : on déclenche un pull immédiat (en plus du pull automatique périodique) sans attendre son résultat. Utile pour forcer une synchro quand l'opérateur vient de préparer l'événement côté Hub.

Toutes ces routes exigent un jeton tech (requireTech, §11.19).
