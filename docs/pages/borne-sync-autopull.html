4 — Le serveur Borne

borne/sync/autoPull.js

Le pull automatique : un cycle qui tourne périodiquement pour (1) envoyer au Hub les statuts live/closed des événements locaux (heartbeats), et (2) tirer l'événement du token (pullMyEvent, §11.20). C'est la page de référence pour setInterval et le pattern « timer de fond ».

Le timer

let _timer = null;
let _lastPull = null;   // ISO du dernier pull réussi
export function getLastPull() { return _lastPull; }

export function startAutoPull(dataDir) {
  if (_timer !== null) return;                                  // déjà démarré → no-op
  runCycle(dataDir).catch(() => {});                            // premier cycle immédiat
  _timer = setInterval(() => runCycle(dataDir).catch(() => {}), config.pullIntervalMs);
}

export function stopAutoPull() {
  if (_timer !== null) { clearInterval(_timer); _timer = null; }
}
JS setInterval / clearInterval

setInterval(fn, ms) exécute fn toutes les ms millisecondes, indéfiniment, et retourne un identifiant de timer. clearInterval(id) l'arrête. Ici l'intervalle est config.pullIntervalMs (5 min par défaut). C'est le moteur du pull périodique.

Deux gardes idiomatiques : if (_timer !== null) return empêche de démarrer deux timers (idempotence) ; _timer = null après clearInterval permet de redémarrer proprement. Le runCycle(...).catch(() => {}) avant le setInterval lance un premier cycle immédiat — sinon il faudrait attendre 5 min avant le premier pull au démarrage.

Chaque tick fait runCycle(...).catch(() => {}) : on lance le cycle async sans l'attendre (le callback de setInterval n'est pas await-é par le timer), et on absorbe les erreurs. Conséquence à connaître : si un cycle dure plus longtemps que l'intervalle, plusieurs cycles peuvent se chevaucher. Ici ce n'est pas un problème car les opérations sont idempotentes et le pull saute les événements non-loaded, mais c'est une subtilité de setInterval + async à garder en tête (contrairement à un setTimeout qui se reprogramme à la fin de chaque exécution).

Un cycle : heartbeats puis pull conditionnel

async function runCycle(dataDir) {
  if (!config.hubUrl || !config.boxToken) return;     // mode autonome → ne rien faire

  await sendHeartbeats();

  const db = getRegistry();
  const hasLoaded = db.prepare("SELECT 1 FROM local_events WHERE status = 'loaded' LIMIT 1").get();
  const hasNone = db.prepare('SELECT COUNT(*) as n FROM local_events').get().n === 0;

  if (hasLoaded || hasNone) {
    try {
      await pullMyEvent(dataDir);
      _lastPull = new Date().toISOString();
    } catch { /* réseau — silencieux, retenté au prochain cycle */ }
  }
}

Deux gardes intelligentes :

  • Mode autonome : si pas de hubUrl ou pas de boxToken, le cycle ne fait rien. Une borne 100 % offline n'essaie jamais de joindre un Hub.
  • Pull conditionnel : on ne pulle que s'il existe au moins un événement loaded (susceptible de recevoir des mises à jour) ou qu'il n'y a aucun événement local (bootstrap initial). Si tous les événements sont déjà live/ closed/pushed, inutile de solliciter le Hub — on évite du trafic réseau superflu.

Les heartbeats

async function sendHeartbeats() {
  const db = getRegistry();
  const events = db.prepare("SELECT * FROM local_events WHERE status IN ('live','closed')").all();
  for (const ev of events) {
    try {
      await hubFetch(`/api/sync/events/${ev.id}/status`, {
        method: 'POST', body: JSON.stringify({ status: ev.status }),
        headers: { 'Content-Type': 'application/json' },
      });
    } catch { /* best effort — silencieux */ }
  }
}
ℹ Pourquoi des heartbeats « best-effort » ?

Quand un événement passe live (premier invité) ou closed (clôture) sur la Borne, le Hub doit le savoir pour mettre à jour son propre statut. Mais la Borne peut être hors-ligne à ce moment précis. La solution : réémettre le statut à chaque cycle, en best-effort (le try/catch silencieux ignore les échecs réseau). Si le Hub est injoignable maintenant, le prochain cycle réessaiera. C'est un mécanisme de convergence : tant que la Borne a parfois du réseau, le Hub finit par recevoir les statuts. Le Hub, de son côté, ignore les transitions « en arrière » (voir POST /status), donc réémettre plusieurs fois est sans danger.
