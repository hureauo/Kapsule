5 — Le code front (web)

borne/web client.js — XHR

Le client API du front Borne. Sa partie apiFetch et l'objet api sont jumeaux de ceux du Hub. La nouveauté — et la raison d'être de cette page — est l'upload vidéo via XMLHttpRequest, qui permet de suivre la progression (ce que fetch ne sait pas faire).

Pourquoi XHR et pas fetch pour l'upload ?

// Upload vidéo invité via XHR (seul XHR expose upload.onprogress — fetch ne le fait pas)
export function uploadVideo({ sessionId, questionId, questionText, blob, mimeType, onProgress }) {
  return new Promise((resolve, reject) => {
    const ext = mimeType.includes('mp4') ? 'mp4' : 'webm';
    const file = new File([blob], `recording.${ext}`, { type: mimeType });
    const form = new FormData();
    form.append('video', file);
    form.append('session_id', sessionId);
    if (questionId != null) form.append('question_id', String(questionId));
    form.append('question_text', questionText);
    form.append('recorded_at', new Date().toISOString());

    const xhr = new XMLHttpRequest();
    xhr.open('POST', '/api/videos');
    xhr.setRequestHeader('Accept', 'application/json');

    if (onProgress) {
      xhr.upload.onprogress = (e) => {
        if (e.lengthComputable) onProgress(e.loaded / e.total);    // 0 → 1
      };
    }
    xhr.onload = () => {
      if (xhr.status >= 200 && xhr.status < 300) resolve(JSON.parse(xhr.responseText));
      else {
        const body = JSON.parse(xhr.responseText || '{}');
        reject(Object.assign(new Error(body.error ?? `HTTP ${xhr.status}`), { status: xhr.status }));
      }
    };
    xhr.onerror = () => reject(new Error('Erreur réseau'));
    xhr.send(form);
  });
}
JS XMLHttpRequest et upload.onprogress

XMLHttpRequest (XHR) est l'ancienne API de requêtes du navigateur, antérieure à fetch. On l'utilise spécifiquement ici pour une raison : xhr.upload.onprogress émet des événements pendant l'envoi du corps, avec e.loaded / e.total (octets envoyés / total). C'est ce qui permet d'afficher une barre de progression d'upload. fetch, lui, n'expose pas la progression d'upload — c'est sa limitation majeure et la seule raison de garder XHR.

XHR fonctionne par événements (onload, onerror, upload.onprogress), pas par Promise. On l'enveloppe donc dans une Promise manuelle (même technique que checksum.js) : resolve sur onload succès, reject sur erreur. Résultat : l'appelant peut await uploadVideo({...}) tout en passant un callback onProgress pour la barre.

C'est l'invariant qui explique ce choix dans PROJET.md : l'upload kiosque doit montrer une progression (une vidéo de plusieurs dizaines de Mo sur le Wi-Fi d'une salle peut prendre du temps — l'invité a besoin d'un retour visuel). Donc XHR ici, fetch partout ailleurs. Le code combine aussi cet upload avec une politique de retry/backoff (5 essais, min(2000·2^(n-1), 30000)) au niveau de la couche qui l'appelle — la même formule que hubClient, pour un comportement cohérent sur réseau instable.

JS File et Blob côté navigateur

La vidéo enregistrée est un Blob (données binaires, produit par MediaRecorder). new File([blob], 'recording.mp4', { type: mimeType }) l'emballe en File (un Blob avec un nom et un type) — nécessaire pour que FormData l'envoie comme un fichier nommé. FormData construit le corps multipart, exactement comme côté Node mais avec les objets natifs du navigateur. Le champ s'appelle video — c'est ce que multer côté serveur attend (upload.single('video')).

Deux jetons, deux wrappers : apiFetch et techApiFetch

L'admin Borne est scindé en deux espaces (§11.19) — client (/admin) et technicien (/admin/tech) — chacun avec son propre jeton en localStorage : 

const TOKEN_KEY = 'admin_token';
const TECH_TOKEN_KEY = 'tech_token';

function getToken()     { return localStorage.getItem(TOKEN_KEY); }
function getTechToken() { return localStorage.getItem(TECH_TOKEN_KEY); }

export function saveToken(token)      { localStorage.setItem(TOKEN_KEY, token); }
export function saveTechToken(token)  { localStorage.setItem(TECH_TOKEN_KEY, token); }
export function clearToken()          { localStorage.removeItem(TOKEN_KEY); }
export function clearTechToken()      { localStorage.removeItem(TECH_TOKEN_KEY); }
export function isAuthenticated()     { return Boolean(getToken()); }
export function isTechAuthenticated() { return Boolean(getTechToken()); }

Comme le même endpoint de login sert les deux espaces (le serveur signe le rôle dans le JWT, voir auth.js), c'est le composant front qui range le jeton dans la bonne clé : AdminPage appelle saveToken, TechPage appelle saveTechToken. Le routage entre les deux est manuel (lecture de window.location.pathname dans App.jsx, sans react-router).

Conséquence côté client : deux wrappers fetch jumeaux. Le wrapper par défaut apiFetch attache admin_token ; techApiFetch attache tech_token. Les méthodes de l'objet api choisissent l'un ou l'autre selon que la route est protégée par requireAdmin ou requireTech côté serveur : 

// Routes tech (préflight, synchro, clôture) — lisent tech_token (§11.19)
async function techApiFetch(path, options = {}) {
  const token = getTechToken();
  // … identique à apiFetch, mais avec le jeton tech …

export const api = {
  // Routes client (requireAdmin = client OU tech) → apiFetch / admin_token
  listEvents:          () => apiFetch('/api/events'),
  updateEventSettings: (id, s) => apiFetch(`/api/events/${id}/settings`, { method: 'PUT', body: JSON.stringify(s) }),
  // …
  // Routes tech (requireTech) → techApiFetch / tech_token
  closeEvent:    (id) => techApiFetch(`/api/events/${id}/close`, { method: 'PUT' }),
  getPreflight:  (t)  => techApiFetch(`/api/preflight?client_time=${encodeURIComponent(t)}`),
  getSyncStatus:     ()   => techApiFetch('/api/sync/status'),
  getHubConfig:      ()   => techApiFetch('/api/sync/hub-config'),
  triggerPull:       ()   => techApiFetch('/api/sync/pull', { method: 'POST' }),
  triggerPushConfig: ()   => techApiFetch('/api/sync/push-config', { method: 'POST' }),
  updateToken:       (t)  => techApiFetch('/api/sync/token', { method: 'POST', body: JSON.stringify({ token: t }) }),
  triggerPush:       (id) => techApiFetch(`/api/sync/push/${id}`, { method: 'POST' }),
  purgeEvent:        (id, confirm) => techApiFetch(`/api/sync/purge/${id}`, { method: 'POST', body: JSON.stringify({ confirm }) }),
};

Le découpage côté client doit refléter le re-tagging côté serveur : si closeEvent partait sur apiFetch (jeton client), elle enverrait admin_token à une route requireTech et récolterait un 403. L'autorité reste le middleware serveur (§11.19) ; le bon wrapper côté front n'est qu'une commodité pour envoyer d'emblée le bon jeton.

→ détail : apiFetch, localStorage, ?token= (vu dans hub/web client.js)

Une particularité inchangée : certaines routes invité (créer une session, uploader) sont publiques — pas de jeton du tout.

Parmi les méthodes client, updateEventSettings(id, settings) appelle la route PUT /events/:id/settings (thème + textes) en JSON.stringify(settings). Le test du Content-Type dans apiFetch ne dépend pas de la présence du jeton mais de celle d'un corps de requête (if (options.body && !(options.body instanceof FormData))), pour qu'un POST/PUT envoie bien application/json.

L'URL vidéo invité (capability)

export function guestVideoUrl(sessionId, questionId) {
  return `/api/sessions/${sessionId}/videos/${questionId}/file`;   // pas de token : capability
}

Pour que l'invité revoie sa vidéo, l'URL ne porte pas de jeton : l'accès est protégé par l'UUID de session lui-même (le capability token). Connaître l'URL = avoir le droit. Cohérent avec la route publique correspondante côté serveur.
