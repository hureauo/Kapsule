7 — Transversal

Décisions d'architecture

Les choix non-évidents du projet, regroupés ici avec leur justification. Quand tu te demandes « pourquoi est-ce fait comme ça plutôt qu'autrement ? », la réponse est probablement ici.

Pourquoi ESM (et pas CommonJS) ?

Le projet est en import/export partout ("type": "module"). Raisons : cohérence avec les fronts React (ESM natif côté navigateur), c'est le standard moderne (CommonJS est l'héritage), et les imports dynamiques propres (import() dans le worker). Le revers : quelques libs natives s'intègrent historiquement plus simplement en CJS, et l'extension .js est obligatoire dans les imports relatifs. Détail : ESM.

Pourquoi better-sqlite3 (synchrone) plutôt qu'un ORM async ?

SQLite est une base en-process (pas de serveur réseau) : une requête prend des microsecondes. Une API synchrone évite l'overhead et la complexité de l'async pour un gain de blocage nul en pratique — et rend les transactions réellement atomiques (aucun await ne peut s'intercaler au milieu). Pas d'ORM : le SQL est simple, explicite, et on garde le contrôle total des requêtes (utile pour les index, les jointures, les UPSERT). Détail : eventDbSchema.

Pourquoi une base SQLite par événement ?

Trois bénéfices : RGPD (purge = rm -rf d'un dossier), transfert (le push envoie un fichier db.sqlite autonome, pas un export partiel), isolation (un événement corrompu n'affecte pas les autres). Le coût (plusieurs fichiers ouverts) est borné par un cache LRU côté Hub et un cache à 1 entrée côté Borne. Détail : Deux apps, deux bases.

Pourquoi le registry et l'event store sont séparés ?

Conséquence directe de l'invariant RGPD §11.13 : les données « annuaire » (qui existe, quel statut) sont distinctes des données « contenu » (prénoms, vidéos). Le registry survit à une purge (il garde la trace qu'un événement a existé, sans données personnelles) ; l'event store est jetable d'un bloc. Détail : §11.13.

Pourquoi JWT dans ?token= pour les vidéos ?

Un <video src>, un <a download> ou un CSV ouvert par le navigateur ne peuvent pas porter d'en-tête Authorization (le navigateur charge la ressource lui-même). Le seul moyen d'authentifier ces requêtes est le jeton en query. C'est l'invariant §11.2, présent des deux côtés : construction d'URL côté front, extraction côté serveur.

Pourquoi XMLHttpRequest et pas fetch pour l'upload ?

Uniquement parce que fetch n'expose pas la progression d'envoi, alors que xhr.upload.onprogress oui. Une vidéo de dizaines de Mo sur le Wi-Fi d'une salle a besoin d'une barre de progression. Partout ailleurs, c'est fetch. Invariant §11.18, détail : client.js Borne.

Pourquoi un worker séparé (et pas dans le serveur HTTP) ?

Le traitement vidéo (ffmpeg) est CPU-bound et lent. Le faire dans un handler HTTP bloquerait la boucle d'événements et figerait le serveur. Le worker est un processus distinct (même image Docker, commande différente) qui dépile les jobs en boucle. La table jobs SQLite sert de file — pas de Redis/BullMQ à déployer, simplicité maximale pour la charge attendue.

Pourquoi le worker fait du polling plutôt qu'une vraie file de messages ?

Pour éviter une dépendance externe (Redis…). La table jobs est la file ; le worker la scrute toutes les 5 s. Compromis : latence jusqu'à 5 s avant prise d'un job — acceptable ici. Le « claim » est rendu atomique par une transaction (SELECT+UPDATE) pour rester correct même avec plusieurs workers. Détail : worker.

Pourquoi les tests instancient le serveur en mémoire (pas via Docker) ?

supertest attaque l'app Express directement en mémoire, sans ouvrir de port — rapide, sans conflit, parallélisable. Chaque suite a un DATA_DIR temporaire jetable. C'est permis par le « main module guard » : createApp est exporté sans .listen(). Le runner tourne dans Docker (Node absent en local) mais le code testé, lui, ne dépend pas de Docker.

Pourquoi des factory functions pour les routeurs ?

makeXxxRouter(dataDir, cfg) permet d'injecter le dossier de données et la config — au lieu de variables globales. Bénéfice : testabilité (on passe un dataDir temporaire et une config de test), et découplage. Côté Borne, la config est carrément injectée dans chaque routeur (vs import direct côté Hub) — deux styles cohérents, l'un privilégiant la pureté, l'autre la concision.

Pourquoi argon2 (Hub) mais timingSafeEqual (Borne) ?

Le Hub a des comptes avec mots de passe → hachage argon2 (lent, salé, résistant au brute-force ; verify est déjà constant-time). La Borne a un unique mot de passe admin comparé en clair → on le protège avec timingSafeEqual (comparaison à temps constant). Deux contextes, deux outils adaptés.

ℹ Le fil conducteur de ces décisions

La plupart de ces choix privilégient la simplicité et l'absence de dépendances (SQLite plutôt qu'un SGBD réseau, polling plutôt qu'une file de messages, runner natif plutôt que Jest), tout en respectant deux contraintes fortes : le RGPD (séparation des données, purge atomique) et le fonctionnement hors-ligne de la Borne (tout est local, la synchro est reprenable). Quand tu ajoutes du code, garde ces deux boussoles.
