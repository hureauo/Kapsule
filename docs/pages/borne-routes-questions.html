4 — Le serveur Borne

borne/routes/questions.js

Le CRUD des questions côté Borne. Quasi identique à hub/routes/questions.js dans sa logique (validation, ordre des routes §11.1, UPDATE dynamique), avec deux nuances : il opère sur l'événement actif (pas un :eventId dans l'URL), et il expose une route publique pour le kiosque.

Public vs admin : deux vues des questions

// PUBLIC (kiosque) — uniquement les questions activées
router.get('/questions', (req, res, next) => {
  const db = requireActiveDb(req, res);
  if (!db) return;
  const questions = db.prepare('SELECT * FROM questions WHERE enabled=1 ORDER BY order_index, id').all();
  res.json(questions);
});

// ADMIN — toutes les questions (même désactivées)
router.get('/questions/all', auth, (req, res, next) => {
  const db = requireActiveDb(req, res);
  if (!db) return;
  const questions = db.prepare('SELECT * FROM questions ORDER BY order_index, id').all();
  res.json(questions);
});

La route publique /questions ne renvoie que les questions enabled=1 : c'est ce que l'invité voit dans le kiosque. La route admin /questions/all renvoie tout, y compris les désactivées, pour que l'opérateur puisse les gérer. Distinction classique « vue publique filtrée / vue admin complète ».

⛔ §11.1 encore : /questions/all et /questions/reorder/batch avant /questions/:id

Comme partout, les routes à segment littéral (/all, /reorder/batch) sont déclarées avant /questions/:id, sinon "all" ou "reorder" seraient interprétés comme un :id. Le commentaire du code le rappelle explicitement.

Le reste : identique au Hub

La validation (validateQuestion), le réordonnancement en transaction, et l'UPDATE dynamique sur champs partiels fonctionnent exactement comme côté Hub — inutile de les re-détailler ici.

→ détail : validation, reorder, UPDATE dynamique (vu dans hub/routes/questions.js)
ℹ La différence de fond : « actif » plutôt que « par id »

Le Hub gère les questions de n'importe quel événement via :eventId dans l'URL (+ requireOwner). La Borne ne gère que les questions de l'événement actif — d'où requireActiveDb au lieu d'un paramètre d'URL. C'est la conséquence directe du modèle « une borne = un événement actif » (voir eventDb.js). Toute la pré-résolution d'événement disparaît : pas de mergeParams, pas de requireOwner.
