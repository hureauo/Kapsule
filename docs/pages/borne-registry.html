4 — Le serveur Borne

borne/registry.js — état local

Le registre local de la Borne, volontairement minimal : deux tables seulement (local_events et push_state). Même pattern singleton que le Hub (registry.js), mais avec une particularité intéressante : une migration douce du schéma.

Le schéma : deux tables, zéro donnée invité

db.exec(`
  CREATE TABLE IF NOT EXISTS local_events (
    id         TEXT PRIMARY KEY,
    name       TEXT NOT NULL,
    origin     TEXT NOT NULL CHECK(origin IN ('hub','local')),
    status     TEXT NOT NULL DEFAULT 'loaded'
               CHECK(status IN ('loaded','live','closed','pushed','purged')),
    active     INTEGER NOT NULL DEFAULT 0,
    is_preview INTEGER NOT NULL DEFAULT 0,
    pulled_at  DATETIME, pushed_at DATETIME,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP
  );

  CREATE TABLE IF NOT EXISTS push_state (
    event_id    TEXT NOT NULL,
    video_id    TEXT NOT NULL,
    checksum    TEXT NOT NULL,
    uploaded_at DATETIME,
    PRIMARY KEY (event_id, video_id)
  );
`);
⛔ Invariant RGPD §11.13 : toujours respecté ici

local_events ne contient que des métadonnées (id, nom de l'événement, statut) ; push_state ne contient que des id et checksums. Aucun prénom, aucune vidéo, aucune session — tout ça vit dans events/<id>/db.sqlite. La purge d'un événement reste un rm -rf du dossier. Voir Deux apps, deux bases.

Quelques colonnes notables :

  • origin CHECK(origin IN ('hub','local')) : un événement vient soit du Hub (pullé), soit a été créé localement sur la borne autonome.
  • active : un booléen (0/1) marquant l'unique événement actif — celui que le kiosque sert aux invités. Un seul à la fois (voir setActiveEvent).
  • is_preview : un booléen (0/1) indiquant que l'événement vient d'un token borne d'essai (mode démo). Persisté au pull depuis la réponse Hub (pullMyEvent, §11.20) ; combiné à previewMode de la config, il déclenche le refus de push, le quota d'upload et le bandeau « BORNE D'ESSAI » (§11.21).
  • Les statuts de la Borne (loaded → live → closed → pushed → purged) sont un sous-ensemble de ceux du Hub : la Borne ne connaît pas draft/ready (préparation côté Hub) ni processed (traitement côté Hub).

La migration douce

// Migrations douces
const cols = db.pragma('table_info(local_events)').map(c => c.name);
if (!cols.includes('pulled_at')) db.exec('ALTER TABLE local_events ADD COLUMN pulled_at DATETIME');
if (!cols.includes('pushed_at')) db.exec('ALTER TABLE local_events ADD COLUMN pushed_at DATETIME');
if (!cols.includes('is_preview')) db.exec('ALTER TABLE local_events ADD COLUMN is_preview INTEGER NOT NULL DEFAULT 0');
JS Migration de schéma avec PRAGMA table_info

CREATE TABLE IF NOT EXISTS ne modifie pas une table existante : si la table a été créée par une version antérieure du code (sans les colonnes pulled_at/ pushed_at, ou is_preview ajoutée en Phase 6D), elle reste telle quelle. Pour ajouter ces colonnes sur une base déjà en service, on fait une migration manuelle, une ligne par colonne attendue :

  1. db.pragma('table_info(local_events)') renvoie la liste des colonnes actuelles (un tableau d'objets avec .name).
  2. .map(c => c.name) en extrait les noms.
  3. Si une colonne attendue manque, on l'ajoute avec ALTER TABLE … ADD COLUMN.

C'est une migration idempotente et défensive : on vérifie avant d'ajouter, donc relancer le code ne casse rien. C'est une mini-version de ce que feraient des outils comme Alembic (Python) ou les migrations Go — mais fait à la main, adapté à un projet où le schéma évolue peu.

Pourquoi pas un vrai système de migrations versionnées ? Parce que SQLite + projet de cette taille = la simplicité prime. La limite de cette approche : elle ne gère que l'ajout de colonnes (SQLite ne sait pas facilement supprimer/renommer une colonne sans recréer la table). Pour une refonte de schéma plus profonde, il faudrait une stratégie « créer nouvelle table → copier → remplacer ». Mais pour ajouter des colonnes nullable, ce pattern est parfait et lisible.

Helpers métier : la notion d'événement « actif »

export function getActiveEvent() {
  return getRegistry().prepare('SELECT * FROM local_events WHERE active = 1 LIMIT 1').get() ?? null;
}

export function setActiveEvent(id) {
  const db = getRegistry();
  db.transaction(() => {
    db.prepare('UPDATE local_events SET active = 0, updated_at = CURRENT_TIMESTAMP').run();           // désactive tout
    db.prepare('UPDATE local_events SET active = 1, updated_at = CURRENT_TIMESTAMP WHERE id = ?').run(id);  // active celui-ci
  })();
}

setActiveEvent illustre une transaction qui maintient un invariant métier : « au plus un événement actif ». On désactive tous les événements puis on active le ciblé, le tout atomiquement — impossible de se retrouver avec deux actifs ou zéro pendant une fraction de seconde. getActiveEvent renvoie l'actif ou null (le ?? null convertit le undefined de .get() en null explicite).
