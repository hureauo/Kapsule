3 — Le serveur Hub

hub/middleware/boxAuth.js

Les routes de synchronisation (routes/sync.js) ne sont pas appelées par un humain via le navigateur, mais par une Borne. Elles s'authentifient donc différemment : pas de JWT, mais un jeton de borne envoyé dans l'en-tête X-Box-Token. C'est le rôle de requireBox.

Le fichier entier :

import { createHash } from 'node:crypto';
import { getDb, getBoxTokenByHash, updateBoxTokenSeen } from '../registry.js';

export function requireBox(req, res, next) {
  const raw = req.headers['x-box-token'];
  if (!raw) return res.status(401).json({ error: 'X-Box-Token manquant' });

  const hash = createHash('sha256').update(raw).digest('hex');
  const db = getDb();
  const row = getBoxTokenByHash(db, hash);
  if (!row) return res.status(401).json({ error: 'Token borne invalide' });

  updateBoxTokenSeen(db, row.id);
  // Exposer token_id, event_id et is_preview (invariant §11.20)
  req.box = { token_id: row.id, event_id: row.event_id, is_preview: row.is_preview };
  next();
}

Comment ça marche

  1. On lit l'en-tête x-box-token. Détail JS : les noms d'en-têtes sont normalisés en minuscules par Node, donc on accède toujours à req.headers['x-box-token'] même si la Borne a envoyé X-Box-Token. La notation crochets ['x-box-token'] est obligatoire car le nom contient des tirets (impossible en notation pointée).
  2. On calcule le SHA-256 du jeton reçu, puis on cherche un token de borne (box_tokens) ayant ce hash.
  3. Si trouvé → on note la date de dernier contact (updateBoxTokenSeen), on attache à req.box un objet réduit { token_id, event_id, is_preview }, et on passe la main.
⛔ §11.20 — req.box porte l'event_id (token = événement)

Depuis la Phase 6C, un token de borne désigne directement un événement (voir la table box_tokens). Le middleware n'expose donc plus la ligne brute mais un objet ciblé : req.box = { token_id, event_id, is_preview }. Toutes les routes de sync.js s'en servent pour rejeter (403) toute requête …/events/:id/… où :id ≠ req.box.event_id — un token ne peut tirer ou pousser que son propre événement. C'est le cœur de l'invariant §11.20. On n'expose volontairement pas token_hash dans req.box (rien à en faire en aval, et on évite de le promener).

⛔ On stocke le hash du jeton, jamais le jeton en clair

La table box_tokens ne contient que token_hash, pas le jeton lui-même. À la génération d'un token (routes/admin.js), le jeton en clair est renvoyé une seule fois à l'admin (pour le configurer sur la Borne), puis seul son hash est conservé. Si la base fuite, les jetons restent inutilisables (on ne peut pas inverser un SHA-256). C'est le même principe que le hachage des mots de passe — sauf qu'ici on utilise un simple SHA-256 (et non argon2) car le jeton est déjà une chaîne aléatoire de 256 bits, non « devinable » par force brute.

→ notion JS : createHash / node:crypto (vue dans core/checksum.js)
JS Hacher une chaîne (vs un fichier)

Dans checksum.js on hachait un fichier en streaming. Ici on hache une simple chaîne, donc tout tient sur une ligne : createHash('sha256').update(raw).digest('hex'). update() alimente le hash (on peut l'appeler plusieurs fois), digest('hex') finalise et renvoie l'empreinte en hexadécimal. C'est une API « chaînable » (chaque méthode retourne l'objet).

Pourquoi pas de sync_log ici ?

Le commentaire le dit : le middleware ne journalise pas le contact. Ce sont les routes qui posent leur propre entrée dans sync_log avec l'action précise (pull, push_manifest, push_file, finalize…). Le middleware se contente de mettre à jour last_seen_at (utile pour l'écran admin « cette borne a été vue il y a X minutes »). Séparation des responsabilités : l'authentification authentifie, la route journalise son métier.
