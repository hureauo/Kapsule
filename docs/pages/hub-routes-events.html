3 — Le serveur Hub

hub/routes/events.js

Le CRUD des événements côté Hub : créer, lister, lire, modifier, changer de statut, assigner une borne, supprimer (purge RGPD). C'est le routeur le plus complet — il illustre Set, Map, la gestion des transitions de statut, et un invariant de purge.

Statuts gelés : un Set

const FROZEN_STATUSES = new Set(['live', 'closed', 'pushed', 'processed', 'purged']);
function isFrozen(status) { return FROZEN_STATUSES.has(status); }
JS Le Set — un ensemble

Un Set est une collection de valeurs uniques, optimisée pour le test d'appartenance .has(x) en O(1). Ici il répond à « ce statut interdit-il l'édition ? ». On pourrait utiliser un tableau + .includes(), mais le Set exprime mieux l'intention (un ensemble, pas une liste ordonnée) et reste O(1) quel que soit le nombre d'éléments.

LangageÉquivalent
Pythonfrozenset({...}) + x in s
Gomap[string]struct{} (idiome set)
JSnew Set([...]) + s.has(x)

La logique métier : une fois qu'un événement est live (ou au-delà), on ne peut plus l'éditer depuis le Hub — il « appartient » à la Borne en cours d'utilisation. Les routes PUT vérifient isFrozen() et répondent 409 si c'est le cas.

Transitions manuelles : une Map

// Transitions manuelles autorisées : draft↔ready uniquement
const MANUAL_TRANSITIONS = new Map([
  ['draft', 'ready'],
  ['ready', 'draft'],
]);
JS Le Map comme table de correspondance

On a déjà vu Map pour le cache LRU (eventStore). Ici il sert de simple table : « depuis tel statut, la seule transition manuelle permise mène à tel autre ». MANUAL_TRANSITIONS.get('draft') renvoie 'ready'. On l'initialise depuis un tableau de paires [clé, valeur].

Pourquoi une Map et pas un objet ? Ici un objet conviendrait. Le choix de Map est cohérent avec le reste du fichier et exprime « correspondance dynamique » plutôt que « structure fixe ». La logique : seules les transitions draft↔ready sont déclenchées à la main par le client ; toutes les autres (loaded, live, pushed…) sont posées automatiquement par la Borne ou le worker.

Vérification dans PUT /:eventId/status :

const allowed = MANUAL_TRANSITIONS.get(event.status);
if (allowed !== status) {
  return res.status(400).json({
    error: `Transition non autorisée : ${event.status} → ${status}. Seules draft↔ready sont manuelles.`,
  });
}

Création d'un événement

router.post('/', requireUser, (req, res, next) => {
  try {
    const { name, event_date } = req.body;
    if (!name || typeof name !== 'string' || !name.trim()) {
      return res.status(400).json({ error: 'name requis' });
    }
    const id = uuidv4();                              // identifiant unique
    const eventDir = join(dataDir, 'events', id);
    mkdirSync(eventDir, { recursive: true });          // crée le dossier de l'événement

    const db = getDb();
    insertEvent(db, { id, owner_id: req.user.sub, name: name.trim(), event_date: event_date ?? null });
    openEventDb(id, dataDir);    // initialise db.sqlite + 4 questions par défaut

    res.status(201).json(getEvent(db, id));
  } catch (err) { next(err); }
});

Trois effets coordonnés : (1) une fiche dans registry.events, (2) un dossier events/<id>/, (3) un db.sqlite initialisé (via openEventDb, qui appelle createEventDb et seede les questions). L'uuidv4() vient du paquet uuid (importé { v4 as uuidv4 }). req.user.sub est l'id du propriétaire, posé par requireUser.

La purge RGPD : DELETE /:eventId

router.delete('/:eventId', requireUser, requireOwner, (req, res, next) => {
  try {
    const event = req.event;
    const { confirm } = req.body;
    if (!confirm || confirm.trim() !== event.name.trim()) {
      return res.status(400).json({ error: 'Confirmation invalide : fournir { confirm: "" }' });
    }

    closeEventDb(event.id);                            // §11.11 : fermer AVANT rm -rf
    const eventDir = join(dataDir, 'events', event.id);
    rmSync(eventDir, { recursive: true, force: true }); // supprime tout le dossier

    const db = getDb();
    updateEvent(db, event.id, { status: 'purged', purged_at: new Date().toISOString() });
    insertSyncLog(db, { event_id: event.id, action: 'purge', detail: { name: event.name } });
    res.json({ ok: true });
  } catch (err) { next(err); }
});
⛔ Deux protections imbriquées sur la purge
  1. Confirmation par le nom : le client doit renvoyer le nom exact de l'événement dans confirm. Empêche une suppression accidentelle (et une CSRF aveugle). Le .trim() des deux côtés tolère les espaces.
  2. §11.11 — closeEventDb avant rmSync : on ferme le handle SQLite avant de supprimer le dossier (voir eventStore). Supprimer un fichier de base encore ouvert laisse SQLite dans un état incohérent.

Après la suppression physique, l'événement reste dans registry.events mais passe en statut purged avec purged_at — on garde la trace qu'il a existé (audit, facturation), sans aucune donnée invité. C'est cohérent avec l'invariant RGPD §11.13 : le registry ne contient toujours pas de donnée personnelle.

JS Petits idiomes : spread dans une réponse, new Date().toISOString()

new Date().toISOString() produit un horodatage UTC normalisé ("2026-06-15T10:30:00.000Z") — le format stocké partout dans les colonnes *_at qu'on remplit côté code (les autres ont DEFAULT CURRENT_TIMESTAMP côté SQLite).

Dans la route GET sync (non montrée ici), la réponse compose plusieurs sources avec le spread : { ...freshEvent, meta } copie tous les champs de freshEvent puis ajoute meta. C'est l'équivalent de {**dict, "meta": meta} en Python.
