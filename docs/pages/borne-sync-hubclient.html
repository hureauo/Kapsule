4 — Le serveur Borne

borne/sync/hubClient.js

Le client HTTP que la Borne utilise pour parler au Hub. Il ajoute le jeton de borne en en-tête, réessaie sur erreur réseau avec un backoff exponentiel, et expose une variante qui parse le JSON et lève sur erreur. C'est la page de référence pour le fetch natif de Node et l'attachement de données à une Error.

hubFetch : fetch + retry réseau

import { config } from '../config.js';

const MAX_ATTEMPTS = 5;
function backoffMs(attempt) {
  // min(2000 · 2^(n-1), 30000) — n commence à 1
  return Math.min(2000 * Math.pow(2, attempt - 1), 30000);
}
function sleep(ms) { return new Promise(resolve => setTimeout(resolve, ms)); }

export async function hubFetch(path, options = {}) {
  const url = `${config.hubUrl}${path}`;
  const headers = { 'X-Box-Token': config.boxToken, ...options.headers };

  // Ne pas poser Content-Type si FormData (multipart géré par fetch)
  if (options.body && typeof options.body === 'string') {
    headers['Content-Type'] = 'application/json';
  }

  let lastError;
  for (let attempt = 1; attempt <= MAX_ATTEMPTS; attempt++) {
    try {
      const res = await fetch(url, { ...options, headers });
      return res;
    } catch (err) {
      lastError = err;
      if (attempt < MAX_ATTEMPTS) await sleep(backoffMs(attempt));
    }
  }
  throw Object.assign(
    new Error(`hubFetch ${path} : ${MAX_ATTEMPTS} tentatives échouées — ${lastError?.message}`),
    { cause: lastError }
  );
}
JS fetch natif (Node 18+)

fetch(url, options) est l'API standard pour faire des requêtes HTTP — la même que dans les navigateurs, désormais intégrée à Node (depuis la version 18, plus besoin du paquet node-fetch). Elle retourne une Promise d'un objet Response. options porte method, headers, body…

Détail subtil : fetch ne rejette pas sur un statut HTTP d'erreur (404, 500…) — il rejette seulement sur une erreur réseau (Hub injoignable, DNS, timeout). C'est pourquoi le try/catch ici n'attrape que les pannes réseau ; les statuts d'erreur HTTP sont gérés séparément dans hubFetchJson (voir plus bas).

JS Backoff exponentiel

En cas d'échec réseau, réessayer immédiatement est contre-productif (le réseau est peut-être saturé). On attend donc de plus en plus longtemps entre les tentatives : backoffMs(n) = min(2000 · 2^(n-1), 30000) donne 2 s, 4 s, 8 s, 16 s, plafonné à 30 s. C'est un backoff exponentiel avec plafond, pattern standard pour les appels réseau résilients. Math.pow(2, n-1) est la puissance de 2 ; Math.min(..., 30000) impose le plafond.

⛔ Le backoff est un invariant du projet

La formule min(2000·2^(n-1), 30000) et les 5 tentatives sont spécifiées dans les invariants (§11.18). On la retrouve identique dans push.js (upload des fichiers) et côté front dans l'upload XHR. C'est volontaire : tout transfert Borne↔Hub utilise la même politique de reprise, pour un comportement prévisible sur réseau instable.

JS Object.assign(new Error(...), { ... }) — enrichir une erreur

Un objet Error n'a par défaut que message et stack. Pour y attacher des données (un code HTTP, une cause…), on utilise Object.assign(cible, source) qui copie les propriétés de source dans cible et retourne cible : 

throw Object.assign(new Error('Hub 409: …'), { status: 409, body });

L'erreur lancée porte alors .status et .body, que l'appelant peut inspecter (if (err.status === 401) …). C'est l'idiome JS pour des « erreurs typées » sans créer de classe d'erreur custom. On le retrouve partout dans le code de synchro.

hubFetchJson : parser et lever sur statut d'erreur

export async function hubFetchJson(path, options = {}) {
  const res = await hubFetch(path, options);
  const body = await res.json().catch(() => ({}));    // parse JSON, {} si corps vide/non-JSON
  if (!res.ok) {                                       // res.ok = statut 200-299
    throw Object.assign(
      new Error(`Hub ${res.status}: ${body.error ?? res.statusText}`),
      { status: res.status, body }
    );
  }
  return body;
}

Cette variante ajoute la couche « statut HTTP » au-dessus de hubFetch : res.ok est true pour 200-299. Si le Hub répond une erreur (4xx/5xx), on lève une Error enrichie de status et body. Le res.json().catch(() => ({})) protège contre une réponse sans corps JSON valide (on retombe sur un objet vide). C'est la fonction qu'utilisent pull.js et push.js pour leurs appels métier.

JS Le spread des en-têtes et le piège FormData

{ 'X-Box-Token': config.boxToken, ...options.headers } : on pose le jeton par défaut, puis on étale les en-têtes fournis par l'appelant (qui peuvent surcharger). Le test if (options.body && typeof options.body === 'string') ne pose Content-Type: application/json que pour un corps texte. Pour un upload FormData (multipart), on laisse fetch gérer le Content-Type lui-même — il y ajoute la « boundary » nécessaire au multipart. Poser manuellement Content-Type sur du FormData casserait l'upload. Piège classique.
