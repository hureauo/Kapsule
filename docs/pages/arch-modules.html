1 — Architecture

ESM : import / export

Kapsule utilise les modules ES (ESM) : la syntaxe import / export. C'est le système de modules standard de JavaScript moderne. Tu connais déjà l'idée (les import de Python, les packages de Go), mais JS a deux systèmes de modules concurrents et il faut savoir lequel on utilise et pourquoi.

JS ESM vs CommonJS — les deux systèmes de modules de Node

Historiquement, Node utilisait CommonJS (CJS) : on importe avec require() et on exporte en assignant à module.exports. C'est encore très répandu. Puis JavaScript a standardisé ESM : import / export, qui est aussi ce qu'utilisent les navigateurs.

CommonJS (ancien)ESM (Kapsule)
Importerconst x = require('m')import x from 'm'
Importer nomméconst {a} = require('m')import { a } from 'm'
Exportermodule.exports = xexport default x
Exporter nomméexports.a = …export const a = …

On active ESM avec "type": "module" dans le package.json (ce que fait Kapsule à la racine — voir Monorepo). Sans ce champ, Node interprète les .js comme du CommonJS.

LangageAnalogie
Pythonfrom module import a ≈ import { a } from './module.js'
Goimport "pkg" puis pkg.Func() ≈ import * as pkg

Différences techniques qui comptent :

  • ESM est statique : les import sont résolus avant l'exécution du corps du fichier, et doivent être au niveau racine (pas dans un if). Pour un import conditionnel, on utilise import() (dynamique, qui renvoie une Promise) — Kapsule s'en sert dans le worker.
  • En ESM, require, module, __dirname, __filename n'existent pas. Pour retrouver le chemin du fichier courant, on utilise import.meta.url (voir Flux de démarrage).
  • Les export ESM sont des liaisons vivantes (live bindings) : si un module exporte let x et le modifie plus tard, les importateurs voient la nouvelle valeur. CommonJS, lui, copie la valeur au moment du require. Ce détail explique une astuce de test dans Kapsule (muter config.allowRegister sur l'objet importé — voir Tests).

Les formes d'import/export utilisées dans Kapsule

Export nommé (le plus courant)

Dans packages/core/src/constants.js :

export const EVENT_STATUS = {
  DRAFT: 'draft',
  READY: 'ready',
  // …
};
export const LIMITS = { /* … */ };

Et on les importe en les nommant entre accolades :

import { LIMITS, STATUS_ORDER } from './constants.js';

Export par défaut

Un module peut avoir un seul export « par défaut ». Kapsule l'utilise par exemple pour le hook React et pour les paquets externes : 

// définition (apps/borne/web/src/hooks/useMediaRecorder.js)
export default function useMediaRecorder({ maxDuration = 60 } = {}) { /* … */ }

// import : pas d'accolades, on choisit le nom
import useMediaRecorder from './hooks/useMediaRecorder.js';
import Database from 'better-sqlite3';   // export par défaut du paquet

Renommage à l'import

Avec as, fréquent pour uuid dans le projet :

import { v4 as uuidv4 } from 'uuid';
// on importe l'export nommé `v4`, qu'on appelle localement `uuidv4`
⚠ Piège venant de Python/Go : l'extension .js est obligatoire

En ESM côté Node, les imports de fichiers locaux doivent inclure l'extension : import './constants.js', pas import './constants'. Node ne « devine » pas l'extension comme le font Python ou les bundlers. Tu verras donc des .js partout dans les imports relatifs du projet. (Les paquets de node_modules, eux, s'importent par leur nom sans extension : import 'express'.)

Pourquoi ESM (et pas CommonJS) dans ce projet ?

  • Cohérence front/back : les fronts React (apps/*/web) utilisent ESM nativement (c'est le standard navigateur). Utiliser ESM aussi côté serveur évite de jongler entre deux syntaxes selon le fichier.
  • C'est la direction de l'écosystème : ESM est le format standardisé, CommonJS est l'héritage. Un projet neuf qui vise Node 20+ n'a pas de raison de partir sur CJS.
  • Imports dynamiques propres : import() permet le chargement paresseux (worker), avec une sémantique claire de Promise.

On revient sur ce choix, et son revers (certaines libs natives s'intègrent plus facilement en CJS), dans Décisions d'architecture.
