5 — Le code front (web)

hub/web client.js

Le client API du front Hub : un module qui centralise tous les appels HTTP vers le serveur. C'est du code navigateur (pas Node) — la première fois qu'on quitte le serveur. Notions clés : fetch côté navigateur, localStorage pour le jeton, et un objet de méthodes fléchées.

Gestion du jeton dans localStorage

const TOKEN_KEY = 'hub_token';
export function getToken() { return localStorage.getItem(TOKEN_KEY); }
export function saveToken(t) { localStorage.setItem(TOKEN_KEY, t); }
export function clearToken() { localStorage.removeItem(TOKEN_KEY); }
export function isAuthenticated() { return !!getToken(); }
JS localStorage — stockage navigateur persistant

localStorage est un stockage clé→valeur (chaînes uniquement) fourni par le navigateur, persistant entre les sessions (survit à la fermeture de l'onglet, contrairement à sessionStorage). On y range le JWT après login ; il est relu à chaque appel API pour authentifier. !!getToken() convertit la valeur (chaîne ou null) en booléen (!! = double négation = « est-ce truthy ? »).

APIEffet
getItem(k)lit (ou null)
setItem(k, v)écrit
removeItem(k)supprime

Pourquoi localStorage et pas un cookie ? Parce que le jeton doit être lu en JS pour être mis dans l'en-tête Authorization (un cookie HttpOnly n'est pas lisible en JS). Le compromis sécurité : localStorage est accessible à tout JS de la page, donc vulnérable au XSS — mais le projet n'a pas de contenu tiers et échappe ses sorties. C'est un choix courant pour les SPA. Le revers : pour les ressources que le navigateur charge seul (<video>, téléchargements), on ne peut pas ajouter d'en-tête, d'où le ?token= (invariant §11.2).

Le wrapper apiFetch

async function apiFetch(path, opts = {}) {
  const token = getToken();
  const headers = { ...(opts.headers ?? {}) };
  if (token) headers['Authorization'] = `Bearer ${token}`;
  if (opts.body && typeof opts.body === 'object' && !(opts.body instanceof FormData)) {
    headers['Content-Type'] = 'application/json';
    opts = { ...opts, body: JSON.stringify(opts.body) };       // objet → JSON
  }
  const res = await fetch(`/api${path}`, { ...opts, headers });
  if (!res.ok) {
    const data = await res.json().catch(() => ({}));
    throw Object.assign(new Error(data.error ?? `HTTP ${res.status}`), { status: res.status });
  }
  if (res.status === 204) return null;                          // No Content
  return res.json();
}
JS fetch côté navigateur + instanceof

Même fetch que côté Node (l'API est commune). Ce wrapper : attache le jeton en Authorization: Bearer …, sérialise automatiquement un corps objet en JSON (sauf si c'est du FormData, qu'on laisse tel quel), gère les erreurs (lève une Error enrichie de status) et le cas 204 (pas de corps).

opts.body instanceof FormData teste si le corps est un objet FormData (upload de fichier). instanceof vérifie le type d'un objet (≈ isinstance Python). On ne sérialise en JSON que les corps objets ordinaires — un FormData doit rester intact pour que le navigateur gère le multipart (même piège que côté Node).

L'objet api : des méthodes fléchées

export const api = {
  login: (email, password) => apiFetch('/auth/login', { method: 'POST', body: { email, password } }),
  listEvents: () => apiFetch('/events'),
  createEvent: (name, event_date) => apiFetch('/events', { method: 'POST', body: { name, event_date } }),
  getEvent: (id) => apiFetch(`/events/${id}`),
  deleteEvent: (id, confirm) => apiFetch(`/events/${id}`, { method: 'DELETE', body: { confirm } }),
  // … une méthode par endpoint …
};
JS Un objet de fonctions fléchées comme « SDK »

api est un objet dont chaque propriété est une fonction fléchée qui appelle apiFetch avec le bon chemin et la bonne méthode. C'est un mini-SDK : le reste du front écrit api.listEvents() au lieu de manipuler des URLs et des en-têtes. Centraliser ainsi les appels rend le code appelant lisible et facilite les changements (un seul endroit à modifier si l'API évolue).

Les fonctions fléchées concises (x) => expr retournent expr sans return ni accolades. Ici chaque méthode est un one-liner qui délègue à apiFetch.

Les URLs avec ?token= (invariant §11.2)

// URL directe avec ?token= pour téléchargements (le navigateur ne peut pas ajouter d'en-tête)
videoStreamUrl: (eventId, videoId) => `/api/events/${eventId}/videos/${videoId}/file?token=${getToken()}`,
videoDownloadUrl: (eventId, videoId) => `/api/events/${eventId}/videos/${videoId}/download?token=${getToken()}`,
csvExportUrl: (eventId) => `/api/events/${eventId}/videos/export/csv?token=${getToken()}`,

Ces méthodes ne font pas de fetch : elles construisent des URLs à mettre dans un <video src>, un <a href> ou un lien CSV. Comme le navigateur charge ces ressources lui-même (sans passer par apiFetch), il ne peut pas ajouter l'en-tête Authorization — d'où le jeton en query (?token=). C'est exactement le besoin que satisfait l'extraction ?token= côté serveur (requireUser). Les deux bouts de l'invariant §11.2 se rejoignent ici.
