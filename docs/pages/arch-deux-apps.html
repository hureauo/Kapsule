1 — Architecture

Deux apps, deux bases SQLite

Kapsule, c'est deux serveurs Node distincts (Hub et Borne) qui ont une structure de code jumelle mais des rôles opposés. Comprendre leur découpage de données est le préalable à tout le reste, parce que la même donnée n'est pas stockée au même endroit selon qu'elle est « annuaire » ou « contenu d'un événement ».

Le principe : registry vs event store

Chaque serveur a deux types de bases SQLite :

BaseCombienContenu
registry.sqliteune seule, globaleL'annuaire : qui/quoi existe. Pas de données invité.
db.sqliteune par événementLe contenu d'un événement : questions, sessions, vidéos.

Les fichiers sont rangés ainsi sur le disque (sous le DATA_DIR) : 

data/
├── registry.sqlite              ← l'annuaire global
└── events/
    ├── <uuid-event-1>/
    │   ├── db.sqlite            ← base de CET événement
    │   ├── videos/             ← fichiers vidéo bruts
    │   │   └── <uuid>.mp4
    │   └── derived/            ← miniatures, archive.zip (Hub)
    └── <uuid-event-2>/
        └── …
⛔ Invariant RGPD (§11.13) : pourquoi cette séparation existe

Aucune donnée invité (prénom, vidéo, session) ne doit se trouver dans registry.sqlite. Tout ce qui est personnel vit dans events/<id>/. Conséquence directe : pour supprimer toutes les données personnelles d'un événement (droit à l'effacement), il suffit de rm -rf events/<id>/ — un seul dossier, atomique. Si une donnée invité fuyait dans le registry, la purge deviendrait incomplète et le RGPD violé. Cet invariant contraint le schéma des deux registry.js.

Hub : ce que contiennent ses bases

registry.sqlite (Hub) — détail :

  • users — les comptes clients et admins (email, hash de mot de passe).
  • box_tokens — les tokens de borne, un par événement (hash + clair du token, event_id, label, location, is_preview) — modèle « token = événement » (§11.20).
  • events — la fiche de chaque événement (nom, propriétaire, statut, dates). Pas les questions ni les vidéos.
  • jobs — la file de traitement (probe, thumbnail, archive).
  • sync_log — journal des synchronisations.

db.sqlite d'un événement (Hub) — schéma défini dans core/eventDbSchema.js :

  • event_meta, questions, sessions, videos, derived.

Borne : ce que contiennent ses bases

registry.sqlite (Borne) — détail, volontairement minimal :

  • local_events — les événements présents localement (id, nom, origine hub/local, statut, lequel est « actif », et is_preview = borne d'essai §11.21).
  • push_state — l'avancement d'un push (quelles vidéos ont déjà été envoyées).

db.sqlite d'un événement (Borne) :

  • Le même schéma que le Hub — c'est tout l'intérêt du package partagé : les deux serveurs appellent createEventDb() de core/eventDbSchema.js. Donc un db.sqlite créé sur la Borne est directement exploitable par le Hub après le push (c'est littéralement le même fichier qui est transféré).
ℹ Pourquoi une base par événement plutôt qu'une grande base ?

Trois raisons : (1) RGPD — la purge est un rm -rf de dossier. (2) Transfert — le push envoie un fichier db.sqlite autonome, pas un export partiel d'une grande base. (3) Isolation — un événement corrompu n'affecte pas les autres. Le coût (plusieurs fichiers SQLite ouverts) est géré par un petit cache LRU côté Hub (eventStore.js) et un cache à une entrée côté Borne (eventDb.js).

La grande différence : le Hub a un worker (traitement vidéo asynchrone après réception) et la Borne a la capture (enregistrement vidéo côté navigateur) + toute la logique de synchronisation sortante. On voit l'enchaînement complet dans Flux complet : pull & push.
