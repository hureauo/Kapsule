Protection : requireUser + requireAdmin

function requireAdmin(req, res, next) {
  if (req.user.role !== 'admin') return res.status(403).json({ error: 'Réservé aux admins' });
  next();
}

router.use(requireUser, requireAdmin) applique ces deux middlewares à toutes les routes déclarées ensuite — pas besoin de les répéter sur chaque route. requireAdmin s'appuie sur req.user.role posé par requireUser : d'où l'ordre obligatoire (user d'abord, admin ensuite).

Créer une borne : un jeton montré une seule fois

router.post('/boxes', (req, res) => {
  const { name } = req.body;
  if (!name || !name.trim()) return res.status(400).json({ error: 'name requis' });

  const token = randomBytes(32).toString('hex');                  // 256 bits aléatoires
  const token_hash = createHash('sha256').update(token).digest('hex');

  const db = getDb();
  if (getBoxByTokenHash(db, token_hash)) {                        // collision quasi impossible
    return res.status(500).json({ error: 'Collision de token, réessayez' });
  }
  const result = insertBox(db, { name: name.trim(), token_hash });
  res.status(201).json({ id: result.lastInsertRowid, name: name.trim(), token });  // token EN CLAIR ici
});
JS randomBytes — générer un secret cryptographique

randomBytes(32) (de node:crypto) génère 32 octets cryptographiquement aléatoires (≠ Math.random(), qui n'est pas sûr). .toString('hex') les encode en 64 caractères hexadécimaux. Le résultat est un jeton imprévisible de 256 bits — impossible à deviner par force brute.

⛔ Le jeton en clair n'est renvoyé qu'à la création

POST /boxes renvoie { id, name, token } avec le jeton en clair — c'est la seule et unique fois qu'il est visible. L'admin doit le copier pour le configurer sur la Borne (BOX_TOKEN). En base, seul token_hash est stocké. GET /boxes ne renvoie jamais le jeton (ni son hash — voir ci-dessous). Si l'admin le perd, il faut recréer une borne. C'est le même principe que les « personal access tokens » de GitHub.

Lister les bornes sans fuiter le hash

router.get('/boxes', (req, res) => {
  const db = getDb();
  const boxes = listBoxes(db).map(({ token_hash: _t, ...b }) => b);   // retire token_hash
  res.json(boxes);
});
JS Retirer un champ par destructuring + rest

({ token_hash: _t, ...b }) => b est une astuce idiomatique : on destructure chaque box en extrayant token_hash (renommé _t, qu'on ignore) et en collectant tout le reste dans b via le rest ...b. On retourne b — donc l'objet sans token_hash. C'est le moyen JS concis de produire « le même objet mais sans tel champ », sans le muter. Le _t préfixé d'un underscore signale « variable volontairement inutilisée » (convention reconnue par les linters).

Pourquoi ne pas juste faire delete box.token_hash ? Parce que ça muterait l'objet renvoyé par better-sqlite3 (effet de bord). La version par destructuring crée un nouvel objet sans le champ — approche immuable, plus sûre. Même si ici l'objet est jetable, c'est une bonne habitude à reconnaître quand tu la croises.

La vue d'ensemble : taille disque par événement

function dirSize(dirPath) {                       // taille récursive d'un dossier
  let total = 0;
  try {
    for (const entry of readdirSync(dirPath, { withFileTypes: true })) {
      const full = join(dirPath, entry.name);
      if (entry.isDirectory()) total += dirSize(full);        // récursion
      else { try { total += statSync(full).size; } catch {} }  // fichier disparu → ignore
    }
  } catch {}                                     // dossier absent → 0
  return total;
}
JS Récursion sur le système de fichiers + withFileTypes

readdirSync(dir, { withFileTypes: true }) liste le contenu d'un dossier en renvoyant des objets Dirent qui savent dire isDirectory() / isFile() — sans avoir à faire un stat séparé sur chacun (plus efficace). La fonction s'appelle elle-même sur les sous-dossiers (récursion) et somme les tailles des fichiers. Les try/catch vides gèrent les races (un fichier supprimé entre la liste et le stat) sans planter le calcul.

GET /overview assemble : tous les événements (jointure avec l'email du propriétaire) + leur taille disque calculée par dirSize, l'espace libre du volume (statfs), les 20 derniers jobs en échec, et les bornes avec leur dernier contact. C'est l'écran « santé de la plateforme » de l'admin.
