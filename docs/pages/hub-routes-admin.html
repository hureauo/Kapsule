3 — Le serveur Hub

hub/routes/admin.js

Les endpoints réservés aux administrateurs : gérer les comptes clients, gérer les tokens de borne (un token par événement, §11.20) et obtenir une vue d'ensemble de la plateforme (tous les événements, l'espace disque, les jobs en échec). Tout le routeur est protégé par un double middleware.

Protection : requireUser + requireAdmin

function requireAdmin(req, res, next) {
  if (req.user.role !== 'admin') return res.status(403).json({ error: 'Réservé aux admins' });
  next();
}

router.use(requireUser, requireAdmin) applique ces deux middlewares à toutes les routes déclarées ensuite — pas besoin de les répéter sur chaque route. requireAdmin s'appuie sur req.user.role posé par requireUser : d'où l'ordre obligatoire (user d'abord, admin ensuite).

Générer un token de borne

// POST /api/admin/events/:id/tokens — génère un token ; token_clear stocké et retourné
router.post('/events/:id/tokens', (req, res) => {
  const db = getDb();
  const event = getEvent(db, req.params.id);
  if (!event) return res.status(404).json({ error: 'Événement introuvable' });

  const { label, location, is_preview } = req.body;
  const token = randomBytes(32).toString('hex');                  // 256 bits aléatoires
  const token_hash = createHash('sha256').update(token).digest('hex');
  const result = insertBoxToken(db, {
    event_id: req.params.id,
    token_hash,
    token_clear: token,                                            // clair conservé en base
    label: label?.trim() ?? null,
    location: location?.trim() ?? null,
    is_preview: is_preview ? 1 : 0,
  });
  res.status(201).json({
    id: result.lastInsertRowid, event_id: req.params.id,
    token_clear: token, label: label?.trim() ?? null,
    location: location?.trim() ?? null, is_preview: is_preview ? 1 : 0,
  });
});

Le token est rattaché à un événement (:id dans l'URL) : c'est le modèle « token = événement » (box_tokens, §11.20). L'événement doit exister (404 sinon). is_preview marque un token d'essai (borne de démo) ; label/location sont descriptifs. L'ancien POST /boxes (créer une borne nommée puis l'assigner) n'existe plus.

JS randomBytes — générer un secret cryptographique

randomBytes(32) (de node:crypto) génère 32 octets cryptographiquement aléatoires (≠ Math.random(), qui n'est pas sûr). .toString('hex') les encode en 64 caractères hexadécimaux. Le résultat est un jeton imprévisible de 256 bits — impossible à deviner par force brute.

ℹ Le jeton en clair reste consultable (décision Phase 6E)

POST /events/:id/tokens renvoie token_clear (le jeton en clair) que l'admin copie pour configurer la Borne (BOX_TOKEN). Contrairement à un « personal access token » GitHub, ce clair n'est pas jeté après la génération : il est stocké en base (colonne token_clear, voir registry) et renvoyé par les routes de lecture admin (GET /events/:id/tokens et GET /tokens). Raison : l'opérateur configure plusieurs Raspberry à des moments différents et doit pouvoir recopier un token sans le régénérer. Le compromis est borné par l'invariant §11.13b : token_clear n'est exposé qu'aux routes admin (jamais aux routes synchro borne ni aux clients), et token_hash reste ce qui sert à l'authentification (requireBox).

Lister, révoquer et renommer les tokens

// GET /api/admin/events/:id/tokens — liste les tokens de l'événement (avec token_clear, sans hash)
router.get('/events/:id/tokens', (req, res) => {
  const db = getDb();
  res.json(listBoxTokensByEvent(db, req.params.id));   // SELECT … token_clear … (pas token_hash)
});

// GET /api/admin/tokens — tous les tokens, tous événements confondus (vue globale onglet Tokens)
router.get('/tokens', (req, res) => {
  res.json(listAllBoxTokens(getDb()));                 // JOIN events → ajoute event_name
});

// DELETE /api/admin/tokens/:tokenId — révocation
router.delete('/tokens/:tokenId', (req, res) => {
  const db = getDb();
  const result = deleteBoxToken(db, req.params.tokenId);
  if (result.changes === 0) return res.status(404).json({ error: 'Token introuvable' });
  res.status(204).end();
});

// PUT /api/admin/tokens/:tokenId — mise à jour label/location
router.put('/tokens/:tokenId', (req, res) => {
  const db = getDb();
  const row = getBoxTokenById(db, req.params.tokenId);
  if (!row) return res.status(404).json({ error: 'Token introuvable' });
  updateBoxToken(db, req.params.tokenId, req.body);
  const updated = getBoxTokenById(db, req.params.tokenId);
  const { token_hash: _, ...safe } = updated;          // retire token_hash de la réponse
  res.json(safe);
});

Deux familles d'URL coexistent : par événement (/events/:id/tokens pour générer/lister, naturel car un token appartient à un événement) et par token (/tokens/:tokenId pour révoquer/renommer, car on agit sur un token précis sans avoir à répéter son événement). À ces deux familles s'ajoute la vue globale GET /tokens (sans :id) : listAllBoxTokens fait une jointure LEFT JOIN events pour ajouter event_name à chaque ligne — c'est ce qu'affiche l'onglet « Tokens » du super-admin (tous les tokens de tous les événements, triés par date). La révocation est une vraie suppression (DELETE) — le hash disparaît, le token devient inutilisable côté Borne (401). updateBoxToken ne laisse modifier que label/location (liste blanche), jamais l'event_id ni is_preview.

JS Retirer un champ par destructuring + rest

const { token_hash: _, ...safe } = updated est une astuce idiomatique : on destructure l'objet en extrayant token_hash (renommé _, qu'on ignore) et en collectant tout le reste dans safe via le rest ...safe. On renvoie safe — donc l'objet sans token_hash. C'est le moyen JS concis de produire « le même objet mais sans tel champ », sans le muter. (Le GET, lui, écarte le hash plus en amont : sa requête SQL ne le sélectionne pas du tout.)

Pourquoi ne pas juste faire delete updated.token_hash ? Parce que ça muterait l'objet renvoyé par better-sqlite3 (effet de bord). La version par destructuring crée un nouvel objet sans le champ — approche immuable, plus sûre. Même si ici l'objet est jetable, c'est une bonne habitude à reconnaître quand tu la croises.

La vue d'ensemble : taille disque par événement

function dirSize(dirPath) {                       // taille récursive d'un dossier
  let total = 0;
  try {
    for (const entry of readdirSync(dirPath, { withFileTypes: true })) {
      const full = join(dirPath, entry.name);
      if (entry.isDirectory()) total += dirSize(full);        // récursion
      else { try { total += statSync(full).size; } catch {} }  // fichier disparu → ignore
    }
  } catch {}                                     // dossier absent → 0
  return total;
}
JS Récursion sur le système de fichiers + withFileTypes

readdirSync(dir, { withFileTypes: true }) liste le contenu d'un dossier en renvoyant des objets Dirent qui savent dire isDirectory() / isFile() — sans avoir à faire un stat séparé sur chacun (plus efficace). La fonction s'appelle elle-même sur les sous-dossiers (récursion) et somme les tailles des fichiers. Les try/catch vides gèrent les races (un fichier supprimé entre la liste et le stat) sans planter le calcul.

GET /overview assemble : tous les événements (jointure avec l'email du propriétaire) + leur taille disque calculée par dirSize, l'espace libre du volume (statfs), les 20 derniers jobs en échec, et tous les tokens de borne (box_tokens : event_id, label, location, is_preview, last_seen_at) avec leur dernier contact. La réponse expose cette liste sous la clé boxes (nom historique conservé côté front). C'est l'écran « santé de la plateforme » de l'admin.
