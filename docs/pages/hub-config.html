3 — Le serveur Hub

hub/config.js

Le plus petit fichier du serveur, mais le premier importé par presque tous les autres. Il lit les variables d'environnement (injectées par Docker) et expose un objet config unique, typé et avec des valeurs par défaut.

Le fichier entier :

const env = process.env;

export const config = {
  port: parseInt(env.PORT ?? '3001', 10),
  jwtSecret: env.JWT_SECRET ?? 'change-me',
  dataDir: env.DATA_DIR ?? '/app/data',
  allowRegister: env.ALLOW_REGISTER === 'true',
  adminEmail: env.ADMIN_EMAIL ?? '',
  adminPassword: env.ADMIN_PASSWORD_HUB ?? '',
};

process.env et l'opérateur ?? sont expliqués en détail dans la page Docker — si ce n'est pas encore lu :

→ notion JS : process.env & nullish coalescing (vue dans arch-docker)

Les réglages

ChampVariable d'envDéfautRôle
portPORT3001Port d'écoute du serveur HTTP.
jwtSecretJWT_SECRET'change-me'Secret de signature des JWT. Doit être changé en prod.
dataDirDATA_DIR'/app/data'Racine de stockage (registry + events). Surchargé en test par un dossier temporaire.
allowRegisterALLOW_REGISTERfalseAutorise (ou non) l'inscription publique via l'API. Voir routes/auth.
adminEmailADMIN_EMAIL'' (vide)E-mail du compte admin seedé au démarrage. Vide = pas de seed.
adminPasswordADMIN_PASSWORD_HUB'' (vide)Mot de passe du compte admin seedé. Vide = pas de seed. Suffixé _HUB (héritage : le nom court ADMIN_PASSWORD servait historiquement à la Borne, désormais retiré au profit d'une auth nominative).

Les deux derniers alimentent le seed d'un compte admin au démarrage du serveur — détaillé dans index.js (seedAdminIfNeeded). Tant qu'une des deux est vide, aucun seed n'a lieu : on retombe alors sur le script create-admin.

Deux conversions de type à noter

  • parseInt(env.PORT ?? '3001', 10) : process.env ne contient que des chaînes. On convertit en entier (base 10). Si PORT est absent, ?? fournit la chaîne '3001' qui est ensuite parsée.
  • env.ALLOW_REGISTER === 'true' : pour un booléen, on compare la chaîne à 'true'. Toute autre valeur (absente, 'false', '1'…) donne false. Conversion booléenne explicite et stricte.
⛔ Le défaut 'change-me' du secret JWT

Si JWT_SECRET n'est pas défini, le secret vaut 'change-me' — connu de tous (c'est dans le code source public). En production, un attaquant pourrait alors forger des jetons valides. Le compose passe ${JWT_SECRET:-change-me} : il faut donc définir un vrai secret côté hôte. Ce défaut n'existe que pour que le projet démarre sans config en développement/test.

JS Un module exporte un singleton

export const config = {…} est évalué une seule fois, au premier import du module. Tous les fichiers qui font import { config } partagent le même objet (les modules ES sont mis en cache par Node). Ce n'est donc pas « relire l'environnement à chaque fois » : c'est un instantané pris au démarrage.

Conséquence exploitée par les tests : comme c'est un objet partagé et mutable, un test peut faire config.allowRegister = true le temps d'une assertion, puis le remettre à false. C'est un effet de bord global (à manier avec prudence) mais pratique pour tester un comportement dépendant de la config sans relancer le serveur. Voir Tests. C'est aussi une illustration des « live bindings » ESM évoqués dans ESM.
