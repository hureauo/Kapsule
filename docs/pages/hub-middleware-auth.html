Ce fichier contient deux middlewares d'authentification : requireUser (vérifie le jeton JWT) et requireOwner (vérifie que l'utilisateur est membre de l'événement ciblé, ou superuser). C'est la page où l'on explique JWT et la vérification de jeton.

Extraction du jeton : header OU query

function extractToken(req) {
  const auth = req.headers.authorization;
  if (auth && auth.startsWith('Bearer ')) return auth.slice(7);   // "Bearer xxx" → "xxx"
  if (req.query.token) return req.query.token;
  return null;
}
⛔ Invariant §11.2 : accepter ?token= en plus du header

Le jeton est cherché d'abord dans l'en-tête Authorization: Bearer … (le standard), puis dans le paramètre d'URL ?token=. Ce second chemin est indispensable : une balise <video src="…/file">, un lien de téléchargement ou un export CSV ouvert par le navigateur ne peuvent pas porter d'en-tête HTTP personnalisé. Le seul moyen d'authentifier ces requêtes est de mettre le jeton dans l'URL. Retirer le support ?token= casserait la lecture vidéo et les téléchargements dans la galerie. Voir client.js qui construit ces URLs.

JS jsonwebtoken — signer et vérifier un JWT

Un JWT (JSON Web Token) est une chaîne signée qui encode des données (ici l'id et le rôle de l'utilisateur). Le serveur le signe à la connexion avec un secret, et le vérifie à chaque requête. Comme la signature dépend du secret (que seul le serveur connaît), un jeton ne peut être ni forgé ni modifié sans invalider la signature. Pas besoin de stocker les sessions côté serveur — le jeton est auto-porteur.

La bibliothèque jsonwebtoken expose deux fonctions :

  • jwt.sign(payload, secret, options) → crée un jeton (voir routes/auth qui fait sign({ sub, role }, …, { expiresIn: '24h' })).
  • jwt.verify(token, secret, options) → vérifie la signature et l'expiration, et retourne le payload décodé ; lève si le jeton est invalide/expiré.

Anatomie d'un JWT : trois parties séparées par des points, header.payload.signature, chacune en base64url. Le header déclare l'algorithme (alg), le payload porte les données (sub = subject/id, role, iat = issued-at, exp = expiration), la signature est le HMAC du header.payload avec le secret. verify recalcule le HMAC et compare. Important : le payload est seulement signé, pas chiffré — il est lisible par quiconque (base64). On n'y met donc jamais de secret, juste un id et un rôle.

requireUser et l'épinglage d'algorithme

export function requireUser(req, res, next) {
  const token = extractToken(req);
  if (!token) return res.status(401).json({ error: 'Token manquant' });
  try {
    req.user = jwt.verify(token, config.jwtSecret, { algorithms: ['HS256'] });
    next();
  } catch {
    res.status(401).json({ error: 'Token invalide ou expiré' });
  }
}
⛔ algorithms: ['HS256'] — défense contre l'attaque « alg:none » (§S5.1)

On épingle explicitement l'algorithme accepté. Sans ce paramètre, certaines implémentations de vérification acceptent le alg déclaré dans le jeton lui-même — or un attaquant peut forger un jeton avec "alg": "none" (aucune signature) ou tenter une confusion d'algorithme (RS256↔HS256). En forçant ['HS256'], tout jeton annonçant un autre algorithme est rejeté. Le projet teste explicitement qu'un jeton alg:none renvoie 401 (voir Tests).

Si la vérification réussit, le payload décodé est attaché à req.user (il contiendra { sub, role, iat, exp }) et next() passe au handler suivant. Sinon, le catch répond 401. Noter le catch {} sans paramètre : on n'a pas besoin de l'objet d'erreur, on sait que c'est « jeton invalide » (syntaxe « optional catch binding »).

requireOwner : le cloisonnement par appartenance

export function requireOwner(req, res, next) {
  const { eventId } = req.params;
  if (!eventId) return res.status(400).json({ error: 'eventId manquant' });
  const db = getDb();
  const event = getEvent(db, eventId);
  if (!event) return res.status(404).json({ error: 'Événement introuvable' });
  if (req.user.role !== 'superuser') {
    const membership = getEventUser(db, { event_id: eventId, user_id: req.user.sub });
    if (!membership) return res.status(403).json({ error: 'Accès interdit' });
  }
  req.event = event;     // mémorise l'événement pour le handler suivant
  next();
}

Ce middleware s'exécute après requireUser (qui a posé req.user) et lit eventId dans l'URL. Règle d'accès : un superuser passe toujours ; sinon, on exige que l'utilisateur soit membre de l'événement — c'est-à-dire qu'une ligne existe dans la table event_users pour ce couple (event_id, user.sub). Pas de notion de « propriétaire unique » au niveau de l'accès : un événement peut avoir plusieurs membres (chacun avec ses rôles), et events.owner_id ne sert qu'à mémoriser le client principal, pas à autoriser. En bonus, le middleware range l'événement déjà chargé dans req.event pour éviter au handler de le relire — un pattern « charger une fois, réutiliser » fréquent dans Express.

⚠ L'ordre requireUser puis requireOwner est obligatoire

requireOwner lit req.user.sub et req.user.role — qui n'existent que si requireUser s'est exécuté avant. C'est pourquoi les routes les déclarent toujours dans cet ordre : router.get('/:eventId', requireUser, requireOwner, handler). Inverser les deux ferait planter requireOwner sur un req.user indéfini.
