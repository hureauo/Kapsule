4 — Le serveur Borne

borne/routes/sessions.js

Une session est le passage d'un invité : il donne son prénom + consentement, puis enregistre des réponses. Ce fichier gère la création de session, la consultation des réponses, et la complétion. Il illustre deux idées importantes : le consentement strict (RGPD) et le capability token (l'UUID de session sert de droit d'accès).

Création de session : consentement obligatoire et strict

router.post('/sessions', (req, res, next) => {       // PUBLIC (kiosque)
  const ctx = requireActiveDb(res);
  if (!ctx) return;
  const { active, db } = ctx;
  const { guest_name, consent } = req.body;

  // Événement clôturé : plus de nouvelles sessions
  if (active.status === 'closed') {
    return res.status(409).json({ error: 'event_closed', message: "L'événement est terminé" });
  }
  // Invariant RGPD : consent doit être exactement true (booléen)
  if (consent !== true) {
    return res.status(400).json({ error: 'Le consentement est obligatoire' });
  }
  const nameErr = validateGuestName(guest_name);
  if (nameErr) return res.status(400).json({ error: nameErr });

  // Passage live si c'est la première session
  const sessionCount = db.prepare('SELECT COUNT(*) as n FROM sessions').get().n;
  if (sessionCount === 0 && active.status === 'loaded') updateEventStatus(active.id, 'live');

  const id = uuidv4();
  db.prepare('INSERT INTO sessions (id, guest_name, consent_at) VALUES (?, ?, CURRENT_TIMESTAMP)')
    .run(id, guest_name.trim());
  res.status(201).json(db.prepare('SELECT * FROM sessions WHERE id=?').get(id));
});
⛔ consent !== true : l'égalité stricte protège le RGPD

On exige consent === true (testé via !== true) — le booléen exact, pas une valeur « truthy ». Un consent: "yes", consent: 1 ou consent: "true" (chaîne) sont refusés. Pourquoi cette rigueur ? Parce que le consentement RGPD doit être un acte explicite et non ambigu. Accepter une valeur floue affaiblirait la preuve de consentement. La date consent_at est posée par SQLite (CURRENT_TIMESTAMP) — on conserve quand l'invité a consenti.

JS Égalité stricte === vs lâche ==

JS a deux égalités : == (lâche, avec conversion de type) et === (stricte, sans conversion). 1 == true est true (!), mais 1 === true est false. Toujours utiliser === — c'est la règle du projet, et c'est ce qui rend consent !== true fiable. Le == est une source de bugs notoire en JS (les règles de conversion sont contre-intuitives).

ExpressionRésultat
1 == truetrue (conversion)
1 === truefalse (types différents)
"" == falsetrue (piège !)

La machine à états : loaded → live automatique

Quand la première session est créée sur un événement loaded, il passe automatiquement live : 

if (sessionCount === 0 && active.status === 'loaded') updateEventStatus(active.id, 'live');

C'est une transition déclenchée par l'usage, pas par l'admin : dès qu'un invité commence, l'événement est « en cours ». Ce live sera ensuite remonté au Hub via les heartbeats. La clôture (closed), elle, est manuelle (PUT /events/:id/close) ou via le heartbeat.

Le capability token : l'UUID de session = droit d'accès

// Le UUID de session fait office de capability token — pas besoin d'auth supplémentaire
router.get('/sessions/:id/answers', (req, res, next) => {
  const ctx = requireActiveDb(res);
  if (!ctx) return;
  const { db } = ctx;
  const session = db.prepare('SELECT id FROM sessions WHERE id=?').get(req.params.id);
  if (!session) return res.status(404).json({ error: 'Session introuvable' });
  const answers = db.prepare('SELECT question_id, id as video_id, recorded_at FROM videos WHERE session_id=?').all(req.params.id);
  res.json(answers);
});
ℹ Qu'est-ce qu'un « capability token » ?

Ces routes sont publiques (pas de auth) — un invité n'a pas de compte. Comment protéger l'accès aux réponses d'une session ? Par l'UUID de session lui-même : il est aléatoire (impossible à deviner), et le connaître est le droit d'accéder à cette session. C'est le principe de la capability : « posséder la référence = avoir le droit ». L'invité reçoit son UUID à la création de session et l'utilise pour revoir/compléter ses réponses, sans authentification classique. C'est adapté à un kiosque où il n'y a pas de login invité. Même principe que les liens « secrets » de partage (Google Docs, etc.).

JS Le helper requireActiveDb et le retour null

Toutes les routes commencent par const ctx = requireActiveDb(res); if (!ctx) return;. Ce helper local renvoie { active, db } si un événement est actif, ou répond 404 et renvoie null sinon. Le pattern « le helper répond et signale par null » évite de répéter la vérification dans chaque route. Le const { active, db } = ctx est un destructuring d'objet pour récupérer les deux valeurs.
