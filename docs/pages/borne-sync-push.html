4 — Le serveur Borne

borne/sync/push.js — séquence push

Le push : envoyer un événement clôturé vers le Hub (vidéos + base). C'est la pièce de synchronisation la plus riche. On y voit la séquence en 5 étapes, un état module partagé pour la progression, la lecture d'un fichier avec for await, la construction de FormData/Blob, et la gestion d'erreur avec finally. Le côté réception est dans hub/routes/sync.js.

L'état partagé de progression

const _state = { running: false, total: 0, done: 0, currentFile: null, lastError: null };
export function getPushState() { return { ..._state }; }   // copie défensive

export function _setPushRunning(v) { _state.running = v; }  // test-only
JS Un objet module-level comme état partagé

Le push tourne en tâche de fond ; comment le client connaît-il sa progression ? Via _state, un objet au niveau du module (singleton, comme _db dans registry.js). Le push le met à jour au fil de l'eau (_state.done++, _state.currentFile = …), et GET /sync/status le lit via getPushState().

getPushState() renvoie { ..._state } — une copie, pas la référence. Ainsi l'appelant ne peut pas modifier l'état interne par accident, et il obtient un instantané cohérent. C'est une « copie défensive » : pattern utile dès qu'on expose un état mutable interne.

_setPushRunning est exporté uniquement pour les tests (forcer le flag pour vérifier les gardes qui en dépendent, comme « 409 si push déjà en cours »). Le préfixe _ signale « interne, ne pas utiliser en prod ».

La séquence en 5 étapes

export async function pushEvent(eventId, dataDir) {
  // … vérifie event.status === 'closed' …

  // Marquer running AVANT tout await (synchrone) pour que les gardes voient l'état tout de suite
  _state.running = true; _state.total = 0; _state.done = 0; _state.currentFile = null; _state.lastError = null;

  try {
    // ── 1. Checkpoint WAL + sha256 de chaque vidéo + du db.sqlite ──
    const edb = new Database(dbPath, { readonly: true });
    const videos = edb.prepare('SELECT id, filename, size, checksum FROM videos').all();
    edb.close();
    const dbChecksum = await checkpointAndHash(dbPath);     // §11.8 : checkpoint AVANT hash
    const { size: dbSize } = statSync(dbPath);

    // ── 2. POST manifest → liste des fichiers manquants ──
    await hubFetchJson(`/api/sync/events/${eventId}/status`, { method: 'POST', body: JSON.stringify({ status: 'closed' }) }).catch(() => {});
    const { missing } = await hubFetchJson(`/api/sync/events/${eventId}/manifest`, { method: 'POST', body: JSON.stringify(manifest) });

    // ── 3. Upload des vidéos manquantes ──
    _state.total = missing.length;
    for (const videoId of missing) {
      const video = videos.find(v => v.id === videoId);
      if (!video) continue;
      _state.currentFile = video.filename;
      await uploadFileWithRetry(`/api/sync/events/${eventId}/files/${videoId}`, join(videosDir, video.filename), video.filename);
      registry.prepare('UPDATE push_state SET uploaded_at = CURRENT_TIMESTAMP WHERE event_id = ? AND video_id = ?').run(eventId, videoId);
      _state.done++;
    }

    // ── 4. Upload du db.sqlite ──
    _state.currentFile = 'db.sqlite';
    await uploadFileWithRetry(`/api/sync/events/${eventId}/db`, dbPath, 'db.sqlite');

    // ── 5. Finalize + statut local ──
    await hubFetchJson(`/api/sync/events/${eventId}/finalize`, { method: 'POST' });
    updateEventStatus(eventId, 'pushed');
    registry.prepare('UPDATE local_events SET pushed_at = CURRENT_TIMESTAMP … WHERE id = ?').run(eventId);

  } catch (err) {
    const msg = err.status === 401 ? 'Token borne révoqué…' : (err.message ?? 'Erreur inconnue');
    _state.lastError = { message: msg, status: err.status ?? null };
    throw err;
  } finally {
    _state.running = false;                                 // TOUJOURS remettre à false
  }
}
⛔ _state.running = true AVANT le premier await

On positionne running = true de façon synchrone, tout en haut, avant le moindre await. Pourquoi ? Parce qu'un second appel à POST /sync/push (ou un GET /sync/status) peut arriver immédiatement après le lancement. Si on attendait le premier await pour marquer running, il y aurait une fenêtre où deux pushs pourraient démarrer en parallèle (le verrou n'est pas encore posé). En le posant avant tout point de suspension, on garantit que la garde if (state.running) return 409 (dans routes/sync.js) voit l'état correct dès le départ. C'est une subtilité de concurrence propre au modèle async.

⛔ §11.8 : checkpoint WAL avant de hasher/envoyer le db.sqlite

L'étape 1 appelle checkpointAndHash qui fait db.pragma('wal_checkpoint(TRUNCATE)') avant de calculer le checksum. Rappel : en mode WAL, les dernières écritures vivent dans le fichier -wal séparé. Sans checkpoint, on hasherait (et enverrait) un db.sqlite incomplet. Le checkpoint replie le WAL dans le fichier principal, garantissant que le fichier envoyé contient toutes les données. Voir eventDbSchema (WAL).

JS Le bloc try / catch / finally

La séquence est dans un try, avec :

  • catch (err) : on enregistre l'erreur dans _state.lastError (pour que /sync/status l'affiche, ex. « token révoqué » sur un 401), puis on relance (throw err) — le .catch(()=>{}) de l'appelant l'absorbera.
  • finally : _state.running = false quoi qu'il arrive — succès, erreur, ou exception. C'est crucial : si running restait à true après un échec, plus aucun push ne pourrait jamais être lancé (la garde 409 bloquerait à vie). Le finally est la garantie de libération du verrou.

L'upload d'un fichier : for await + FormData/Blob

async function uploadFileWithRetry(path, filePath, filename) {
  const url = `${config.hubUrl}${path}`;
  for (let attempt = 1; attempt <= MAX_ATTEMPTS; attempt++) {
    try {
      const form = new FormData();
      const chunks = [];
      for await (const chunk of createReadStream(filePath)) chunks.push(chunk);   // lit le fichier
      const blob = new Blob(chunks);
      form.append('file', blob, filename);

      const res = await globalThis.fetch(url, { method: 'PUT', headers: { 'X-Box-Token': config.boxToken }, body: form });
      if (!res.ok) { /* … lève une Error enrichie de status … */ }
      return await res.json();
    } catch (err) {
      if (err.status >= 400 && err.status < 500) throw err;   // erreur client → ne pas réessayer
      if (attempt < MAX_ATTEMPTS) await sleep(backoffMs(attempt));
    }
  }
  throw Object.assign(new Error(`upload ${path} : ${MAX_ATTEMPTS} tentatives échouées …`), { cause: lastErr });
}
JS for await…of et FormData/Blob

for await (const chunk of createReadStream(filePath)) lit un stream morceau par morceau avec une boucle asynchrone — la version « pull » de la lecture par événements vue dans checksum.js. Chaque itération attend le prochain chunk. On accumule les chunks, puis on les emballe dans un Blob (un objet « données binaires » du standard web). FormData construit un corps multipart/form-data : form.append('file', blob, filename) ajoute le fichier sous le champ file (celui que multer côté Hub attend via .single('file')).

On passe body: form à fetch sans poser de Content-Type : fetch détecte le FormData et génère le bon en-tête multipart (avec boundary). Voir le piège FormData dans hubClient.js.

⚠ Ne pas réessayer sur erreur client (4xx)

Dans le catch : if (err.status >= 400 && err.status < 500) throw err;. Une erreur 4xx (ex. 422 checksum mismatch, 409 mauvais statut) vient d'un problème côté requête — réessayer à l'identique donnerait le même résultat. On relance donc immédiatement sans retry. En revanche, une 5xx ou une panne réseau peut être transitoire → on applique le backoff. Distinguer « erreur permanente » de « erreur transitoire » est la clé d'une politique de retry correcte.

Pourquoi le push est reprenable

Si le push échoue (réseau coupé) à la 3ᵉ vidéo sur 10, relancer POST /sync/push/:eventId recommence la séquence : le manifest (étape 2) demande au Hub ce qui lui manque encore, et le Hub répond les 7 vidéos restantes (il a gardé les 3 premières). On n'ré-uploade pas ce qui est déjà transféré. C'est l'invariant §11.12 côté Hub (le Hub recalcule missing) combiné à la table push_state locale. Détail complet dans Flux push/pull.
