3 — Le serveur Hub

hub/worker/index.js — file de jobs

Après qu'un événement est poussé, il faut traiter les vidéos : les sonder (durée, dimensions), générer des miniatures, créer l'archive ZIP. Ces tâches sont lourdes (ffmpeg) et asynchrones — on ne les fait pas dans le handler HTTP. Le worker est un processus séparé qui dépile en boucle les jobs de la table jobs. C'est la page de référence pour la boucle de traitement, l'import dynamique, et le « claim » atomique.

La boucle principale

const POLL_IDLE_MS = 5000;   // attente si aucun job
const POLL_BUSY_MS = 500;    // pause entre deux jobs (laisse respirer la DB)

export async function loop(dataDir) {
  const db = getDb();
  recoverOrphans(db);                          // au démarrage : récupère les jobs crashés
  console.log('[worker] démarré, en attente de jobs…');

  while (true) {                               // boucle infinie
    const job = claimNextJob(db);              // prend un job (atomique)
    if (job) {
      await processJob(db, job, dataDir);
      await sleep(POLL_BUSY_MS);
    } else {
      await sleep(POLL_IDLE_MS);               // rien à faire → on attend plus longtemps
    }
  }
}
JS while (true) + await sleep() = polling

C'est un worker par scrutation (polling) : il interroge la base en boucle. La boucle est async et chaque tour fait await sleep(ms) — où sleep est une mini-Promise sur setTimeout : 

function sleep(ms) { return new Promise((r) => setTimeout(r, ms)); }

Pourquoi ça ne « bloque » pas le processus ? Parce que await sleep() rend la main à la boucle d'événements pendant l'attente (voir async/await). Le setTimeout(r, ms) programme la résolution de la Promise après ms, sans occuper le CPU. Les deux délais (5 s à vide, 0,5 s entre jobs) évitent de marteler la base SQLite quand il n'y a rien à faire.

Pourquoi du polling plutôt qu'une vraie file (BullMQ, Redis, RabbitMQ) ? Parce que c'est simple et sans dépendance externe. La table jobs dans SQLite est la file. Pour la charge attendue (quelques événements, quelques dizaines de vidéos), un poll toutes les 5 s est largement suffisant et évite d'ajouter un Redis à déployer. C'est un choix d'architecture assumé — voir Décisions. Le compromis : une latence jusqu'à 5 s avant qu'un nouveau job soit pris. Acceptable ici.

Le « claim » atomique

export function claimNextJob(db) {
  return db.transaction(() => {
    const job = db.prepare(`SELECT * FROM jobs WHERE status = 'pending'
                            ORDER BY created_at ASC LIMIT 1`).get();
    if (!job) return null;
    db.prepare(`UPDATE jobs SET status = 'running', started_at = CURRENT_TIMESTAMP,
                attempts = attempts + 1 WHERE id = ?`).run(job.id);
    return job;
  })();
}
⛔ Pourquoi le SELECT + UPDATE est dans une transaction

« Prendre un job » = le lire et le marquer running. Si ces deux étapes n'étaient pas atomiques, deux workers (ou deux itérations concurrentes) pourraient lire le même job pending avant que l'un le marque running → double traitement. La transaction() garantit que le SELECT et l'UPDATE forment un tout indivisible. Comme better-sqlite3 est synchrone, aucune autre opération ne peut s'intercaler entre les deux — la transaction est réellement atomique. Le projet actuel ne lance qu'un worker, mais ce verrouillage rend le design correct même avec plusieurs.

Récupération après crash

export function recoverOrphans(db) {
  const result = db.prepare(
    "UPDATE jobs SET status = 'pending', started_at = NULL WHERE status = 'running'"
  ).run();
  if (result.changes > 0) console.log(`[worker] ${result.changes} job(s) orphelin(s) remis en pending`);
}

Si le worker crashe pendant un job, ce job reste running à jamais (personne ne le finira). Au redémarrage, recoverOrphans repasse tous les running en pending — ils seront retraités. C'est une récupération simple et robuste : on part du principe qu'au démarrage, aucun job ne devrait légitimement être running (le worker vient de démarrer). result.changes indique combien de lignes ont été modifiées.

L'import dynamique des handlers

let _handlers = null;
async function getHandlers() {
  if (!_handlers) {
    const [{ runProbe }, { runThumbnail }, { runArchive }] = await Promise.all([
      import('./jobs/probe.js'),
      import('./jobs/thumbnail.js'),
      import('./jobs/archive.js'),
    ]);
    _handlers = { probe: runProbe, thumbnail: runThumbnail, archive: runArchive };
  }
  return _handlers;
}
JS import() dynamique + Promise.all

Au lieu d'un import statique en tête de fichier, on charge les handlers à la demande avec import('./jobs/probe.js'). Contrairement à l'import classique (statique, résolu au chargement), import() est une fonction qui retourne une Promise — on peut donc l'appeler n'importe où, et différer le chargement. Le commentaire du code l'explique : ça évite de bloquer le démarrage si une dépendance optionnelle (comme archiver) n'est pas installée.

Promise.all([...]) lance les trois imports en parallèle et attend qu'ils soient tous résolus. Le const [{ runProbe }, …] = await Promise.all(...) combine destructuring de tableau (les 3 résultats) et destructuring d'objet (extraire runProbe de chaque module). _handlers est mémoïsé : les imports n'ont lieu qu'une fois.

FormeQuand
import statiquerésolu au chargement du module, en haut du fichier
import() dynamiquerésolu à l'exécution, retourne une Promise, chargement paresseux

Traiter un job et marquer l'événement processed

// dans processJob : succès
db.prepare(`UPDATE jobs SET status = 'done', finished_at = CURRENT_TIMESTAMP, error = NULL WHERE id = ?`).run(job.id);
maybeMarkProcessed(db, job.event_id);

// maybeMarkProcessed : si plus aucun job non-'done' pour cet événement → events.status = 'processed'
const pending = db.prepare(`SELECT COUNT(*) AS n FROM jobs WHERE event_id = ? AND status NOT IN ('done')`).get(eventId);
if (pending.n === 0) {
  db.prepare(`UPDATE events SET status = 'processed', processed_at = CURRENT_TIMESTAMP
              WHERE id = ? AND status = 'pushed'`).run(eventId);
}

Chaque fois qu'un job se termine, on vérifie s'il restait des jobs à faire pour cet événement. Quand le dernier passe done, l'événement bascule pushed → processed : toutes ses vidéos sont sondées, ses miniatures faites, son archive prête. La galerie devient pleinement exploitable. Si un job échoue, il passe failed avec le message d'erreur (tronqué à 500 caractères) — visible dans overview.
