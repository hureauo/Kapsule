4 — Le serveur Borne

borne/eventDb.js — handle unique

L'équivalent Borne de eventStore.js du Hub — mais radicalement plus simple. Là où le Hub gère un cache LRU de 10 bases (il sert plusieurs événements), la Borne n'a qu'un événement actif à la fois. Son cache est donc à une seule entrée.

Le fichier entier :

import { join } from 'node:path';
import { createEventDb } from '@kapsule/core/src/eventDbSchema.js';

let _cached = null;   // { id, db } — une seule entrée

export function getActiveEventDb(dataDir, activeEvent) {
  if (!activeEvent) {            // plus d'événement actif → on ferme
    closeEventDb();
    return null;
  }
  if (_cached && _cached.id === activeEvent.id) {
    return _cached.db;           // même événement qu'avant → réutilise
  }
  closeEventDb();                // événement différent → ferme l'ancien
  const dbPath = join(dataDir, 'events', activeEvent.id, 'db.sqlite');
  const db = createEventDb(dbPath);
  _cached = { id: activeEvent.id, db };
  return db;
}

export function closeEventDb() {
  if (_cached) {
    _cached.db.close();
    _cached = null;
  }
}

La logique

Une seule variable de module _cached mémorise { id, db }. À chaque appel de getActiveEventDb :

  • Pas d'événement actif → on ferme le handle courant et on renvoie null.
  • Même événement que la dernière fois → on renvoie le handle déjà ouvert (pas de réouverture).
  • Événement différent → on ferme l'ancien handle, on ouvre le nouveau, on le mémorise.
ℹ Pourquoi un cache à une entrée suffit (vs LRU côté Hub)

Le kiosque ne sert qu'un événement — l'actif. Toutes les routes publiques (sessions, vidéos, questions) passent par getActiveEventDb(dataDir, getActiveEvent()). Il n'y a donc jamais besoin de plusieurs bases ouvertes en même temps. Quand l'admin change d'événement actif (activate), le handle de l'ancien est fermé et celui du nouveau ouvert. C'est l'illustration parfaite de « dimensionner la structure de données au besoin réel » : même problème que le Hub, solution dix fois plus simple parce que la contrainte est différente.

⛔ closeEventDb et l'invariant §11.11

Comme côté Hub, closeEventDb() doit être appelé avant de supprimer le dossier d'un événement (purge). On le retrouve dans routes/sync.js (purge) juste avant le rmSync. Subtilité : si l'événement purgé est encore l'actif, son handle est ouvert — d'où l'appel explicite à closeEventDb() avant la suppression physique.
