2 — Le package partagé

core/index.js — le « barrel »

packages/core est le code partagé entre le Hub et la Borne : constantes, fonctions de validation, schéma de la base d'événement, calcul de checksum. Son fichier index.js est minuscule mais structurant — c'est le point d'entrée du package.

Le fichier complet :

export * from './constants.js';
export * from './validate.js';
// eventDbSchema.js uses better-sqlite3 (native module) — server-only, not exported from the barrel
// checksum.js uses node:crypto + node:fs — server-only, not exported from the barrel
JS Le pattern « barrel » et export *

Un barrel est un fichier qui ne fait que ré-exporter le contenu d'autres fichiers, pour offrir un point d'import unique. export * from './x.js' signifie « réexporte tous les exports nommés de x.js ». Résultat : les autres workspaces écrivent import { LIMITS, validateQuestion } from '@kapsule/core' sans savoir dans quel fichier précis chaque chose est définie.

LangageAnalogie

Goregrouper plusieurs fichiers dans le même package (l'API du package est l'union des fichiers)

Quand import { X } from '@kapsule/core' est résolu, Node lit le champ "main" (ou "exports") du package.json de core, qui pointe vers ce index.js.

Attention au revers du barrel : export * ne combine que les exports nommés, pas les export default. Et si deux fichiers réexportés exposent le même nom, il y a conflit. Ici ce n'est pas un souci (noms distincts), mais c'est pourquoi les barils restent simples.

Autre subtilité : importer le barrel charge tous les modules qu'il réexporte. C'est précisément la raison pour laquelle eventDbSchema.js et checksum.js sont volontairement absents du barrel (voir ci-dessous) : les inclure ferait charger better-sqlite3 (binaire natif) et node:crypto partout — y compris dans le code navigateur qui n'en a pas besoin et ne peut même pas les exécuter.

Ce que le barrel exporte… et ce qu'il cache exprès

FichierDans le barrel ?Pourquoi
constants.js✅ ouiJS pur, utilisable partout (serveur ET navigateur).
validate.js✅ ouiJS pur, fonctions de validation partageables front/back.
eventDbSchema.js❌ nonDépend de better-sqlite3 (natif, serveur uniquement).
checksum.js❌ nonDépend de node:crypto + node:fs (serveur uniquement).

Les deux fichiers « server-only » restent importables, mais par leur chemin direct : 

// le barrel — pour le code partageable
import { LIMITS, validateGuestName } from '@kapsule/core';

// chemin direct — pour le code serveur uniquement
import { createEventDb } from '@kapsule/core/src/eventDbSchema.js';
import { sha256File }   from '@kapsule/core/src/checksum.js';
ℹ La leçon de conception ici

Le barrel sépare le code isomorphe (qui tourne aussi bien dans Node que dans un navigateur — les constantes, la validation) du code server-only (qui a besoin de modules Node natifs). C'est une frontière nette : si tu ajoutes un utilitaire à core, demande-toi « peut-il tourner dans un navigateur ? ». Si oui → barrel. Si non (il importe un node:… ou un module natif) → chemin direct, hors barrel.
