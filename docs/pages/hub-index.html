3 — Le serveur Hub

hub/index.js — montage Express

Le chef d'orchestre du serveur : il crée l'application Express, branche tous les routeurs dans le bon ordre, installe le gestionnaire d'erreurs, et (si lancé directement) démarre l'écoute. C'est la page de référence pour Express, la chaîne de middleware, et le cycle req/res/next.

JS Express — le framework HTTP

Express est le framework web minimaliste de Node : il fait correspondre des routes (méthode + chemin) à des fonctions de traitement, via une chaîne de middlewares. C'est l'équivalent de Flask (Python), Gin (Go) ou Ktor (Kotlin), en plus dépouillé : Express ne fournit presque rien par défaut (pas d'ORM, pas de validation) — tout est middleware.

L'objet central est créé par express() :

const app = express();
app.use(express.json());            // middleware global
app.use('/api/auth', monRouteur);   // routeur monté sous un préfixe
app.get('/api/health', handler);    // route directe
app.listen(3001);                   // démarre l'écoute

JS La chaîne de middleware : req, res, next

Un middleware est une fonction (req, res, next). À chaque requête, Express les exécute dans l'ordre où ils ont été déclarés, en passant les mêmes objets req (requête) et res (réponse) de l'un à l'autre. Chaque middleware a trois choix :

  • répondre lui-même (res.json(...), res.status(...).end()) → la chaîne s'arrête ;
  • appeler next() → passe au middleware suivant ;
  • appeler next(err) → saute directement au gestionnaire d'erreurs.

Ce que contiennent ces objets :

  • req : req.params (paramètres d'URL :id), req.query (?token=…), req.body (corps JSON parsé), req.headers, et tout ce que les middlewares précédents y ont ajouté (req.user, req.event, req.box…).
  • res : pour construire la réponse — res.status(n), res.json(obj), res.setHeader(...), res.send(...).
  • next : la fonction qui passe la main.

« Attacher des données à req » (comme req.user = … dans requireUser) est le mécanisme de communication entre middlewares d'une même requête. Comme tous reçoivent la même référence d'objet req, une propriété ajoutée par l'un est visible par les suivants. C'est l'équivalent de l'objet g de Flask ou du context.Context de Go, mais sans cérémonie : on assigne simplement une propriété.

Le corps de createApp

export function createApp(dataDir, opts = {}) {
  openRegistry(dataDir);
  const app = express();
  app.set('trust proxy', 1);                        // 0. Hub derrière Nginx (un seul reverse proxy)
  app.use(express.json());                          // 1. parse le JSON entrant

  app.use('/api/auth', makeAuthRouter());           // 2. routeurs, DANS L'ORDRE
  app.use('/api/events', makeEventsRouter(dataDir));
  app.use('/api/events/:eventId/questions', makeQuestionsRouter(dataDir));
  app.use('/api/admin', makeAdminRouter(dataDir));
  app.use('/api/sync', makeSyncRouter(dataDir, opts.sync));
  app.use('/api/events/:eventId', makeGalleryRouter(dataDir));   // 3. APRÈS questions !

  app.get('/api/health', async (req, res, next) => { /* … */ });

  app.use((err, req, res, next) => { /* gestionnaire d'erreurs */ });   // 4. EN DERNIER
  return app;
}
⛔ L'ordre de montage des routeurs compte

Express teste les routes dans l'ordre de déclaration et s'arrête à la première qui correspond. Conséquences visibles ici :

  • /api/events/:eventId/questions est monté avant /api/events/:eventId (la galerie). Si la galerie était déclarée avant, elle pourrait intercepter des chemins destinés aux questions. On va du plus spécifique au plus général.
  • Le gestionnaire d'erreurs est tout en bas : Express ne l'utilise que pour les next(err), et il doit être enregistré après toutes les routes pour les couvrir toutes.

Ce principe se décline en interne dans chaque routeur avec l'invariant §11.1 : les routes à segment fixe (/export/csv, /reorder/batch) doivent être déclarées avant les routes paramétrées /:id, sinon Express prend "export" ou "reorder" pour un :id. Voir gallery.js et questions.js.

Routeurs imbriqués et :eventId partagé

app.use('/api/events/:eventId/questions', makeQuestionsRouter(...)) monte un routeur sous un chemin qui contient déjà un paramètre :eventId. Pour que le routeur enfant voie ce paramètre, il doit être créé avec Router({ mergeParams: true }) — détaillé dans questions.js. C'est ainsi qu'on factorise « toutes les routes questions d'un événement » sans répéter :eventId partout.

Le gestionnaire d'erreurs : 4 arguments

app.use((err, req, res, next) => {
  // Erreurs multer (fichier trop gros) → statut explicite plutôt que 500
  if (err.name === 'MulterError') {
    const status = err.code === 'LIMIT_FILE_SIZE' ? 413 : 400;
    return res.status(status).json({ error: `Upload refusé : ${err.message}` });
  }
  const status = err.status ?? err.statusCode ?? 500;
  if (status >= 500) {
    console.error(`[hub] ${req.method} ${req.path} →`, err);   // on logge le détail serveur
    return res.status(status).json({ error: 'Erreur interne du serveur' });  // message opaque
  }
  res.status(status).json({ error: err.message ?? 'Erreur interne' });
});
JS Le gestionnaire d'erreurs Express se reconnaît à ses 4 paramètres

Express distingue un gestionnaire d'erreurs d'un middleware normal par le nombre de paramètres : une fonction (err, req, res, next) à quatre arguments est traitée comme handler d'erreur. Express ne l'appelle que lorsqu'un middleware a fait next(err) (ou levé dans un handler synchrone).

C'est pourquoi tous les handlers async du projet sont écrits try { … } catch (err) { next(err); } : une exception attrapée est réinjectée dans la chaîne via next(err), qui la route jusqu'ici. C'est le point de collecte unique des erreurs.

Pourquoi ce try/catch + next(err) est nécessaire : Express (version utilisée ici) n'attrape pas automatiquement les rejets de Promise dans un handler async. Si un await lève et qu'on ne l'attrape pas, l'erreur devient un « unhandled rejection » et la requête reste pendante (le client attend indéfiniment). D'où la discipline systématique du projet. On garde aussi // eslint-disable-next-line no-unused-vars au-dessus du handler : le paramètre next est inutilisé mais doit figurer pour qu'Express compte 4 arguments.

💡 Sécurité : message opaque pour les 5xx (§S5.3)

Quand le statut est ≥ 500, on logge le détail côté serveur (console.error) mais on renvoie au client un message générique « Erreur interne du serveur ». Cela évite de divulguer des détails d'implémentation (chemins, requêtes SQL, stack) à un attaquant. Les erreurs < 500 (4xx, fautes du client) gardent leur message, qui est utile et non sensible. Même logique côté Borne.

ℹ trust proxy : Express derrière Nginx

En production le Hub tourne derrière Nginx (terminaison TLS, fichiers statiques) qui relaie vers le backend Express. app.set('trust proxy', 1) dit à Express de faire confiance à un reverse proxy : il lit alors X-Forwarded-For / X-Forwarded-Proto pour reconstituer l'IP cliente réelle et le protocole d'origine (req.protocol renvoie https et non http). C'est ce que consomme express-rate-limit (limiter par vraie IP, pas par celle du proxy) et la construction des liens d'enregistrement `${req.protocol}://${req.get('host')}/register?token=…` dans PUT /events/:id/owner. Le 1 (et non true) borne la confiance à un seul saut : un client ne peut pas usurper son IP en injectant lui-même un X-Forwarded-For.

Le seed d'un compte admin au démarrage

async function seedAdminIfNeeded() {
  if (!config.adminEmail || !config.adminPassword) return;     // seed désactivé si l'un est vide
  const db = getDb();
  if (getUserByEmail(db, config.adminEmail)) return;           // déjà présent → idempotent
  const password_hash = await argon2.hash(config.adminPassword, { type: argon2.argon2id });
  insertUser(db, { email: config.adminEmail, password_hash, role: 'superuser' });
  console.log(`[hub] compte admin créé : ${config.adminEmail}`);
}

Au premier déploiement, le Hub n'a aucun compte — il faudrait lancer create-admin manuellement. seedAdminIfNeeded automatise ce cas pour un déploiement Docker : si ADMIN_EMAIL et ADMIN_PASSWORD_HUB sont fournis (config) et qu'aucun compte n'existe encore pour cet e-mail, il crée un admin avec le mot de passe haché par argon2. C'est idempotent : le garde getUserByEmail évite de recréer le compte (ou d'écraser un mot de passe changé depuis) à chaque redémarrage. Le script create-admin reste utile pour créer d'autres admins ou en interactif.

Le démarrage (rappel)

if (process.argv[1] === new URL(import.meta.url).pathname) {
  mkdirSync(config.dataDir, { recursive: true });
  const app = createApp(config.dataDir);
  seedAdminIfNeeded().then(() => {                              // seed AVANT d'écouter
    app.listen(config.port, () => console.log(`hub-server démarré sur le port ${config.port}`));
  });
}

Le seedAdminIfNeeded() est async (argon2 hache de façon asynchrone) : on attend qu'il finisse — via .then(...) — avant d'ouvrir l'écoute, pour garantir que le compte existe dès la première requête. Notons qu'il n'est appelé que dans la branche « lancé directement » : les tests qui passent par createApp ne seedent rien (ils créent leurs comptes explicitement).
