3 — Le serveur Hub

hub/routes/sync.js — réception du push

Le côté Hub de la synchronisation : c'est ici que la Borne pousse ses données après un événement. Toutes les routes sont protégées par requireBox. C'est la page de référence pour multer (réception de fichiers uploadés) et pour le remplacement atomique d'un fichier. Le flux complet côté Borne est dans sync/push.js ; ici on voit ce que le Hub reçoit à chaque étape.

Les étapes du push, vues du Hub

EndpointRôle
GET /eventLa Borne demande l'unique événement de son token (404 si non pullable). Remplace l'ancien GET /assigned (§11.20).
GET /events/:id/bundlePull : renvoie l'événement + questions + meta. 403 si :id ≠ req.box.event_id. Passe ready→loaded.
POST /events/:id/configRemontée de config : la Borne pousse questions + meta (overwrite/merge). 409 si statut figé (≥ live).
POST /events/:id/statusTransition de statut : la Borne signale closed (au début du push). Refus 409 si retour en arrière.
POST /events/:id/manifestPush étape 1 : la Borne annonce ses fichiers ; le Hub répond la liste des missing.
PUT /events/:id/files/:videoIdPush étape 2 : upload d'une vidéo, vérif checksum.
PUT /events/:id/dbPush étape 3 : upload du db.sqlite, remplacement atomique.
POST /events/:id/finalizePush étape 4 : vérifie la complétude, passe pushed, enfile les jobs.

§11.20 — un token ne voit que son propre événement

// GET /api/sync/event — remplace GET /assigned (liste) : un token = un événement
router.get('/event', (req, res) => {
  const db = getDb();
  const event = getEvent(db, req.box.event_id);                  // l'événement DU token
  if (!event || !['ready', 'loaded'].includes(event.status)) {
    return res.status(404).json({ error: 'Aucun événement pullable pour ce token' });
  }
  res.json({
    id: event.id, name: event.name, event_date: event.event_date,
    status: event.status, updated_at: event.updated_at,
    is_preview: req.box.is_preview,
  });
});

// Sur chaque route …/events/:id/… : rejeter si l'id ≠ l'événement du token
if (req.params.id !== req.box.event_id) {
  return res.status(403).json({ error: 'Token non autorisé sur cet événement' });
}
⛔ §11.20 : le token désigne l'événement, le Hub le fait respecter

Avec le modèle « token = événement » (box_tokens), requireBox pose req.box.event_id. Deux conséquences ici :

  1. GET /event (singulier) renvoie directement l'événement du token s'il est ready/loaded, sinon 404 (purgé, ou déjà ≥ live). La Borne (pullMyEvent) traite ce 404 comme « rien à tirer ». La réponse inclut is_preview (pour le mode démo, §11.21).
  2. Toutes les routes …/events/:id/… (bundle, status, manifest, files, db, finalize) vérifient que :id === req.box.event_id et répondent 403 sinon. Un token ne peut donc ni tirer ni pousser un événement qui n'est pas le sien — même s'il connaît son id. (Avant la Phase 6C, ce contrôle comparait event.box_id à req.box.id ; il compare désormais les event_id.)

Réception d'une remontée de config (POST /events/:id/config)

// body: { mode: 'overwrite'|'merge', questions: [...], meta: { theme, ... } }
// Protégé par requireBox (token borne) — pas requireUser (JWT admin).
router.post('/events/:id/config', validateUuidParams('id'), (req, res, next) => {
  const event = getEvent(getDb(), req.params.id);
  if (!event) return res.status(404).json({ error: 'Événement introuvable' });
  if (req.params.id !== req.box.event_id) return res.status(403).json({ error: 'Non assigné à cette borne' });

  const FROZEN = new Set(['live', 'closed', 'pushed', 'processed', 'purged']);
  if (FROZEN.has(event.status)) return res.status(409).json({ error: `Import impossible : statut ${event.status}` });

  const { mode, questions, meta } = req.body;
  if (!['overwrite', 'merge'].includes(mode)) return res.status(400).json({ error: 'mode invalide' });

  const META_KEYS = ['theme', 'idle_timeout', ...Object.keys(TEXT_FIELDS)];
  const edb = openEventDb(event.id, dataDir);
  // meta : upsert clé par clé (en merge, on ne remplace pas une valeur non vide ; theme validé via THEMES)
  // questions : en overwrite on vide d'abord ; en merge on ignore les textes déjà présents
  // … insertSyncLog('config_import') …
  res.json({ ok: true });
});

C'est le pendant Hub de pushConfig (la Borne remonte sa config). Comme toutes les routes de ce fichier, elle est protégée par requireBox (token borne), pas par le JWT admin — et applique le même garde §11.20 (:id === req.box.event_id, sinon 403). Deux modes :

  • overwrite : la Borne fait foi — on vide les questions puis on réinsère celles reçues ; les event_meta connues sont écrasées.
  • merge : on ne touche pas à une valeur de meta déjà non vide, et on ignore les questions dont le texte existe déjà — on ne fait qu'ajouter ce qui manque.

Le statut est verrouillé : si l'événement est déjà live ou au-delà (FROZEN), on refuse avec 409 — pas question de réécrire la config d'un événement en cours ou archivé. Seules les clés meta connues (theme validé contre THEMES, idle_timeout, les TEXT_FIELDS) sont acceptées, et chaque import laisse une trace dans sync_log (action config_import).

JS multer — recevoir des fichiers uploadés (multipart)

Quand un client envoie un fichier via un formulaire HTTP, le corps est encodé en multipart/form-data — un format que express.json() ne sait pas lire. multer est le middleware qui parse ce format, écrit le fichier reçu (ici sur disque) et expose ses métadonnées dans req.file. 

const uploadVideo = multer({
  storage: multer.diskStorage({
    destination(req, file, cb) {                       // OÙ écrire
      const dir = join(evDir(dataDir, req.params.id), 'videos');
      mkdirSync(dir, { recursive: true });
      cb(null, dir);                                   // cb(erreur, valeur)
    },
    filename(req, file, cb) {                          // SOUS QUEL NOM
      const ext = extname(file.originalname).toLowerCase() || '.mp4';
      cb(null, `${req.params.videoId}${ext}`);
    },
  }),
  limits: { fileSize: maxUploadBytes, files: 1 },      // plafond + un seul fichier
});

On le branche sur une route avec uploadVideo.single('file') : « attends-toi à un fichier dans le champ file ». Après ce middleware, req.file contient { path, size, originalname, mimetype, … }.

Le pattern cb(null, valeur) est le style callback Node historique : le premier argument est l'erreur (null si tout va bien), le second la valeur. C'est la convention « error-first callback » qu'on retrouve dans beaucoup d'API Node anciennes.

LangageAnalogie
Python/Flaskrequest.files['file'] (Werkzeug parse le multipart)

Le limits: { fileSize, files: 1 } est une protection essentielle (§S3/M2) : sans plafond, une Borne malveillante (ou un bug) pourrait saturer le disque du VPS, qui est mutualisé entre tous les clients. Si le fichier dépasse fileSize, multer interrompt et lève une MulterError avec code: 'LIMIT_FILE_SIZE' — interceptée par le gestionnaire d'erreurs qui renvoie 413. Le plafond par défaut est LIMITS.VIDEO_MAX_BYTES (500 Mo), surchargeable dans les tests via opts.maxUploadBytes pour tester le rejet sans envoyer 500 Mo.

L'idempotence du manifest

// POST /events/:id/manifest — body: { files: [{video_id, checksum, …}], db: {…} }
const videosDir = join(evDir(dataDir, event.id), 'videos');
const missing = [];
for (const f of files) {
  const ok = await videoAlreadyReceived(videosDir, f.video_id, f.checksum);
  if (!ok) missing.push(f.video_id);
}
writeFileSync(manifestPath(dataDir, event.id), JSON.stringify({ files, db: dbMeta }));
res.json({ missing });

Le Hub compare ce que la Borne annonce à ce qu'il a déjà reçu (un fichier présent avec le bon checksum n'est pas « manquant »). Il renvoie la liste missing — la Borne n'enverra que ceux-là. C'est ce qui rend un push reprenable : si la connexion coupe au milieu, on relance, le manifest recense ce qui reste, on n'ré-envoie pas les vidéos déjà transférées. Le manifest est aussi persisté en JSON pour que finalize puisse vérifier la complétude plus tard.

→ notion : sha256File (vérification d'intégrité) — vue dans core/checksum.js

Vérification de checksum à la réception

const actual = await sha256File(req.file.path);
if (expectedChecksum && actual !== expectedChecksum) {
  try { unlinkSync(req.file.path); } catch {}          // supprime le fichier corrompu
  return res.status(422).json({ error: 'Checksum mismatch — fichier corrompu, réessayez' });
}

Le Hub recalcule le SHA-256 du fichier reçu et le compare à celui annoncé dans le manifest. S'ils diffèrent → corruption en transit → on supprime le fichier et on renvoie 422 (la Borne réessaiera). Le try { unlinkSync(...) } catch {} est un nettoyage best-effort : on tente de supprimer, mais si ça échoue (fichier déjà parti), on ignore — d'où le catch {} vide. Ce motif revient à chaque garde de cette route (événement introuvable, mauvaise borne, mauvais statut → on supprime le fichier que multer a déjà écrit).

Le remplacement atomique du db.sqlite

// PUT /events/:id/db
closeEventDb(event.id);                                // §11.11 : fermer AVANT d'écraser

const dest = join(evDir(dataDir, event.id), 'db.sqlite');
try { unlinkSync(dest + '-wal'); } catch {}             // nettoie les fichiers WAL/SHM résiduels
try { unlinkSync(dest + '-shm'); } catch {}

renameSync(req.file.path, dest);                        // remplace atomiquement
⛔ Trois précautions sur le remplacement de la base
  1. §11.11 — closeEventDb d'abord : le handle SQLite pointant sur l'ancien db.sqlite doit être fermé avant qu'on écrase le fichier (voir eventStore).
  2. Nettoyage WAL/SHM : on supprime les -wal et -shm de l'ancienne base. Sinon le nouveau db.sqlite serait associé à un WAL résiduel incohérent → corruption. C'est le pendant réception de l'invariant §11.8 (checkpoint WAL) côté Borne.
  3. renameSync est atomique : sur un même système de fichiers, renommer remplace le fichier de destination d'un seul coup. À aucun instant le db.sqlite n'existe « à moitié écrit ». C'est pourquoi multer a écrit le fichier reçu sous un nom temporaire (db.sqlite.incoming) qu'on renomme ensuite — plutôt que d'écrire directement sur db.sqlite.

finalize : recalcul des missing (ne jamais faire confiance au local)

// POST /events/:id/finalize
const stillMissing = [];
for (const f of manifest.files) {
  const ok = await videoAlreadyReceived(videosDir, f.video_id, f.checksum);
  if (!ok) stillMissing.push(f.video_id);
}
if (stillMissing.length > 0) return res.status(409).json({ error: 'Fichiers manquants', missing: stillMissing });
// … vérifie db.sqlite présent, idempotence si déjà pushed …
// puis enfile les jobs (probe + thumbnail par vidéo, + archive) et passe en 'pushed'
⛔ §11.12 : le Hub revérifie tout, il ne croit pas la Borne sur parole

À la finalisation, le Hub recalcule lui-même quels fichiers sont présents et corrects, en relisant le disque et en recomparant les checksums — il ne se fie pas à un « tout est bon » envoyé par la Borne. Si quoi que ce soit manque, il refuse (409) et la Borne reprendra. C'est la garantie qu'un événement passé pushed a réellement toutes ses données sur le Hub. Ensuite seulement il enfile les jobs de traitement (voir worker) et bascule le statut. L'opération est idempotente : si l'événement est déjà pushed, on ne ré-enfile pas les jobs (évite les doublons).

JS for…of + await = traitement séquentiel

Les boucles for (const f of files) { … await … } traitent les fichiers un par un : chaque await est attendu avant l'itération suivante. C'est voulu ici (vérifier les checksums sans saturer le disque). Si on voulait du parallélisme, on utiliserait await Promise.all(files.map(async f => …)) — mais la version séquentielle est plus prudente pour des I/O disque intensives.
