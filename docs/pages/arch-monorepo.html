1 — Architecture

Monorepo & NPM workspaces

Tout le code de Kapsule vit dans un seul dépôt git (un « monorepo ») qui contient plusieurs sous-projets indépendants : le package partagé, le serveur Hub, le serveur Borne, et les deux fronts web. Ces sous-projets sont liés entre eux par les workspaces NPM. Avant de comprendre ça, il faut savoir ce qu'est NPM.

JS NPM et le fichier package.json

NPM (Node Package Manager) est à Node ce que pip est à Python ou go mod à Go : il installe les dépendances et lance des scripts. Chaque projet JS a un fichier package.json qui le décrit — c'est l'équivalent combiné de pyproject.toml + requirements.txt, ou de go.mod.

Les champs essentiels d'un package.json :

  • "dependencies" — paquets nécessaires en production (ex. express).
  • "devDependencies" — paquets nécessaires seulement pour développer/tester (ex. supertest). Pas installés en prod si on fait npm install --production.
  • "scripts" — des alias de commandes, lancés par npm run <nom> (sauf test, start qui ont un raccourci : npm test).
  • "main" — le fichier d'entrée quand un autre module fait import … from 'ce-paquet'.
  • "private": true — empêche une publication accidentelle sur le registre public npm.

node_modules est volumineux et jamais commité (il est dans .gitignore). On le reconstruit avec npm install, qui lit package.json et fige les versions exactes dans package-lock.json (à commiter, lui, pour des installs reproductibles — comme go.sum).

Différence majeure avec Go : Node résout les imports à l'exécution en remontant l'arborescence node_modules depuis le fichier courant. Il n'y a pas de compilation préalable qui vérifie que tout est présent. Un import manquant n'explose qu'au moment où la ligne s'exécute.

Le package.json racine de Kapsule

Voici le fichier package.json à la racine du dépôt :

{
  "name": "kapsule",
  "version": "0.0.1",
  "private": true,
  "type": "module",
  "workspaces": [
    "packages/*",
    "apps/*/server",
    "apps/*/web"
  ],
  "scripts": {
    "test": "if find packages apps -maxdepth 3 -name 'package.json' ... ; then npm test --workspaces --if-present; fi",
    "dev:borne": "npm run dev --workspace=apps/borne/server",
    "dev:hub": "npm run dev --workspace=apps/hub/server"
  },
  "engines": {
    "node": ">=20"
  }
}

Trois choses importantes ici :

1. "type": "module"

Ce champ bascule tout le dépôt en modules ES (ESM) : on écrit import/export et non require(). Comme les workspaces héritent de ce réglage, l'ensemble du code Kapsule est en ESM. C'est détaillé dans ESM : import / export.

2. "workspaces"

JS Les workspaces NPM (monorepo)

Un workspace est un sous-projet, avec son propre package.json, qui vit dans le même dépôt. Le champ "workspaces" du package.json racine liste les chemins (avec jokers *) où NPM doit chercher ces sous-projets.

Ici, NPM considère comme workspaces :

  • packages/* → packages/core
  • apps/*/server → apps/hub/server, apps/borne/server
  • apps/*/web → apps/hub/web, apps/borne/web

Ce que ça change concrètement : un seul npm install lancé à la racine installe les dépendances de tous les workspaces, et place un unique node_modules à la racine (les paquets communs sont mutualisés). Surtout, NPM crée des liens symboliques entre workspaces : quand le serveur Hub déclare dépendre de @kapsule/core, NPM le fait pointer vers le dossier local packages/core — pas besoin de publier quoi que ce soit.

Le lien symbolique est la clé : node_modules/@kapsule/core est un symlink vers ../../packages/core. Donc quand tu modifies un fichier de core, les serveurs voient le changement immédiatement, sans réinstaller ni rebuild. C'est l'équivalent exact d'un pip install -e (editable install) en Python, mais automatique pour tous les workspaces.

Le flag --workspace=apps/hub/server (visible dans les scripts dev:hub) cible un workspace précis : « lance le script dev, mais dans ce sous-projet-là ». Et --workspaces (pluriel) signifie « dans tous ». Le --if-present évite l'erreur si un workspace n'a pas le script demandé.

3. "scripts" et "engines"

Les scripts dev:borne / dev:hub sont les raccourcis pour lancer chaque serveur en développement (ils délèguent au script dev du workspace ciblé). Le champ "engines": { "node": ">=20" } documente la version de Node requise — le code utilise des fonctionnalités récentes (test runner natif, fetch global…).

ℹ Le préfixe @kapsule/

@kapsule/core est un scoped package : le @kapsule/ est un « scope » (espace de noms), comme un préfixe de module Go (github.com/org/…). Ça évite les collisions de noms et regroupe les paquets d'un même projet. Ici le scope n'est pas publié : il n'existe que localement grâce aux workspaces.

Comment un serveur importe le code partagé

Le package.json de apps/hub/server déclare simplement "@kapsule/core" dans ses dependencies. Ensuite, dans le code, on écrit : 

import { LIMITS } from '@kapsule/core';
import { sha256File } from '@kapsule/core/src/checksum.js';

Le premier import résout vers le "main" / "exports" du package core (son « barrel », voir core/index.js). Le second cible un fichier précis du package — utile pour le code server-only que le barrel n'expose pas exprès (comme checksum.js qui dépend de modules Node). On détaille ce choix dans la page de core/index.js.
