2 — Le package partagé

core/validate.js

Trois fonctions de validation partagées : validateQuestion, validateGuestName, assertStatus. Comme elles sont dans core (et dans le barrel), Hub et Borne valident à l'identique. Elles sont en JS pur — utilisables aussi bien côté serveur que dans un front, même si ici elles servent surtout côté serveur.

Une convention de retour à connaître

validateQuestion et validateGuestName suivent une convention simple : retourner null si tout va bien, ou une chaîne de message d'erreur sinon. 

export function validateGuestName(name) {
  if (!name || typeof name !== 'string' || name.trim().length === 0) {
    return 'Le prénom est requis.';
  }
  if (name.length > LIMITS.GUEST_NAME_MAX) {
    return `Le prénom ne doit pas dépasser ${LIMITS.GUEST_NAME_MAX} caractères.`;
  }
  return null;   // null = valide
}

Et l'appel typique dans une route (sessions.js) :

const nameErr = validateGuestName(guest_name);
if (nameErr) return res.status(400).json({ error: nameErr });
JS Fonction pure, « truthy/falsy », et le template literal

Ces fonctions sont pures : même entrée → même sortie, aucun effet de bord (pas d'accès base, pas de log). Faciles à tester et à raisonner.

if (!name || …) exploite les valeurs « falsy » de JS : sont considérées fausses undefined, null, 0, "", NaN, false. Donc !name attrape « pas fourni » et « chaîne vide » d'un coup. Le typeof name !== 'string' ajoute une garde de type (un client malveillant pourrait envoyer un nombre).

Les messages utilisent les template literals (backticks) : `… ${LIMITS.GUEST_NAME_MAX} …` interpole une expression dans une chaîne, comme une f-string Python.

LangageInterpolation
Pythonf"max {n} car."
Kotlin"max $n car."
JS`max ${n} car.` (backticks obligatoires)

Le choix « retourner null ou une string » (plutôt que lever une exception, ou retourner un booléen) est un compromis pragmatique : la route récupère directement le message à renvoyer au client, sans try/catch ni table de correspondance code→message. C'est un mini « errors as values » à la Go — sauf qu'au lieu de (value, error) on a juste error | null, parce que la validation ne produit pas de valeur, seulement un verdict.

Le revers : il faut penser à tester if (err) à chaque appel. Un oubli ne provoque pas d'erreur visible — la validation est simplement ignorée. C'est pourquoi le projet teste systématiquement les cas d'erreur (voir Tests).

validateQuestion : validation de champs numériques

export function validateQuestion({ text, max_duration, countdown }) {
  if (!text || typeof text !== 'string' || text.trim().length === 0) {
    return 'Le texte de la question est requis.';
  }
  if (text.length > LIMITS.QUESTION_TEXT_MAX) {
    return `Le texte ne doit pas dépasser ${LIMITS.QUESTION_TEXT_MAX} caractères.`;
  }
  if (max_duration !== undefined) {
    const d = Number(max_duration);
    if (!Number.isInteger(d) || d < LIMITS.QUESTION_MIN_DURATION_S || d > LIMITS.QUESTION_MAX_DURATION_S) {
      return `max_duration doit être un entier entre ${LIMITS.QUESTION_MIN_DURATION_S} et ${LIMITS.QUESTION_MAX_DURATION_S}.`;
    }
  }
  // … idem countdown …
  return null;
}

Deux points de syntaxe :

  • Le paramètre { text, max_duration, countdown } est un destructuring : la fonction reçoit un objet et en extrait directement les champs. Équivalent de def f(*, text, max_duration, countdown) en Python avec un dict.
  • Number(x) + Number.isInteger(d) : on convertit explicitement (le client envoie souvent des chaînes) puis on vérifie que c'est bien un entier. Number("12") donne 12, mais Number("12.5") donne 12.5 (rejeté par isInteger) et Number("abc") donne NaN (aussi rejeté).
⚠ Piège : max_duration !== undefined

La validation des champs numériques est conditionnée à !== undefined : un champ absent est accepté (la route appliquera un défaut). C'est ce qui permet une mise à jour partielle (PUT qui ne change que le texte). Mais attention : null n'est pas undefined — si un client envoie max_duration: null, Number(null) vaut 0, qui sera rejeté comme « hors bornes ». Comportement voulu ici, mais c'est le genre de subtilité à garder en tête.

assertStatus : la machine à états, version stricte

export function assertStatus(current, next) {
  const from = STATUS_ORDER.indexOf(current);
  const to = STATUS_ORDER.indexOf(next);
  if (from === -1) throw new Error(`Statut inconnu : ${current}`);
  if (to === -1) throw new Error(`Statut inconnu : ${next}`);
  if (to <= from) throw new Error(`Transition invalide : ${current} → ${next}`);
}

Contrairement aux deux autres, celle-ci lève une exception au lieu de retourner un message. La logique : une transition de statut illégale est un bug de programmation (ou une attaque), pas une saisie utilisateur à corriger gentiment. Elle s'appuie sur STATUS_ORDER de constants.js : indexOf donne la position, et « avancer » signifie to > from.

JS throw et les objets Error

throw lance une exception, comme raise en Python ou panic en Go (mais ici c'est rattrapable normalement, pas catastrophique). On lance par convention un objet Error, qui porte un .message et une .stack (trace d'appel).

On verra plus loin une technique récurrente du projet pour attacher des données à une Error — typiquement un code HTTP : Object.assign(new Error('…'), { status: 409 }). Détaillé dans hubClient.js.
