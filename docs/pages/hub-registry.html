3 — Le serveur Hub

hub/registry.js — la base centrale

Ce fichier gère registry.sqlite, l'annuaire global du Hub. Il fait deux choses : (1) ouvrir/initialiser la base (schéma des tables users, box_tokens, events, jobs, sync_log), et (2) fournir un jeu de fonctions d'accès (insert/get/update/delete) que les routes appellent. Rappel : aucune donnée invité ici (invariant RGPD §11.13).

Le pattern singleton

import Database from 'better-sqlite3';
import { join } from 'node:path';
import { mkdirSync } from 'node:fs';

let _db = null;                          // l'unique connexion, en variable de module

export function openRegistry(dataDir) {
  if (_db) return _db;                   // déjà ouverte → on la réutilise
  mkdirSync(dataDir, { recursive: true });
  const db = new Database(join(dataDir, 'registry.sqlite'));
  db.pragma('journal_mode = WAL');
  db.pragma('foreign_keys = ON');
  db.exec(`CREATE TABLE IF NOT EXISTS users (…); …`);   // schéma (voir plus bas)
  _db = db;
  return db;
}

export function getDb() {
  if (!_db) throw new Error('Registry not initialized — call openRegistry() first');
  return _db;
}

export function closeRegistry() {
  if (_db) { _db.close(); _db = null; }
}
JS Le singleton « par module »

Une variable déclarée au niveau d'un module (ici let _db = null) est privée au fichier et partagée par tout le code qui l'importe — parce qu'un module ES n'est évalué qu'une fois et mis en cache. C'est l'idiome JS du singleton : pas besoin de classe ni de variable globale.

Le préfixe _ de _db est une convention (« privé, ne pas toucher de l'extérieur ») — JS n'a pas de vrai private au niveau module, mais comme la variable n'est pas exportée, elle est de fait inaccessible ailleurs. On expose seulement des fonctions : openRegistry, getDb, closeRegistry.

Le trio open / get / close est un cycle de vie classique : openRegistry est appelé une fois au démarrage (dans createApp), getDb est utilisé partout ailleurs (et lève si on a oublié d'ouvrir — fail-fast utile), et closeRegistry existe surtout pour les tests : entre deux suites, on ferme et on rouvre sur un nouveau dossier temporaire pour repartir d'une base vierge. En production, la connexion vit aussi longtemps que le processus.

Le schéma : contraintes SQL comme garde-fou

Extrait du schéma (table events) :

CREATE TABLE IF NOT EXISTS events (
  id           TEXT PRIMARY KEY,
  owner_id     INTEGER NOT NULL REFERENCES users(id),
  name         TEXT NOT NULL,
  event_date   DATE,
  status       TEXT NOT NULL DEFAULT 'draft'
               CHECK(status IN ('draft','ready','loaded','live','closed','pushed','processed','purged')),
  pulled_at    DATETIME, pushed_at DATETIME, processed_at DATETIME, purged_at DATETIME,
  created_at   DATETIME DEFAULT CURRENT_TIMESTAMP,
  updated_at   DATETIME DEFAULT CURRENT_TIMESTAMP
);

Le CHECK(status IN (…)) reproduit la liste de STATUS_ORDER (constants.js) au niveau base : SQLite refuse physiquement une valeur de statut hors liste. C'est une duplication assumée (la liste existe en JS et en SQL) qui ajoute une dernière ligne de défense — même un bug applicatif ne peut pas écrire un statut invalide. Idem pour role CHECK(role IN ('admin','client')) dans users.

La table box_tokens : un token = un événement (§11.20)

CREATE TABLE IF NOT EXISTS box_tokens (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  event_id     TEXT NOT NULL REFERENCES events(id) ON DELETE CASCADE,
  token_hash   TEXT UNIQUE NOT NULL,                  -- sha256(token) : sert à l'auth (X-Box-Token)
  token_clear  TEXT UNIQUE NOT NULL DEFAULT '',       -- token en clair : ré-consultable par l'admin
  label        TEXT,
  location     TEXT,
  is_preview   INTEGER NOT NULL DEFAULT 0,
  last_seen_at DATETIME,
  created_at   DATETIME DEFAULT CURRENT_TIMESTAMP
);

Cette table remplace l'ancienne boxes (et la colonne events.box_id a disparu). Le changement de modèle : au lieu d'enregistrer des « bornes » nommées qu'on assignait ensuite à un événement, on génère désormais un token par événement. Le event_id NOT NULL REFERENCES events(id) ON DELETE CASCADE ancre chaque token à son événement — purger l'événement supprime automatiquement ses tokens. Conséquences à connaître :

  • Un token désigne directement son événement : plus besoin d'un PUT …/assign (supprimé). Le lien Borne↔événement se crée en générant le token.
  • Plusieurs tokens peuvent pointer le même événement (un réel + un d'essai), d'où une table plutôt qu'une colonne sur events — chacun révocable indépendamment.
  • is_preview = 1 marque un token d'essai (borne de démo, §11.21) ; label/location sont purement descriptifs (affichés à l'admin).
  • Le token est stocké en double : token_hash (SHA-256) sert à l'authentification de la Borne (requireBox), tandis que token_clear permet à l'admin de re-consulter et copier le token plus tard (décision Phase 6E — voir routes/admin.js et l'invariant §11.13b). Le clair n'est jamais exposé aux routes synchro ni aux clients, uniquement aux routes admin.

La table sync_log a aussi perdu sa colonne box_id : avec un token par événement, event_id suffit à tracer qui a fait quoi.

La migration douce de token_clear

box_tokens a d'abord existé sans token_clear (le clair n'était montré qu'une fois). Pour ne pas perdre les bases déjà en place, l'ajout de la colonne se fait par une migration douce au lieu d'un simple CREATE TABLE (qui ne s'applique pas à une table existante) : 

// Migration: add 'token_clear' to box_tokens if the table predates this change
const boxCols = db.pragma('table_info(box_tokens)').map((c) => c.name);
if (!boxCols.includes('token_clear')) {
  db.exec("ALTER TABLE box_tokens ADD COLUMN token_clear TEXT NOT NULL DEFAULT ''");
}

On interroge le schéma réel via pragma('table_info(...)'), et on n'ajoute la colonne que si elle manque — idempotent, rejouable à chaque démarrage. Le DEFAULT '' couvre les lignes anciennes (tokens générés avant la migration : leur clair n'a pas été conservé). C'est le même motif que les migrations active sur users plus haut dans le fichier.

Les fonctions d'accès : db passé en argument

Toutes les fonctions reçoivent db en premier paramètre :

export function getUserByEmail(db, email) {
  return db.prepare('SELECT * FROM users WHERE email = ?').get(email);
}
export function insertEvent(db, { id, owner_id, name, event_date = null }) {
  return db.prepare('INSERT INTO events (id, owner_id, name, event_date) VALUES (?, ?, ?, ?)')
    .run(id, owner_id, name, event_date);
}

Pourquoi passer db alors que getDb() existe ? Pour la testabilité et la clarté : ces fonctions deviennent pures vis-à-vis de la base (on peut leur passer n'importe quelle connexion, y compris une base de test), et l'appelant contrôle explicitement quelle connexion il utilise. La méthode .run() renvoie { changes, lastInsertRowid } — on récupère souvent lastInsertRowid pour connaître l'id auto-incrémenté qu'on vient de créer.

L'UPDATE dynamique

updateEvent mérite une lecture attentive — c'est un mini-générateur de SQL : 

export function updateEvent(db, id, fields) {
  const allowed = ['name', 'event_date', 'status',
    'pulled_at', 'pushed_at', 'processed_at', 'purged_at'];
  const updates = Object.keys(fields)
    .filter((k) => allowed.includes(k))      // ne garde que les colonnes autorisées
    .map((k) => `${k} = ?`);                 // ['name = ?', 'status = ?', …]
  if (updates.length === 0) return;
  updates.push('updated_at = CURRENT_TIMESTAMP');
  const values = Object.keys(fields).filter((k) => allowed.includes(k)).map((k) => fields[k]);
  db.prepare(`UPDATE events SET ${updates.join(', ')} WHERE id = ?`).run(...values, id);
}
JS Object.keys, filter/map, et le spread ...
  • Object.keys(fields) → tableau des noms de propriétés de l'objet (≈ dict.keys() Python).
  • .filter(predicat) → garde les éléments qui passent le test. Ici : seulement les colonnes de la liste blanche allowed.
  • .map(transform) → transforme chaque élément. Ici : 'name' → 'name = ?'.
  • .join(', ') → recolle le tableau en une chaîne séparée par des virgules.
  • .run(...values, id) → le spread ...values « étale » le tableau en arguments individuels, suivis de id.

La liste blanche allowed est une protection : seules ces colonnes peuvent être modifiées, même si fields contient d'autres clés (envoyées par un client malveillant). On ne construit jamais un nom de colonne à partir d'entrée brute sans filtrer.

Subtilité de sécurité : les valeurs sont paramétrées (? + spread), donc pas d'injection sur les valeurs. Mais les noms de colonnes, eux, sont interpolés directement dans la chaîne (${k} = ?) — c'est inévitable, SQLite ne permet pas de paramétrer un nom de colonne. D'où l'importance vitale de la liste blanche allowed : sans elle, un attaquant pourrait injecter du SQL via une clé d'objet. C'est le seul endroit où l'on interpole une partie de requête, et c'est verrouillé par la whitelist.
