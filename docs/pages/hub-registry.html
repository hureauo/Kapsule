3 — Le serveur Hub

hub/registry.js — la base centrale

Ce fichier gère registry.sqlite, l'annuaire global du Hub. Il fait deux choses : (1) ouvrir/initialiser la base (schéma des tables users, registration_tokens, box_tokens, events, event_users, jobs, sync_log) avec ses migrations, et (2) fournir un jeu de fonctions d'accès (insert/get/update/delete) que les routes appellent. Rappel : aucune donnée invité ici (invariant RGPD §11.13) — prénoms, vidéos et sessions vivent uniquement dans les db.sqlite par événement.

Le pattern singleton

import Database from 'better-sqlite3';
import { join } from 'node:path';
import { mkdirSync } from 'node:fs';

let _db = null;                          // l'unique connexion, en variable de module

export function openRegistry(dataDir) {
  if (_db) return _db;                   // déjà ouverte → on la réutilise
  mkdirSync(dataDir, { recursive: true });
  const db = new Database(join(dataDir, 'registry.sqlite'));
  db.pragma('journal_mode = WAL');
  db.pragma('foreign_keys = ON');
  db.exec(`CREATE TABLE IF NOT EXISTS users (…); …`);   // schéma (voir plus bas)
  _db = db;
  return db;
}

export function getDb() {
  if (!_db) throw new Error('Registry not initialized — call openRegistry() first');
  return _db;
}

export function closeRegistry() {
  if (_db) { _db.close(); _db = null; }
}
JS Le singleton « par module »

Une variable déclarée au niveau d'un module (ici let _db = null) est privée au fichier et partagée par tout le code qui l'importe — parce qu'un module ES n'est évalué qu'une fois et mis en cache. C'est l'idiome JS du singleton : pas besoin de classe ni de variable globale.

Le préfixe _ de _db est une convention (« privé, ne pas toucher de l'extérieur ») — JS n'a pas de vrai private au niveau module, mais comme la variable n'est pas exportée, elle est de fait inaccessible ailleurs. On expose seulement des fonctions : openRegistry, getDb, closeRegistry.

Le trio open / get / close est un cycle de vie classique : openRegistry est appelé une fois au démarrage (dans createApp), getDb est utilisé partout ailleurs (et lève si on a oublié d'ouvrir — fail-fast utile), et closeRegistry existe surtout pour les tests : entre deux suites, on ferme et on rouvre sur un nouveau dossier temporaire pour repartir d'une base vierge. En production, la connexion vit aussi longtemps que le processus.

Le schéma : contraintes SQL comme garde-fou

Extrait du schéma (tables users et events) :

CREATE TABLE IF NOT EXISTS users (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  email         TEXT UNIQUE NOT NULL,
  password_hash TEXT,                       -- NULL tant que le client n'a pas défini son mot de passe
  name          TEXT,
  role          TEXT NOT NULL DEFAULT 'client'
                CHECK(role IN ('superuser','client')),
  active        INTEGER NOT NULL DEFAULT 1,
  created_at    DATETIME DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE IF NOT EXISTS events (
  id           TEXT PRIMARY KEY,
  owner_id     INTEGER REFERENCES users(id),  -- nullable : un événement peut exister sans client assigné
  name         TEXT NOT NULL,
  event_date   DATE,
  status       TEXT NOT NULL DEFAULT 'draft'
               CHECK(status IN ('draft','ready','loaded','live','closed','pushed','processed','purged')),
  pulled_at    DATETIME, pushed_at DATETIME, processed_at DATETIME, purged_at DATETIME,
  created_at   DATETIME DEFAULT CURRENT_TIMESTAMP,
  updated_at   DATETIME DEFAULT CURRENT_TIMESTAMP
);

Le CHECK(status IN (…)) reproduit la liste de STATUS_ORDER (constants.js) au niveau base : SQLite refuse physiquement une valeur de statut hors liste. C'est une duplication assumée (la liste existe en JS et en SQL) qui ajoute une dernière ligne de défense — même un bug applicatif ne peut pas écrire un statut invalide. Idem pour role CHECK(role IN ('superuser','client')) dans users : seuls ces deux rôles globaux existent (le rôle historique 'admin' a été renommé 'superuser', voir la migration plus bas).

Deux points à connaître sur users : password_hash est nullable — un compte client créé par l'admin n'a pas encore de mot de passe tant qu'il n'a pas suivi son lien d'enregistrement (voir registration_tokens ci-dessous) ; owner_id sur events est lui aussi nullable, car un événement peut être créé par l'admin avant d'être attribué à un client. L'accès, lui, ne dépend pas de owner_id mais de la table event_users (cf. requireOwner).

La table registration_tokens : définir son mot de passe par lien

CREATE TABLE IF NOT EXISTS registration_tokens (
  token_hash  TEXT PRIMARY KEY,
  user_id     INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  expires_at  DATETIME NOT NULL,
  used_at     DATETIME,
  created_at  DATETIME DEFAULT CURRENT_TIMESTAMP
);

Quand l'admin crée un compte client (ou l'assigne à un événement), il ne fixe pas son mot de passe : le serveur génère un jeton d'enregistrement à usage unique, n'en stocke que le hash SHA-256 (token_hash, comme pour les tokens de borne), et renvoie le clair dans un lien …/register?token=…. Le client suit ce lien pour poser son mot de passe (routes/auth — set-password). Le token a une expiration (expires_at, 7 jours par défaut) et est marqué consommé via used_at — on ne le réutilise pas. ON DELETE CASCADE sur user_id nettoie les jetons orphelins si le compte est supprimé.

La table box_tokens : un token = un événement (§11.20)

CREATE TABLE IF NOT EXISTS box_tokens (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  event_id     TEXT NOT NULL REFERENCES events(id) ON DELETE CASCADE,
  token_hash   TEXT UNIQUE NOT NULL,                  -- sha256(token) : sert à l'auth (X-Box-Token)
  token_clear  TEXT UNIQUE NOT NULL DEFAULT '',       -- token en clair : ré-consultable par l'admin
  label        TEXT,
  location     TEXT,
  is_preview   INTEGER NOT NULL DEFAULT 0,
  last_seen_at DATETIME,
  created_at   DATETIME DEFAULT CURRENT_TIMESTAMP
);

Cette table remplace l'ancienne boxes (et la colonne events.box_id a disparu). Le changement de modèle : au lieu d'enregistrer des « bornes » nommées qu'on assignait ensuite à un événement, on génère désormais un token par événement. Le event_id NOT NULL REFERENCES events(id) ON DELETE CASCADE ancre chaque token à son événement — purger l'événement supprime automatiquement ses tokens. Conséquences à connaître :

  • Un token désigne directement son événement : plus besoin d'un PUT …/assign (supprimé). Le lien Borne↔événement se crée en générant le token.
  • Plusieurs tokens peuvent pointer le même événement (un réel + un d'essai), d'où une table plutôt qu'une colonne sur events — chacun révocable indépendamment.
  • is_preview = 1 marque un token d'essai (borne de démo, §11.21) ; label/location sont purement descriptifs (affichés à l'admin).
  • Le token est stocké en double : token_hash (SHA-256) sert à l'authentification de la Borne (requireBox), tandis que token_clear permet à l'admin de re-consulter et copier le token plus tard (décision Phase 6E — voir routes/admin.js et l'invariant §11.13b). Le clair n'est jamais exposé aux routes synchro ni aux clients, uniquement aux routes admin.

La table sync_log a aussi perdu sa colonne box_id : avec un token par événement, event_id suffit à tracer qui a fait quoi.

La table event_users : qui accède à quel événement, avec quels rôles

CREATE TABLE IF NOT EXISTS event_users (
  event_id   TEXT NOT NULL REFERENCES events(id) ON DELETE CASCADE,
  user_id    INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  roles      TEXT NOT NULL DEFAULT '[]',          -- tableau JSON de rôles borne, ex. '["admin_borne"]'
  PRIMARY KEY (event_id, user_id)
);

C'est la table d'appartenance : une ligne (event_id, user_id) dit que ce client a accès à cet événement. La clé primaire composite garantit une seule ligne par couple (un client ne figure qu'une fois sur un événement). Deux usages distincts :

  • Cloisonnement de l'UI Hub : requireOwner autorise un non-superuser uniquement s'il a une ligne ici pour l'événement visé (plus de owner_id === sub).
  • Rôles sur la Borne : le champ roles est un tableau JSON (admin_borne, tech_borne…) qui est pullé dans le db.sqlite de l'événement (table event_users côté Borne). C'est ainsi qu'un client se connecte à la borne avec un compte nominatif plutôt qu'un mot de passe partagé.

Stocker un tableau comme chaîne JSON (plutôt qu'une table de jointure rôles) est un choix de simplicité : la liste de rôles est courte, lue/écrite d'un bloc, jamais requêtée par rôle au niveau SQL. Voir upsertEventUser (qui fait JSON.stringify(roles)) plus bas.

La migration douce de token_clear

box_tokens a d'abord existé sans token_clear (le clair n'était montré qu'une fois). Pour ne pas perdre les bases déjà en place, l'ajout de la colonne se fait par une migration douce au lieu d'un simple CREATE TABLE (qui ne s'applique pas à une table existante) : 

// Migration: add 'token_clear' to box_tokens if the table predates this change
const boxCols = db.pragma('table_info(box_tokens)').map((c) => c.name);
if (!boxCols.includes('token_clear')) {
  db.exec("ALTER TABLE box_tokens ADD COLUMN token_clear TEXT NOT NULL DEFAULT ''");
}

On interroge le schéma réel via pragma('table_info(...)'), et on n'ajoute la colonne que si elle manque — idempotent, rejouable à chaque démarrage. Le DEFAULT '' couvre les lignes anciennes (tokens générés avant la migration : leur clair n'a pas été conservé). C'est le même motif que la migration active sur users plus haut dans le fichier.

Migration par reconstruction de table (renommage de rôle, colonne nullable)

ALTER TABLE … ADD COLUMN suffit pour ajouter une colonne. Mais SQLite ne sait pas modifier une colonne existante (changer un CHECK, retirer un NOT NULL) de façon portable. Deux migrations le contournent par reconstruction : créer une table neuve au bon schéma, recopier les données, jeter l'ancienne, renommer la neuve. Exemple — renommer le rôle 'admin' en 'superuser' (le CHECK n'accepte plus 'admin') : 

// Migration 7A.1 : role 'admin' → 'superuser'. Reconstruction car CHECK non modifiable en place.
const needsUsersMigration =
  db.prepare("SELECT COUNT(*) AS n FROM users WHERE role = 'admin'").get().n > 0;
if (needsUsersMigration) {
  db.exec('PRAGMA foreign_keys = OFF');           // les recopies temporaires violeraient les FK
  db.exec(`
    DROP TABLE IF EXISTS users_new;
    CREATE TABLE users_new ( … role TEXT … CHECK(role IN ('superuser','client')) … );
    INSERT INTO users_new SELECT
      id, email, password_hash, name,
      CASE WHEN role = 'admin' THEN 'superuser' ELSE role END,   -- transformation à la volée
      active, created_at
    FROM users;
    DROP TABLE users;
    ALTER TABLE users_new RENAME TO users;
  `);
  db.exec('PRAGMA foreign_keys = ON');
}

La même technique relâche events.owner_id de NOT NULL à nullable : on détecte le besoin en inspectant pragma('table_info(events)') et en regardant notnull === 1 sur la colonne owner_id, puis on reconstruit. Les deux migrations sont conditionnelles (elles ne tournent que si l'ancien schéma est encore là) et donc idempotentes : sur une base neuve, le CREATE TABLE IF NOT EXISTS initial pose déjà le bon schéma et la condition est fausse.

⚠ Pourquoi couper les foreign keys pendant la reconstruction

Le DROP TABLE users casserait les clés étrangères qui pointent vers users (events, event_users, registration_tokens) si elles étaient appliquées. PRAGMA foreign_keys = OFF le temps de l'opération évite ces erreurs, puis on les réactive. La table renommée garde le même nom, donc les FK redeviennent valides. À ne faire que dans une migration contrôlée, jamais en fonctionnement normal.

Les fonctions d'accès : db passé en argument

Toutes les fonctions reçoivent db en premier paramètre :

export function getUserByEmail(db, email) {
  return db.prepare('SELECT * FROM users WHERE email = ?').get(email);
}
export function insertEvent(db, { id, name, event_date = null }) {
  return db.prepare('INSERT INTO events (id, name, event_date) VALUES (?, ?, ?)')
    .run(id, name, event_date);
}

Noter que insertEvent ne pose pas d'owner_id : un événement naît sans propriétaire. L'attribution à un client se fait plus tard via une route dédiée (qui insère dans event_users et fixe éventuellement owner_id).

Pourquoi passer db alors que getDb() existe ? Pour la testabilité et la clarté : ces fonctions deviennent pures vis-à-vis de la base (on peut leur passer n'importe quelle connexion, y compris une base de test), et l'appelant contrôle explicitement quelle connexion il utilise. La méthode .run() renvoie { changes, lastInsertRowid } — on récupère souvent lastInsertRowid pour connaître l'id auto-incrémenté qu'on vient de créer.

L'UPDATE dynamique

updateEvent mérite une lecture attentive — c'est un mini-générateur de SQL : 

export function updateEvent(db, id, fields) {
  const allowed = ['name', 'event_date', 'status',
    'pulled_at', 'pushed_at', 'processed_at', 'purged_at'];
  const updates = Object.keys(fields)
    .filter((k) => allowed.includes(k))      // ne garde que les colonnes autorisées
    .map((k) => `${k} = ?`);                 // ['name = ?', 'status = ?', …]
  if (updates.length === 0) return;
  updates.push('updated_at = CURRENT_TIMESTAMP');
  const values = Object.keys(fields).filter((k) => allowed.includes(k)).map((k) => fields[k]);
  db.prepare(`UPDATE events SET ${updates.join(', ')} WHERE id = ?`).run(...values, id);
}
JS Object.keys, filter/map, et le spread ...
  • Object.keys(fields) → tableau des noms de propriétés de l'objet (≈ dict.keys() Python).
  • .filter(predicat) → garde les éléments qui passent le test. Ici : seulement les colonnes de la liste blanche allowed.
  • .map(transform) → transforme chaque élément. Ici : 'name' → 'name = ?'.
  • .join(', ') → recolle le tableau en une chaîne séparée par des virgules.
  • .run(...values, id) → le spread ...values « étale » le tableau en arguments individuels, suivis de id.

La liste blanche allowed est une protection : seules ces colonnes peuvent être modifiées, même si fields contient d'autres clés (envoyées par un client malveillant). On ne construit jamais un nom de colonne à partir d'entrée brute sans filtrer.

Subtilité de sécurité : les valeurs sont paramétrées (? + spread), donc pas d'injection sur les valeurs. Mais les noms de colonnes, eux, sont interpolés directement dans la chaîne (${k} = ?) — c'est inévitable, SQLite ne permet pas de paramétrer un nom de colonne. D'où l'importance vitale de la liste blanche allowed : sans elle, un attaquant pourrait injecter du SQL via une clé d'objet. C'est le seul endroit où l'on interpole une partie de requête, et c'est verrouillé par la whitelist.

À noter : listEvents filtre selon le rôle — un superuser voit tous les événements, un client seulement ceux dont il est membre, via une jointure sur event_users (et non plus un WHERE owner_id = ?) : 

export function listEvents(db, { userId, role }) {
  if (role === 'superuser') return db.prepare('SELECT * FROM events ORDER BY created_at DESC').all();
  return db.prepare(`
    SELECT e.* FROM events e
    INNER JOIN event_users eu ON eu.event_id = e.id
    WHERE eu.user_id = ?
    ORDER BY e.created_at DESC
  `).all(userId);
}

C'est le socle du cloisonnement, le même critère d'appartenance que le middleware requireOwner applique route par route : le INNER JOIN event_users ne laisse remonter que les événements où il existe une ligne d'appartenance pour ce userId.
