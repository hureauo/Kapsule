4 — Le serveur Borne

borne/sync/pull.js

Le pull : tirer un événement préparé sur le Hub et l'installer localement (questions, réglages). C'est ce qui se passe avant l'événement, quand la Borne a du réseau. Ce fichier porte deux points importants : la vérification du statut local au moment d'appliquer la réponse (§11.10), et le modèle un token = un événement (§11.20) qui fait que pullMyEvent tire un seul événement, pas une liste.

pullEvent : tirer un événement précis

export async function pullEvent(hubEventId, dataDir) {
  // 1. Requête Hub (peut échouer → lève)
  const bundle = await hubFetchJson(`/api/sync/events/${hubEventId}/bundle`);

  // 2. Vérifie le statut LOCAL au moment d'appliquer (invariant §11.10)
  const db = getRegistry();
  const existing = db.prepare('SELECT * FROM local_events WHERE id = ?').get(hubEventId);
  if (existing && existing.status !== 'loaded') {
    // Événement passé live/closed entre la requête et la réponse — ne pas écraser
    return { skipped: true, reason: `statut local ${existing.status} — pull ignoré` };
  }

  // 3. Crée/met à jour l'event local
  const eventDir = join(dataDir, 'events', hubEventId);
  mkdirSync(eventDir, { recursive: true });
  mkdirSync(join(eventDir, 'videos'), { recursive: true });
  if (!existing) {
    insertEvent({ id: hubEventId, name: bundle.event.name, origin: 'hub', status: 'loaded' });
  }
  // 4. Met à jour pulled_at
  db.prepare('UPDATE local_events SET pulled_at = CURRENT_TIMESTAMP, updated_at = CURRENT_TIMESTAMP WHERE id = ?').run(hubEventId);

  // 5. Écrit questions + event_meta dans la BD événement (le Hub est source de vérité)
  const edb = createEventDb(join(eventDir, 'db.sqlite'));
  try {
    edb.transaction(() => {
      edb.prepare('DELETE FROM questions').run();                 // vide
      const ins = edb.prepare('INSERT INTO questions (id, text, max_duration, countdown, order_index, enabled) VALUES (?, ?, ?, ?, ?, ?)');
      for (const q of bundle.questions) ins.run(q.id, q.text, q.max_duration, q.countdown, q.order_index, q.enabled ?? 1);
    })();
    // … upsert event_meta …
  } finally {
    edb.close();
  }
  return { ok: true, eventId: hubEventId, questions: bundle.questions.length };
}
⛔ Invariant §11.10 : vérifier le statut local À L'APPLICATION, pas au lancement

Le piège : entre le moment où la Borne demande le bundle au Hub (étape 1) et le moment où elle reçoit la réponse (étapes 2-5), du temps passe — potentiellement plusieurs secondes sur un réseau lent. Pendant ce laps, un invité a pu commencer une session, faisant passer l'événement local de loaded à live.

Si on appliquait le pull aveuglément, on écraserait les questions d'un événement en cours (l'étape 5 fait DELETE FROM questions puis réinsère). D'où la vérification à l'étape 2, faite après avoir reçu la réponse : « l'événement local est-il toujours en loaded ? ». S'il est passé live/closed entre-temps, on abandonne le pull (skipped: true) sans rien écraser.

La règle générale : pour une opération « lire à distance puis appliquer localement », revérifie l'état local au moment d'appliquer, pas au moment de lancer la requête. L'état a pu changer pendant l'aller-retour réseau.

JS try { … } finally { edb.close() }

Le finally garantit que edb.close() est appelé quoi qu'il arrive — même si l'insertion des questions lève une exception. Sans ça, une erreur en plein milieu laisserait un handle SQLite ouvert (fuite). C'est le même rôle qu'un finally Python ou un defer Go : du nettoyage garanti. Ici la base est ouverte directement (hors cache eventDb) car le pull manipule la base d'un événement qui n'est pas forcément l'actif — donc on gère sa fermeture nous-mêmes.

Pourquoi DELETE puis réinsérer les questions ?

Le Hub est la source de vérité pour les questions. Plutôt que de tenter une synchro différentielle (compliquée : ajouts, suppressions, modifications), on remplace intégralement : on vide les questions locales et on réinsère celles du bundle, le tout en transaction (atomique). C'est simple et correct. Possible uniquement parce que l'événement est en loaded (pas encore d'usage) — d'où le lien avec l'invariant §11.10 ci-dessus.

pullMyEvent : tirer l'unique événement du token (§11.20)

/**
 * Tire l'événement unique associé à ce token depuis le Hub.
 * Remplace pullAssigned() — un token = un événement (invariant §11.20).
 *
 * Retourne 1 si un pull a eu lieu, 0 si aucun événement pullable (404 Hub).
 */
export async function pullMyEvent(dataDir) {
  let eventInfo;
  try {
    eventInfo = await hubFetchJson('/api/sync/event');
  } catch (e) {
    if (e.status === 404) return 0;   // pas d'événement pullable pour ce token
    throw e;
  }

  const db = getRegistry();
  const existing = db.prepare('SELECT * FROM local_events WHERE id = ?').get(eventInfo.id);

  // Pull si : pas encore présent localement, ou encore en statut 'loaded' (re-pull autorisé)
  if (!existing || existing.status === 'loaded') {
    await pullEvent(eventInfo.id, dataDir);
    // Persiste is_preview depuis la réponse Hub (§11.20)
    db.prepare('UPDATE local_events SET is_preview = ? WHERE id = ?')
      .run(eventInfo.is_preview ? 1 : 0, eventInfo.id);
    return 1;
  }
  return 0;
}

Depuis la Phase 6C, un token de borne désigne un seul événement (box_tokens, §11.20). La Borne ne demande donc plus une liste mais l'événement singulier de son token (GET /sync/event), puis applique le même filtre qu'avant : pull seulement s'il est absent localement ou encore en loaded (re-pull autorisé pour récupérer des modifications de questions tant que l'événement n'a pas démarré). Un événement déjà live/closed est ignoré. C'est ce que le pull automatique appelle en boucle.

Après le pull, pullMyEvent recopie le flag is_preview de la réponse Hub dans local_events : c'est ainsi que la Borne « apprend » qu'elle est une borne d'essai (mode démo). Ce flag local pilote ensuite le refus de push, le quota d'upload et le bandeau « BORNE D'ESSAI » (§11.21) — voir sync.js. La normalisation eventInfo.is_preview ? 1 : 0 convertit le booléen JSON du Hub en l'entier 0/1 attendu par SQLite.

JS Traiter le 404 comme « rien à faire » (pas comme une erreur)

hubFetchJson lève une Error enrichie d'un champ status (hubClient.js) quand le Hub répond ≥ 400. Ici un 404 est un cas normal : l'événement n'est plus pullable (purgé, ou déjà passé live). On l'intercepte spécifiquement (if (e.status === 404) return 0) et on renvoie 0 — « aucun pull » — au lieu de propager l'exception. Toute autre erreur (réseau, 500…) est throw-ée pour être retentée au prochain cycle. Distinguer « pas de travail » d'« échec » évite de polluer les logs et de déclencher des retries inutiles.
