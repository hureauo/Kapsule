4 — Le serveur Borne

borne/index.js

Le montage Express de la Borne. Très proche de hub/index.js — même structure createApp + guard de démarrage — avec deux différences : tous les routeurs reçoivent la config injectée, et toutes les routes sont montées sous un préfixe /api commun.

Le corps de createApp

export function createApp(dataDir, cfg = config) {
  openRegistry(dataDir);
  const app = express();
  app.use(express.json());

  const routerCfg = { ...cfg, requireAdmin: requireAdmin(cfg) };   // config + middleware prêt
  app.post('/api/admin/login', makeAuthRouter(cfg));
  app.use('/api', makeEventsRouter(dataDir, routerCfg));
  app.use('/api', makeQuestionsRouter(dataDir, routerCfg));
  app.use('/api', makeSessionsRouter(dataDir, routerCfg));
  app.use('/api', makeVideosRouter(dataDir, routerCfg));
  app.use('/api', makeSyncRouter(dataDir, routerCfg));

  app.get('/api/health', async (req, res, next) => { /* … disque + événement actif … */ });

  app.use((err, req, res, next) => { /* error handler, idem Hub */ });
  return app;
}
JS Injection de config par le spread : { ...cfg, requireAdmin: requireAdmin(cfg) }

createApp(dataDir, cfg = config) prend la config en paramètre (avec le module config comme défaut). Cela permet aux tests de passer une config sur mesure. Ensuite : 

const routerCfg = { ...cfg, requireAdmin: requireAdmin(cfg) };

Le spread ...cfg copie tous les champs de la config dans un nouvel objet, puis on y ajoute une propriété requireAdmin : le middleware d'auth déjà « armé » avec cette config (rappel : requireAdmin(cfg) est une factory). Chaque routeur reçoit donc routerCfg et y trouve à la fois les réglages (hubUrl, adminPassword…) et le middleware requireAdmin prêt à l'emploi — sans devoir réimporter la config ni recréer le middleware. C'est de l'injection de dépendances « à la main », légère et explicite.

ℹ Pourquoi injecter la config plutôt que l'importer ? (vs Hub)

Le Hub importe directement config dans chaque fichier qui en a besoin. La Borne, elle, la fait circuler via cfg et routerCfg. Les deux marchent ; l'approche Borne rend les routeurs purs vis-à-vis de la config (ils ne dépendent pas d'un module global), donc plus faciles à tester en isolation avec une config arbitraire. C'est un choix de style cohérent avec les factories à closure de la Borne. Voir aussi Décisions d'architecture.

Le montage sous /api partagé

Contrairement au Hub qui monte chaque routeur sous un préfixe distinct (/api/events, /api/admin…), la Borne monte tous les routeurs sous /api : 

app.use('/api', makeEventsRouter(dataDir, routerCfg));
app.use('/api', makeSessionsRouter(dataDir, routerCfg));
// …

Chaque routeur déclare donc ses chemins complets en interne (/events, /sessions, /videos…). C'est un choix d'organisation : les routeurs Borne mélangent routes publiques (kiosque) et admin sur des chemins variés, et les regrouper sous un seul /api évite de fragmenter. L'ordre de montage reste important pour les mêmes raisons qu'au Hub (premier match gagne).

Le health check expose l'événement actif

app.get('/api/health', async (req, res, next) => {
  const stats = await statfs(dataDir);
  const activeEvent = getActiveEvent();
  res.json({ ok: true, activeEvent: activeEvent?.id ?? null, disk: { free_bytes, total_bytes } });
});

Le health check de la Borne ajoute activeEvent : utile pour superviser « quel événement la borne sert actuellement ». L'activeEvent?.id ?? null combine optional chaining (si pas d'actif, undefined) et ?? null (normalisé en null).

if (process.argv[1] === new URL(import.meta.url).pathname) {

⚠ Où démarre le pull automatique ?

Le code de index.js montré ici ne lance pas explicitement startAutoPull dans cet extrait. Le démarrage du cycle de synchronisation automatique est porté par autoPull.js (fonction startAutoPull(dataDir)) — à appeler au bootstrap de la Borne quand un Hub est configuré. Reporte-toi à cette page pour le détail du cycle et à ROADMAP.md pour son état d'intégration.
