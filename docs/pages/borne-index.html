4 — Le serveur Borne

borne/index.js

Le montage Express de la Borne. Très proche de hub/index.js — même structure createApp + guard de démarrage — avec deux différences : tous les routeurs reçoivent la config injectée, et toutes les routes sont montées sous un préfixe /api commun.

Le corps de createApp

export function createApp(dataDir, cfg = config) {
  openRegistry(dataDir);
  const app = express();
  app.use(express.json());

  // config + les deux middlewares d'auth déjà armés (client et tech, §11.19)
  const routerCfg = { ...cfg, requireAdmin: requireAdmin(cfg), requireTech: requireTech(cfg) };
  app.post('/api/admin/login', makeAuthRouter(cfg));
  app.use('/api', makeEventsRouter(dataDir, routerCfg));
  app.use('/api', makeQuestionsRouter(dataDir, routerCfg));
  app.use('/api', makeSessionsRouter(dataDir, routerCfg));
  app.use('/api', makeVideosRouter(dataDir, routerCfg));
  app.use('/api', makeSyncRouter(dataDir, routerCfg));

  app.get('/api/health', async (req, res, next) => { /* … disque + événement actif … */ });

  app.use((err, req, res, next) => { /* error handler, idem Hub */ });
  return app;
}
JS Injection de config par le spread : { ...cfg, requireAdmin: …, requireTech: … }

createApp(dataDir, cfg = config) prend la config en paramètre (avec le module config comme défaut). Cela permet aux tests de passer une config sur mesure. Ensuite : 

const routerCfg = { ...cfg, requireAdmin: requireAdmin(cfg), requireTech: requireTech(cfg) };

Le spread ...cfg copie tous les champs de la config dans un nouvel objet, puis on y ajoute deux propriétés requireAdmin et requireTech : les middlewares d'auth déjà « armés » avec cette config (rappel : requireAdmin(cfg) et requireTech(cfg) sont des factories). Chaque routeur reçoit donc routerCfg et y trouve à la fois les réglages (hubUrl, techPassword…) et les deux gardes prêtes à l'emploi — il choisit cfg.requireAdmin ou cfg.requireTech selon la route (§11.19), sans réimporter la config ni recréer le middleware. C'est de l'injection de dépendances « à la main », légère et explicite.

ℹ Pourquoi injecter la config plutôt que l'importer ? (vs Hub)

Le Hub importe directement config dans chaque fichier qui en a besoin. La Borne, elle, la fait circuler via cfg et routerCfg. Les deux marchent ; l'approche Borne rend les routeurs purs vis-à-vis de la config (ils ne dépendent pas d'un module global), donc plus faciles à tester en isolation avec une config arbitraire. C'est un choix de style cohérent avec les factories à closure de la Borne. Voir aussi Décisions d'architecture.

Le montage sous /api partagé

Contrairement au Hub qui monte chaque routeur sous un préfixe distinct (/api/events, /api/admin…), la Borne monte tous les routeurs sous /api : 

app.use('/api', makeEventsRouter(dataDir, routerCfg));
app.use('/api', makeSessionsRouter(dataDir, routerCfg));
// …

Chaque routeur déclare donc ses chemins complets en interne (/events, /sessions, /videos…). C'est un choix d'organisation : les routeurs Borne mélangent routes publiques (kiosque) et admin sur des chemins variés, et les regrouper sous un seul /api évite de fragmenter. L'ordre de montage reste important pour les mêmes raisons qu'au Hub (premier match gagne).

Le health check expose l'événement actif et le mode démo

app.get('/api/health', async (req, res, next) => {
  const stats = await statfs(dataDir);
  const activeEvent = getActiveEvent();
  const isPreview = !!(cfg.previewMode) || !!(activeEvent?.is_preview);
  res.json({ ok: true, activeEvent: activeEvent?.id ?? null, isPreview, disk: { free_bytes, total_bytes } });
});

Le health check de la Borne ajoute activeEvent : utile pour superviser « quel événement la borne sert actuellement ». L'activeEvent?.id ?? null combine optional chaining (si pas d'actif, undefined) et ?? null (normalisé en null).

Il expose aussi isPreview : true si la borne est en mode démo — soit via la config (cfg.previewMode), soit parce que l'événement actif a été pullé avec un token is_preview (§11.20/11.21). Le front interroge /api/health au démarrage pour décider d'afficher le bandeau « BORNE D'ESSAI » sur le kiosque et l'admin (composants UI, hors périmètre de ces pages serveur). C'est la même formule isPreviewMode() qui garde le push dans sync.js.

Démarrage + pull one-shot

if (process.argv[1] === new URL(import.meta.url).pathname) {
  mkdirSync(config.dataDir, { recursive: true });
  const app = createApp(config.dataDir);
  app.listen(config.port, async () => {
    // Pull one-shot au démarrage — bootstrappe l'événement du token si aucun n'est présent.
    // Les pulls suivants sont déclenchés manuellement depuis /admin/tech.
    let pullResult = null;
    if (config.hubUrl && config.boxToken) {
      pullResult = await pullMyEvent(config.dataDir)
        .then(n => ({ pulled: n > 0 }))
        .catch(err => ({ error: err.message }));
    }
    // … puis affiche une bannière de boot (port, Hub, événement actif, quota, secret JWT) …
  });
}
→ notion JS : le main module guard (vue dans Flux de démarrage)
ℹ Un seul pull, au démarrage (plus de timer périodique)

L'ancien autoPull.js (un setInterval toutes les 5 min + des heartbeats) a été supprimé. Désormais la Borne fait un pull au boot (pullMyEvent) si un Hub et un token sont configurés — juste pour bootstrapper l'événement du token si la borne est vierge. Le résultat est affiché dans la bannière de démarrage (✓ pull réussi / aucun événement pullable / l'erreur). Ensuite, toute synchro est manuelle depuis l'espace technicien (POST /sync/pull, swap de token, push…). Le mode autonome (pas de hubUrl/boxToken) saute simplement le pull.
