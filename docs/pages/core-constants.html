2 — Le package partagé

core/constants.js

Ce fichier centralise toutes les valeurs « magiques » du projet : les statuts d'un événement, les types de jobs, les limites (taille de vidéo, durée…), les valeurs par défaut. Le mettre dans core garantit que Hub et Borne partagent exactement les mêmes valeurs — impossible que la Borne plafonne une vidéo à 500 Mo et le Hub à 400.

Lecture du fichier

export const EVENT_STATUS = {
  DRAFT: 'draft',
  READY: 'ready',
  LOADED: 'loaded',
  LIVE: 'live',
  CLOSED: 'closed',
  PUSHED: 'pushed',
  PROCESSED: 'processed',
  PURGED: 'purged',
};

// Transitions légales (machine à états) — chaque statut avance vers le suivant
export const STATUS_ORDER = [
  'draft', 'ready', 'loaded', 'live', 'closed', 'pushed', 'processed', 'purged',
];
JS Un objet comme « enum », et const

JavaScript n'a pas de type enum natif (contrairement à Go ou Kotlin). L'idiome est un objet figé de constantes : EVENT_STATUS.DRAFT vaut la chaîne 'draft'. On y gagne des noms lisibles dans le code plutôt que des chaînes nues éparpillées.

const empêche de réassigner la variable (EVENT_STATUS = … échouerait), mais — piège classique — n'empêche pas de muter l'objet : EVENT_STATUS.DRAFT = 'x' passerait. C'est l'équivalent d'un pointeur constant vers une structure mutable.

LangageÉquivalent
Goconst ( Draft = "draft"; … ) ou un type dédié
Kotlinenum class ou object de const val
Pythonclass EventStatus(str, Enum)
JSconst EVENT_STATUS = { DRAFT: 'draft' }

Pour rendre l'objet réellement immuable, on utiliserait Object.freeze({...}). Kapsule ne le fait pas — par convention (on ne mute pas les constantes) plutôt que par garde-fou. Si tu veux durcir, Object.freeze est le bon outil ; en mode strict (ce que ESM active automatiquement), une mutation d'objet gelé lève une TypeError au lieu d'échouer silencieusement.

Noter la double représentation : EVENT_STATUS (objet, pour nommer un statut) et STATUS_ORDER (tableau, pour ordonner les statuts). Le tableau est ce qui permet de vérifier qu'une transition « avance » : on compare les indexOf. C'est utilisé par validate.js (assertStatus) et par les heartbeats du Hub.

TEXT_FIELDS est la source unique des textes du parcours invité personnalisables depuis l'admin. La même structure sert à deux endroits : le serveur itère ses clés pour valider et persister les champs reçus (route settings), et l'UI admin itère ses clés pour générer un <textarea> par champ. Deux clés ont un défaut dynamique (chaîne vide dans DEFAULTS) : welcome_title retombe sur le nom de l'événement et welcome_subtitle sur la 1ʳᵉ ligne du consentement — ce fallback est calculé côté serveur dans borne/routes/events.js, pas dans DEFAULTS. Comme le thème, ces textes sont des configs d'événement stockées dans event_meta — jamais de donnée invité dans registry.sqlite (invariant RGPD §11.13). TEXT_FIELD_MAX plafonne chaque champ pour éviter un payload abusif.

THEMES est une liste blanche : la route admin qui change le thème d'un événement valide la valeur reçue contre ce tableau (THEMES.includes(theme)) avant de l'écrire en base. 'modern' est volontairement plat (sans transparence ni backdrop-filter) pour rester léger à l'affichage sur le matériel Borne (Raspberry / iPad). Le thème est une config d'événement, stockée dans event_meta (events/<id>/db.sqlite) — jamais dans registry.sqlite (invariant RGPD §11.13). Détail côté serveur : borne/routes/events.js.

Détail d'écriture : 500 * 1024 * 1024 plutôt que 524288000. JS évalue la multiplication à la définition (une seule fois, au chargement du module) — on garde donc la lisibilité sans coût. C'est une habitude qu'on retrouve partout dans le projet.

💡 Recette : ajouter une limite ou un statut

Ajoute la valeur ici, dans LIMITS/DEFAULTS/EVENT_STATUS, puis importe-la là où tu en as besoin. Pour un nouveau statut, pense à l'ajouter aussi à STATUS_ORDER (sinon les vérifications de transition le rejetteront) et aux contraintes CHECK(...) des schémas SQL dans registry.js / borne registry.js, qui dupliquent volontairement la liste pour que SQLite refuse une valeur illégale.
